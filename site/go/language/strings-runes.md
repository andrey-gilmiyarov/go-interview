# Строки и руны

## Коротко

Строка Go — неизменяемая последовательность байтов. Она часто содержит UTF‑8-текст, но тип `string` сам по себе не гарантирует корректную кодировку. `len(s)` возвращает число байтов, `s[i]` — байт по индексу, а `for offset, r := range s` декодирует UTF‑8 и выдаёт начальный байтовый индекс и значение типа `rune` для каждого закодированного символа.

Руна — псевдоним `int32`, которым удобно представить кодовую точку Unicode. Она не обязательно совпадает с тем, что пользователь видит как один знак: эмодзи с модификатором или буква с комбинируемым ударением могут состоять из нескольких кодовых точек. Поэтому байты, руны и графемные кластеры отвечают на разные вопросы.

## Как работает

Строки сравниваются и индексируются как последовательности байтов. Это уместно для точного сравнения идентификаторов или ASCII-токенов, но не подходит для произвольного «символа номер три». При UTF‑8 символ занимает от одного до четырёх байтов; срез `s[1:3]` может разделить многобайтовую последовательность и создать некорректную строку. Поскольку строка неизменяема, изменить отдельный байт нельзя: обычно строят новую строку через `strings.Builder`, `strings.Replace` или конвертацию в `[]byte` с последующим обратным преобразованием.

Range по строке выполняет декодирование. Индекс — смещение байта, а значение — руна. Например, у `"ёж"` две руны, но четыре байта. Если байтовая последовательность содержит некорректный UTF‑8, range сообщает `utf8.RuneError` для ошибочного байта и продолжает обход; это не означает, что исходные байты были заменены внутри строки. Для проверки входного протокола вызовите `utf8.ValidString`, а для преобразования с явными границами используйте функции пакета `unicode/utf8`.

`[]rune(s)` полезно, когда алгоритму нужна работа с кодовыми точками, но преобразование создаёт отдельное представление и не решает сегментацию текста для пользовательского интерфейса. Преобразование `[]byte(s)` нужно для байтового протокола, хеширования или кодека; его не следует воспринимать как список букв. Если надо строить строку из множества частей, `strings.Builder` выразительнее повторного `result += part` в цикле: наивная конкатенация может копировать уже накопленный префикс снова и снова. Предварительная оценка через `Grow` — подсказка по объёму, а не обещание точного количества аллокаций.

Для backend важно определить границу данных. Если принимается текст, который должен быть валидным UTF‑8, проверяйте его при разборе запроса и возвращайте понятную ошибку. Если байты произвольны, используйте `[]byte` и формат кодирования, который сохраняет их точно. `encoding/json` v1 при записи строки заменяет некорректные UTF‑8-последовательности символом U+FFFD, поэтому двоичный payload нельзя безопасно переносить как будто это обычный текст. На границе HTTP также отдельно определяйте допустимую кодировку и правила нормализации; визуально одинаковые строки могут иметь различные последовательности кодовых точек.

## Пример

```go
package main

import (
	"fmt"
	"strings"
	"unicode/utf8"
)

func main() {
	text := "ёж"
	fmt.Println("байтов:", len(text), "рун:", utf8.RuneCountInString(text))
	for offset, r := range text {
		fmt.Printf("byte=%d rune=%U\n", offset, r)
	}

	broken := string([]byte{0xff, 'A'})
	fmt.Println("валидный UTF-8:", utf8.ValidString(broken))
	for offset, r := range broken {
		fmt.Printf("byte=%d rune=%U\n", offset, r)
	}

	var builder strings.Builder
	for _, part := range []string{"go", "-", "api"} {
		builder.WriteString(part)
	}
	fmt.Println(builder.String())
}
```

Для некорректной строки обход выдаёт `U+FFFD` на смещении ноль, затем продолжает со следующего байта. Само значение `broken` по-прежнему хранит исходный байт `0xff`.

## Ошибки и ограничения

- Не используйте `len(s)` как число видимых букв или даже кодовых точек.
- Не режьте UTF‑8-строку по произвольному смещению, если границы байтов не проверены.
- Не считайте `range` по строке средством проверки входа: проверяйте `utf8.ValidString`, если невалидные данные должны отклоняться.
- Не используйте тип `string` для произвольного двоичного содержимого только потому, что Go это допускает.
- Не полагайтесь на `[]rune` для границ, соответствующих пользовательским символам; для графем нужна отдельная Unicode-сегментация.
- Не обещайте фиксированное число аллокаций от `strings.Builder.Grow`; измеряйте конкретную нагрузку бенчмарком.

## Практика

Свяжите стоимость построения текста с упражнением [«Сборка строки»](/practice/allocations): сравнивайте корректность и профиль аллокаций на репрезентативных данных, не закрепляя абсолютные цифры.
