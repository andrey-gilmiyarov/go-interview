## Коротко

`defer` откладывает вызов функции до выхода из текущей функции: при обычном `return`, достижении закрывающей скобки или раскрутке panic. Отложенные вызовы выполняются в обратном порядке регистрации. Функция и её аргументы вычисляются в момент выполнения `defer`, а тело отложенной функции запускается позже.

`panic` запускает раскрутку текущей горутины и выполняет её отложенные функции. `recover` может остановить эту раскрутку, если вызван непосредственно внутри отложенной функции той же горутины. Это механизм границы отказа, а не обычная замена `error` для ожидаемых ошибок.

## Как работает

В выражении `defer log(value)` копируются функциональное значение и аргументы прямо сейчас. Если `value` позднее изменится, отложенный вызов всё равно получит сохранённую копию. В `defer func() { log(value) }()` откладывается вызов замыкания: оно обращается к переменной и прочитает её новое содержимое при выполнении. При нескольких отложенных вызовах последним выполнится тот, который был зарегистрирован первым. Это естественно раскручивает ресурсы: сначала захватить внешний ресурс, затем внутренний; LIFO-порядок defer закроет сначала внутренний, затем внешний.

`defer` относится к функции, а не к ближайшим фигурным скобкам. Поэтому `defer body.Close()` внутри цикла оставит все тела открытыми до возврата из внешней функции. Для большого потока файлов или ответов это может исчерпать файловые дескрипторы. Вынесите работу с одним ресурсом во вспомогательную функцию, чтобы defer выполнился при завершении одной итерации, или явно закройте ресурс в подходящем месте.

Результаты функции вычисляются перед запуском defer. Если результат именованный, отложенная функция может его прочитать и поменять. Это позволяет обогатить результат, например добавить ошибку закрытия к возвращаемой ошибке. Но такой код влияет на внешний контракт функции и может удивить читателя; используйте именованный результат только когда связь видна и покрыта проверкой.

При panic Go выполняет отложенные функции по цепочке вызовов вверх по текущей горутине. Отложенная функция может вызвать `recover` напрямую и получить значение паники. Вызов `recover` в обычной функции или косвенно через отдельную helper-функцию не останавливает раскрутку. Паника в другой горутине не может быть поймана defer-ом вызывающей горутины: границы горутин независимы. После успешного восстановления стек между местом паники и функцией, вызвавшей `recover`, не возобновляется; выполнение возвращается из функции, чей defer восстановил панику.

На серверной границе восстановление иногда уместно, чтобы один некорректный запрос не завершил весь процесс. Такая граница должна записать диагностику с request ID, не раскрыть внутренние детали клиенту и определить, можно ли продолжать работу после нарушения инварианта. В обычных слоях приложения ожидаемое отсутствие записи, конфликт или ошибка сети должны идти через `error`: их можно классифицировать, объединять с контекстом и преобразовать в HTTP-ответ. Безусловный `recover` скрывает дефекты и превращает некорректное состояние в трудноотслеживаемый частичный успех.

## Пример

```go
package main

import "fmt"

func namedResult() (result int) {
	defer func() { result++ }()
	return 4
}

func showEvaluationTime() {
	value := "до"
	defer fmt.Println("аргумент:", value)
	defer func() { fmt.Println("замыкание:", value) }()
	value = "после"
}

func isolatedBoundary() {
	defer func() {
		if recovered := recover(); recovered != nil {
			fmt.Println("восстановлено:", recovered)
		}
	}()
	panic("неверная запись")
}

func main() {
	fmt.Println("результат:", namedResult())
	showEvaluationTime()
	isolatedBoundary()
}
```

`namedResult` сначала устанавливает `4`, затем defer меняет именованный результат на `5`. В `showEvaluationTime` замыкание печатает `после`, а сохранённый аргумент — `до`; порядок строк соответствует обратному порядку defer.

## Ошибки и ограничения

- Не переносите `defer` из короткой функции ресурса во внешний цикл без оценки времени удержания ресурса.
- Не ожидайте, что defer-аргумент увидит позднее значение переменной; для этого нужно замыкание.
- Не пытайтесь восстановить panic другой горутины из родительской горутины.
- Не оборачивайте каждый вызов в `recover`: восстановление оправдано на документированной границе, где определён ответ после сбоя.
- Не используйте `panic` для обычной валидации запроса или ожидаемой ошибки зависимости.
- Не рассчитывайте на изменение результата от defer, если функция не использует именованный результат.
