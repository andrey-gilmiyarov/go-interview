# Сборка и toolchain

## Коротко

Строка go в <code>go.mod</code> задаёт минимальную версию Go, языковые правила и часть поведения команды go; это не обязательно точная версия установленного компилятора. Строка toolchain предлагает версию toolchain для главного модуля. В этом репозитории <code>go 1.27.0</code> сочетается с <code>toolchain go1.27.1</code>, и локальная команда go version подтверждает <code>go1.27.1</code>.

Повторяемая сборка зависит и от других входов. Выбор файлов меняют <code>GOOS</code>, <code>GOARCH</code>, build tags и <code>CGO_ENABLED</code>; cgo добавляет внешний C-компилятор и системное окружение. Эти параметры определяют, какой код попадёт в бинарный файл.

## Как работает

Начиная с Go 1.21 строка go — обязательный минимум: слишком старый toolchain откажется работать с модулем, которому нужна более новая версия. Она также ограничивает языковые возможности пакетов. Build constraint с версией Go, например <code>//go:build go1.27</code>, может задать языковую версию для отдельного файла. Поэтому факт «компилируется локально» сам по себе не отвечает на вопрос о минимальной версии всего модуля.

<code>toolchain go1.27.1</code> предлагает toolchain для главного модуля, но не запрещает более новый установленный компилятор. При <code>GOTOOLCHAIN=auto</code> команда go может переключиться на нужную версию и при необходимости загрузить её; при <code>GOTOOLCHAIN=local</code> неожиданное требование новой версии завершится ошибкой. В CI локальный режим полезен, если образ уже устанавливает требуемый компилятор: он не маскирует неверно подготовленное окружение автоматической загрузкой. Проверяйте go version и go env GOTOOLCHAIN, а не только текст <code>go.mod</code>.

Build constraint — условие включения файла в пакет. На выбор влияют ОС и архитектура, языковая версия, явно заданные теги через <code>-tags</code> и специальные условия вроде cgo. Теги могут менять набор исходников и тестов, следовательно, поведение бинарного файла. cgo обычно включён для нативной сборки, где он поддерживается, и выключен по умолчанию при cross-compile. Для него нужны доступный C-компилятор и совместимый системный toolchain; одного <code>CGO_ENABLED=1</code> недостаточно.

Чтобы повторить выпуск, фиксируйте toolchain, версии модулей, <code>GOOS</code>, <code>GOARCH</code>, <code>CGO_ENABLED</code>, теги, C-компилятор, флаги сборки и шаги генерации исходников. Флаг <code>-trimpath</code> удаляет абсолютные пути файлов из результата, но не делает сборку автоматически побитово одинаковой. <code>-buildvcs</code> управляет встраиванием VCS-информации; в режиме auto команда go добавляет её, когда пакет, модуль и текущая директория принадлежат одному репозиторию. Эти параметры помогают управлять источниками различий, но не заменяют запись полного контекста выпуска.

## Пример

Программа выводит runtime и версию Go, которой она была собрана. <code>ReadBuildInfo</code> возвращает сведения, встроенные командой go; одинаковая версия в строках ниже не доказывает, что совпали целевая платформа и параметры сборки.

~~~go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func main() {
	build, ok := debug.ReadBuildInfo()
	if !ok {
		fmt.Println("build info unavailable")
		return
	}
	fmt.Printf("runtime=%s compiler=%s go=%s\n", runtime.Version(), runtime.Compiler, build.GoVersion)
}
~~~

Для анализа уже собранного бинарного файла используйте go version -m ./app. Для анализа выбора файлов сравните go list с нужными тегами. В этом проекте тест заготовки practice/slice-alias/starter/starter_test.go помечен //go:build exercise, поэтому вывод о test-файлах различается с тегом и без него:

~~~sh
go list -f '{{.TestGoFiles}}' ./practice/slice-alias/starter
go list -tags=exercise -f '{{.TestGoFiles}}' ./practice/slice-alias/starter
~~~

Тег только включает файл. Tagged-проверка заготовки здесь намеренно не является обычным тестом и может падать до реализации упражнения.

## Ошибки и ограничения

- Не трактуйте toolchain как запрет запускать более новую версию; для контроля используйте управляемый образ и проверку go version.
- Не меняйте строку go ради исправления отдельной ошибки сборки: она меняет минимальную версию и языковые правила модуля.
- Не считайте <code>GOOS</code> и <code>GOARCH</code> единственными измерениями платформы; cgo требует C-компилятор, а tags могут исключить нужную реализацию.
- Не используйте <code>-trimpath</code> как доказательство идентичности двух бинарных файлов. Сверяйте toolchain, параметры, зависимости, исходники и VCS-данные.
- Автоматическое переключение toolchain удобно локально, но CI должен явно сообщать, какую версию использовал.
- Не выводите переносимость только из статической линковки: при cgo и целевой среде важны C ABI, системные библиотеки и доступность внешних данных вроде сертификатов или timezone.

## Практика

Перед диагностикой сборки запишите вывод go version и go env GOTOOLCHAIN <code>GOOS</code> <code>GOARCH</code> <code>CGO_ENABLED</code>. Затем сравните команды go list из примера для исходников и тестов с тегом exercise и без него. После cross-compile проверьте, какие файлы попали в сборку и доступен ли C toolchain. В release pipeline используйте go version -m для артефакта и храните рядом проверенный набор параметров.
