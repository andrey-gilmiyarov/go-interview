# Модули и зависимости

## Коротко

Пакет — файлы Go в одной директории, которые компилируются вместе. Модуль — версиями управляемая коллекция пакетов, публикуемая как одно целое. Путь импорта пакета складывается из пути модуля и подкаталога. Например, <code>errgroup</code> и <code>semaphore</code> — разные пакеты одного модуля golang.org/x/sync.

В корневом <code>go.mod</code> этого проекта указаны модуль github.com/andreygilmiyarov/go-interview, минимум <code>go 1.27.0</code>, предложенный <code>toolchain go1.27.1</code> и требование golang.org/x/sync v0.22.0. Требование входит в граф зависимостей; оно не означает «всегда брать последнюю версию».

## Как работает

Версия модуля имеет вид vMAJOR.MINOR.PATCH. По договору SemVer несовместимое изменение требует нового major-релиза. В Go для модулей v2 и выше major включается в путь импорта, например <code>/v2</code>. Поэтому несовместимые версии имеют разные пути и могут сосуществовать в одной сборке. v0 не обещает обратной совместимости; v1 — договор автора модуля, а не свойство, которое проверяет компилятор.

Команда go строит граф требований из <code>go.mod</code> главного модуля и его зависимостей. Алгоритм minimal version selection (MVS) выбирает для каждого пути модуля самую высокую требуемую версию в этом графе. Если приложение требует <code>shared v1.2.0</code>, а транзитивный модуль требует <code>shared v1.5.0</code>, будет выбрана v1.5.0. Это не поиск самой новой опубликованной версии в реестре. go mod graph показывает рёбра требований, а go list -m all — итоговый build list. Для намеренного обновления задайте версию через go get; go mod tidy затем согласует <code>go.mod</code> и <code>go.sum</code> с импортами пакетов и тестов.

<code>go.sum</code> хранит криптографические хэши загруженных архивов и файлов <code>go.mod</code> зависимостей. Команда go проверяет содержимое при загрузке. Файл может содержать хэши нескольких версий одного модуля и отдельный хэш только <code>go.mod</code>; он не выбирает версии вместо <code>go.mod</code> и MVS. Поэтому <code>go.sum</code> — контрольные суммы, а не lock-файл. Успешная проверка подтверждает ожидаемое содержимое, но не доказывает, что код зависимости безопасен или подходит продукту.

go mod verify проверяет локальный кеш на изменение после загрузки, но не анализирует смысл кода. go mod vendor копирует нужные исходники в vendor; режим vendoring использует эту копию, однако обновление vendor — отдельное изменение, которое следует ревьюить вместе с <code>go.mod</code> и <code>go.sum</code>. Начинайте диагностику неожиданной версии с графа и импорта, а не с ручного редактирования хэшей.

## Пример

Фрагмент <code>go.mod</code> проекта и небольшая программа, использующая пакет <code>errgroup</code> из указанного модуля:

~~~text
module github.com/andreygilmiyarov/go-interview

go 1.27.0
toolchain go1.27.1

require golang.org/x/sync v0.22.0
~~~

~~~go
package main

import (
	"fmt"

	"golang.org/x/sync/errgroup"
)

func main() {
	var group errgroup.Group
	group.Go(func() error { return nil })
	fmt.Printf("wait=%v\n", group.Wait())
}
~~~

Запуск из корня модуля печатает <code>wait=&lt;nil&gt;</code>. Импорт указывает пакет <code>errgroup</code>, а require выбирает версию модуля, который его поставляет. Посмотреть выбранную версию и граф можно командами:

~~~sh
go list -m golang.org/x/sync
go mod graph
~~~

## Ошибки и ограничения

- Не считайте прямое требование единственным источником версии: транзитивные требования входят в MVS.
- Не заменяйте анализ <code>go.mod</code> чтением <code>go.sum</code>: хэши не показывают, какую версию выбрал граф.
- Не называйте go mod tidy командой «обновить всё до latest»: она синхронизирует граф с импортами, а для обновления задайте цель явно.
- Не удаляйте <code>go.sum</code> ради чистоты: при следующей загрузке хэши будут рассчитаны заново, а история проверки станет менее понятной.
- Не смешивайте replace для локальной разработки с опубликованным контрактом: замена действует только в главном модуле и может скрыть несовпадение с релизом.
- Хэши и ревью зависимостей решают разные задачи; go mod verify не является аудитом безопасности.

## Практика

В корне проекта сравните go list -m all с go mod graph, найдите, почему нужен golang.org/x/sync, и выполните go mod verify. Перед сменой версии сформулируйте причину, проверьте diff <code>go.mod</code> и <code>go.sum</code> и прогоните тесты потребляющих пакетов. Если новый граф неожиданен, сохраните вывод go mod graph для ревью.
