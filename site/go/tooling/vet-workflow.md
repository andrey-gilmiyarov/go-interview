# Проверки Go-кода в ежедневной работе

## Коротко

Форматтер, статический анализ, тесты, race detector, fuzzing и бенчмарки отвечают на разные вопросы. Для обычного изменения начните с форматирования затронутых файлов, затем запустите go vet и go test для затронутых пакетов. Более дорогие проверки добавляйте по риску: <code>-race</code> для конкурентного кода, fuzzing для большого пространства входов, benchmark — когда есть вопрос о производительности.

Ни один зелёный прогон не доказывает, что программа верна для всех данных и расписаний. Значение имеют выбранные пакеты, build tags, окружение и пути, которые реально исполнили тесты.

## Как работает

gofmt приводит исходники к стандартному формату, но не проверяет логику. go vet запускает анализаторы подозрительных конструкций. Например, он сверяет формат <code>fmt.Printf</code> с типами аргументов. Эти проверки используют эвристики: анализатор может пропустить дефект, а предупреждение не является спецификацией поведения программы.

go test запускает тесты пакета и перед ними автоматически включает подмножество vet-анализаторов с высоким уровнем уверенности, например проверки форматных строк, <code>errors.As</code> и тестовых деклараций. Отдельный go vet ./путь/к/пакету запускает стандартный набор vet-проверок выбранных пакетов. Если тест остановился до выполнения из-за vet-сообщения, исправьте причину и перезапустите тест; не отключайте анализатор лишь ради зелёного отчёта.

go test <code>-race</code> инструментирует код и сообщает о гонках данных, которые возникли в наблюдённом выполнении. Он не перебирает все расписания и не доказывает отсутствие гонок. Race detector требует cgo, работает только на поддерживаемых сочетаниях ОС и архитектуры и обычно увеличивает время и расход памяти. Сочетайте его с тестами, проходящими по опасным interleaving-ам; основы happens-before описаны в [модели памяти Go](../concurrency/memory-model-atomic.md).

Fuzz-тест запускает функцию на seed corpus и генерируемых входах. Он полезен для парсеров и декодеров, если тест проверяет инвариант или отсутствие panic и ограничивает ресурсы. Короткий локальный прогон может найти воспроизводимый случай, но не заменяет контрактные сценарии. Бенчмарк отвечает на узкий вопрос о стоимости операции на выбранной машине и входе; сравнивайте повторы на одной версии и в одинаковых условиях, а не считайте <code>ns/op</code> постоянной.

Привязывайте проверки к стоимости обратной связи. На каждом изменении форматируйте и проверяйте затронутый пакет; на CI запускайте согласованный полный набор. Fuzzing и benchmark можно держать отдельными шагами, если они дороги или нужны не каждому pull request. Контрактные unit/integration-проверки разобраны в статье [«Модульные и интеграционные тесты»](../testing/unit-integration.md).

## Пример

Исправный вызов компилируется и проходит проверку формата:

~~~go
package main

import "fmt"

func main() {
	name := "Mira"
	fmt.Printf("user=%s\n", name)
}
~~~

Если заменить %s на %d, программа всё ещё компилируется, но go vet сообщает, что аргумент string не подходит формату %d. Запустите проверку для конкретного пакета, затем его тесты:

~~~sh
go vet ./practice/slice-alias/solution
go test ./practice/slice-alias/solution
~~~

Для конкурентного пакета добавьте go test <code>-race</code> на поддерживаемой платформе. Не включайте инструмент без разбора в каждую задачу CI: он полезен только для исполненных путей, а дополнительные ресурсы увеличивают цикл обратной связи.

## Ошибки и ограничения

- Не считайте go vet полной проверкой ошибок: он ищет подозрительные конструкции, но не доказывает корректность бизнес-логики.
- Не считайте зелёный go test доказательством отсутствия гонок или успешной обработки каждого входа.
- Не запускайте fuzzing без проверяемого свойства; случайные входы не заменяют спецификацию контракта.
- Не используйте benchmark как тест корректности и не сравнивайте единичные измерения на разных машинах.
- Не игнорируйте build tags: нужная реализация или тестовый файл может вообще не попасть в проверку.
- Не задавайте одинаковый набор дорогих проверок для локального цикла и release CI; у них разная цена и цель.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Что доказывает успешный go vet?</summary>

Только отсутствие замечаний выбранных анализаторов в проверенных пакетах. Это не доказательство корректной логики, полного покрытия или правильных внешних эффектов. Senior follow-up: какие инварианты лучше закрепить тестом, а какие проверить ревью или измерением?

</details>

<details>
<summary>Почему go test <code>-race</code> может пройти, хотя в коде есть гонка?</summary>

Детектор сообщает только о гонках, возникших на выполненных путях и расписаниях; тест мог не попасть в опасное чередование. Senior follow-up: как сделать синхронизацию и rendezvous в тесте детерминированными?

</details>

<details>
<summary>Когда benchmark нужно запускать отдельно от обычного теста?</summary>

Когда вопрос касается производительности, а подготовка данных, повторы и среда должны быть контролируемы. Senior follow-up: что вы оставите одинаковым между базовым и новым результатом?

</details>

## Практика

Для локального цикла возьмите изменённый пакет: сначала примените gofmt к затронутым .go-файлам, затем запустите go vet и go test только этого пакета. Если изменение затрагивает конкурентность, дополните go test <code>-race</code>; если пакет содержит fuzz-тест для конкретного инварианта, задайте короткий -fuzztime. Отдельный benchmark запускайте при наличии вопроса о производительности. Сравнение измерений и профилирование разобраны в статьях [«Бенчмарки»](../testing/benchmarks.md) и [«Профилирование и execution trace»](../testing/pprof-trace.md).
