# Стек горутины и escape analysis

## Коротко

Переменная в Go не обязана жить в куче лишь потому, что для неё написано <code>new</code>, <code>make</code> или взят адрес. Компилятор анализирует, может ли значение пережить область, где оно создано, и выбирает размещение. В runtime Go 1.27.1 пользовательские стеки горутин растут и могут уменьшаться; конкретный размер стека и решение escape analysis не входят в гарантии языка.

## Как работает

Каждая выполняющаяся горутина использует собственный пользовательский стек. Он начинается небольшим и растёт, когда очередной вызов требует больше места. Текущий компилятор вставляет проверку границы стека; при необходимости runtime выделяет больший непрерывный диапазон, копирует активные кадры и исправляет ссылки на адреса внутри стека. Рост не требует заранее резервировать большой фиксированный стек каждому запросу. При завершении горутины её стек может быть освобождён или переиспользован runtime; это не означает, что память немедленно вернётся ОС.

Escape analysis решает другую задачу: может ли значение оставаться привязанным к кадру текущего вызова? Если указатель сохранён в глобальной переменной, возвращён вызывающему коду или записан в объект с более долгим временем жизни, данные должны пережить исходный кадр. Текущий компилятор обычно переносит такое значение в управляемую кучу. Если компилятор доказывает, что значение используется только в пределах кадра, он может держать его на стеке или вовсе устранить после оптимизации.

Решение не определяется отдельным синтаксисом. Адрес локальной переменной может быть безопасно возвращён: runtime и GC обеспечат необходимое время жизни. И наоборот, короткий вызов <code>new(T)</code> не означает обязательную аллокацию в куче: если указатель не утекает за область вызова, компилятор может выбрать стек. Встраивание функции, размер значения, динамический размер backing array, замыкание, интерфейсное преобразование и дальнейшее использование вместе влияют на анализ. Алгоритм компилятора меняется от релиза к релизу.

Для диагностики используйте сообщения установленного компилятора, а не таблицу правил вроде «возврат указателя всегда heap». Флаг <code>-m=2</code> выводит причины решений об escape и inlining. Повторяйте наблюдение с той же версией Go, build tags и оптимизационными флагами, что и у целевого бинарного файла. Это инструмент объяснения текущего сборочного контекста, а не часть контракта программы.

## Пример

~~~go
package main

import "fmt"

var published *int

func localSum(values []int) int {
	total := 0
	for _, value := range values {
		total += value
	}
	return total
}

func publish(value int) {
	published = &value
}

func main() {
	fmt.Println("sum:", localSum([]int{1, 2, 3}))
	publish(42)
	fmt.Println("published:", *published)
}
~~~

Программа выводит сумму и значение 42. Локальный накопитель не обязан покидать кадр <code>localSum</code>; в <code>publish</code> указатель сохраняется в глобальном состоянии и должен оставаться действительным после возврата. Посмотрите решение именно вашей версии компилятора:

~~~sh
go run -gcflags=-m=2 main.go
~~~

Для этого запуска положите пример в отдельный файл <code>main.go</code>; вывод включает диагностику компиляции и обычный результат программы.

## Ошибки и ограничения

- Не пытайтесь гарантировать размещение ради производительности: ни стек, ни куча не являются источником наблюдаемой семантики программы.
- Не называйте «escape» утечкой памяти. Утёкшее в кучу значение всё ещё собирается, когда оно недостижимо; ошибка удержания обычно начинается с живой ссылки или необоснованного cache.
- Не используйте <code>uintptr</code> вместо корректного указателя, чтобы скрыть связь времени жизни от компилятора или GC.
- Глубокая рекурсия и большие кадры могут увеличить использование стека; бесконечная рекурсия всё равно завершится аварией, а не бесконечным ростом.
- Ручной pooling меняет время жизни объектов и может увеличить удерживаемую память. Сначала сравните allocation profile и benchmark; не переносите решение escape analysis одной версии на будущую.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Гарантирует ли new(T), что объект окажется в куче?</summary>

Нет. <code>new(T)</code> создаёт указатель на нулевое значение типа <code>T</code>, но место размещения выбирает реализация. Если компилятор доказывает короткое время жизни, он может держать значение на стеке или устранить его. Senior follow-up: каким выводом компилятора и каким профилем вы проверите свой реальный hot path?

</details>

<details>
<summary>Почему publish сохраняет value после возврата функции?</summary>

Адрес записывается в глобальную переменную, поэтому стековый кадр функции не может быть единственным местом хранения значения. Компилятор Go 1.27.1 перемещает его в кучу в этом примере. Senior follow-up: что изменится, если вызывающий код немедленно разыменует указатель и нигде его не сохранит?

</details>

<details>
<summary>Что происходит при росте стека горутины, если стек располагался по другому адресу?</summary>

Runtime копирует используемую часть в новый диапазон и обновляет указатели, связанные с кадрами и состоянием выполнения. Код Go видит те же значения и адреса только в рамках действующих правил указателей. Senior follow-up: почему сохранение сырого адреса в uintptr может нарушить эту модель?

</details>
