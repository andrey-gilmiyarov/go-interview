# Планировщик, netpoll и системные вызовы

## Коротко

Спецификация Go описывает горутины и наблюдаемое поведение программы, но не обещает конкретное отображение горутин на потоки ОС. В runtime Go 1.27.1 планировщик связывает G (goroutine), M (OS thread) и P (ресурсы для исполнения Go-кода). Сетевой poller позволяет при поддержке ОС припарковать ожидающую сетевого события горутину, не удерживая отдельный поток на каждый сокет. <code>GOMAXPROCS</code> ограничивает одновременное исполнение пользовательского Go-кода, а не число горутин или потоков процесса.

## Как работает

G описывает ход выполнения и его стек; G может быть исполняемой, готовой к запуску или ожидающей канала, таймера, ввода-вывода и других событий. M — поток ОС, на котором исполняется код. P содержит ресурсы, необходимые runtime для запуска пользовательских горутин: ровно столько P, сколько сейчас задаёт <code>GOMAXPROCS</code>. Для исполнения Go-кода нужны одновременно G, M и P; очередь исполняемых G может быть намного длиннее числа P.

Когда G блокируется на канале, она переходит в ожидание, а M/P могут выполнять другую работу. С обычным сетевым соединением runtime вместе с пакетом <code>net</code> использует неблокирующий ввод-вывод и poller ОС: пока сокет не готов, G ждёт событие, а поток доступен для других горутин. Конкретный механизм зависит от платформы. Обычный блокирующий системный вызов отличается: M может оставаться внутри ОС-вызова, но runtime способен отдать его P другому M. Когда вызов завершится, прежней G ещё нужно получить P, прежде чем продолжить пользовательский код. Поэтому большое число блокирующих syscall или вызовов C может увеличить число M, даже если P мало.

Это объясняет важную границу: увеличение числа горутин не означает увеличение параллелизма CPU. Если все P заняты вычислениями, дополнительные G ждут планировщика; если они ждут I/O, новые готовые G всё ещё могут использовать доступные P. <code>GOMAXPROCS</code> — не предел на число потоков, сокетов, горутин и не квота на стендовое время процесса.

Начиная с Go 1.25 стандартное значение на Linux учитывает CPU bandwidth limit cgroup наряду с доступными логическими CPU и affinity; runtime также может периодически пересчитывать его. В Go 1.27.1 автоматическое обновление отключено, если приложение задаёт <code>GOMAXPROCS</code> через переменную окружения или вызов <code>runtime.GOMAXPROCS</code>. Это деталь текущего runtime, а не гарантия языка. Например, вручную закрепив значение при старте контейнера, приложение может продолжить использовать его после изменения лимита cgroup.

## Пример

~~~go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	fmt.Println("логических CPU при запуске:", runtime.NumCPU())
	fmt.Println("одновременных исполнителей Go:", runtime.GOMAXPROCS(0))
}
~~~

Вторая строка показывает текущий лимит параллельного исполнения Go-кода и ничего не меняет: аргумент меньше единицы только запрашивает текущее значение. Числа зависят от среды и не должны проверяться тестом на конкретное значение. Если приложение задаёт лимит вручную, сохраните предыдущее значение через <code>old := runtime.GOMAXPROCS(0)</code> и восстановите только если это действительно требуется границей теста или компонента: такой вызов меняет общий для процесса runtime.

## Ошибки и ограничения

- Не считайте, что на каждую горутину создан поток ОС или что число M всегда равно числу P.
- Не увеличивайте <code>GOMAXPROCS</code> в ответ на задержку без профиля: узким местом может быть блокировка, конкуренция за mutex, лимит CPU контейнера или внешний сервис.
- Не трактуйте ожидание сетевого сокета как гарантию одного универсального механизма poller для всех типов файлов и платформ.
- При диагностике сначала отделите runnable-очередь от goroutine, ожидающих ресурс. Исполнительный trace показывает переходы и сетевое ожидание; метрики <code>/sched/goroutines/runnable</code>, <code>/sched/goroutines/waiting</code> и <code>/sched/latencies</code> помогают понять, ждёт ли работа планировщика.
- Блокирующие syscall не становятся асинхронными только потому, что вызваны из горутины; для долгого внешнего вызова отдельно ограничивайте параллелизм и время ожидания.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Почему сотни тысяч горутин могут работать при GOMAXPROCS=4?</summary>

Большинство из них могут быть ожидающими, а одновременно исполнять пользовательский Go-код runtime разрешает четырём P. Ожидание не требует выделить каждой G отдельный M. Senior follow-up: какая метрика отличит избыток ожидающих задач от очереди runnable-задач, и какой trace подтвердит причину?

</details>

<details>
<summary>Что происходит с P, если M вошёл в блокирующий системный вызов?</summary>

Поток может продолжать ждать внутри syscall, а runtime может передать его P другому M для пользовательского Go-кода. Вернувшаяся G должна снова получить P. Senior follow-up: как изменится поведение между обычным syscall, сетевым ожиданием через poller и cgo-вызовом?

</details>

<details>
<summary>Почему ручной GOMAXPROCS может плохо соответствовать изменившемуся лимиту контейнера?</summary>

Явно заданное значение отключает автоматическое обновление стандартного значения. После изменения cgroup лимита оно может стать слишком большим или слишком маленьким. Senior follow-up: как проверить эффективный лимит на том же окружении, где работает сервис?

</details>
