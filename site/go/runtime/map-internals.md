# Внутреннее устройство map

## Коротко

Гарантии языка для <code>map</code> — чтение, запись, удаление, сравнимость ключа и семантика обхода. Формат хранения, хеширование и рост не являются публичным контрактом. Начиная с Go 1.24 встроенные карты в стандартной реализации Go используют Swiss-table design; в Go 1.27.1 source это таблицы группами по восемь слотов, а крупная карта управляет несколькими таблицами через directory.

## Как работает

Для чтения реализация вычисляет хеш ключа, выбирает начальную группу и ищет кандидатов. Каждая группа содержит восемь пар ключ/значение и контрольное слово. Восемь байтов контроля соответствуют слотам: байт отмечает пустой, удалённый или занятый слот, а для занятого хранит короткий фрагмент хеша. Сравнение фрагментов помогает быстро отсеять большинство ключей; совпавший фрагмент всё равно требует обычного сравнения ключа. При коллизии поиск проверяет следующую группу по последовательности пробирования.

Удаление связано с этим поиском. Runtime завершает пробирование, когда встречает пустой слот: дальше по этой последовательности искомого ключа быть не может. Если до удаления в группе нет пустых слотов, она может находиться в середине probe sequence. Пометив удалённый слот пустым, runtime преждевременно завершил бы поиск ключа, который лежит в последующей группе той же последовательности пробирования. В Go 1.27.1 в такой группе слот получает tombstone, сохраняющий путь поиска; если до удаления в группе уже есть пустой слот, удалённый слот можно пометить пустым без tombstone. Tombstone сохраняет состояние пробирования, но не сам элемент. Вставка может переиспользовать такое место, а runtime управляет tombstones и ростом таблицы при нехватке ёмкости.

Один большой массив потребовал бы дорого перераспределить все записи при росте. Реализация Go делит карту на таблицы: directory использует часть хеша, чтобы направить ключ в нужную таблицу, а рост затрагивает соответствующую часть структуры. В Go 1.27.1 это детали реализации и оптимизации задержек. Они не разрешают приложению рассчитывать точное число записей до роста, размер слота, capacity или время одной вставки. Гарантия языка для подсказки ёмкости — она не ограничивает число элементов, которое можно записать в карту.

Контракт обхода остаётся независимым от Swiss-table layout: порядок не специфицирован; запись, добавленная во время range, может быть показана или пропущена; запись, удалённая до достижения, не будет показана. Текущая реализация специально поддерживает эти правила и рандомизирует порядок, но приложение должно проектироваться по спецификации, а не наблюдаемому порядку одного запуска.

## Пример

~~~go
package main

import "fmt"

func main() {
	counts := make(map[string]int, 8)
	counts["ready"]++
	counts["failed"]++

	value, exists := counts["missing"]
	fmt.Println("missing:", value, "present:", exists, "len:", len(counts))

	delete(counts, "failed")
	fmt.Println("ready:", counts["ready"], "len:", len(counts))
}
~~~

Чтение отсутствующего ключа даёт нулевое значение, а второй результат различает его с сохранённым нулём. Подсказка 8 помогает выразить ожидаемую нагрузку, но не сообщает программе, сколько групп runtime создал и когда он изменит структуру. Обычная логика не требует знать ни о хеш-фрагментах, ни о tombstones.

## Ошибки и ограничения

- Не рассчитывайте индекс, число buckets, коэффициент роста или внутреннюю capacity по старым версиям runtime. Go 1.24 и новее использует другую реализацию; и она тоже может измениться.
- Не выводите порядок из текущего расположения групп. Спецификация оставляет его неопределённым и между обходами он может отличаться.
- Не используйте одну обычную map из нескольких горутин, если хотя бы одна пишет: built-in map сама не предоставляет синхронизацию.
- Не ожидайте, что <code>delete</code> или <code>clear</code> сразу вернут память операционной системе или уменьшат карту. Если большая временная карта должна освободить память, после потери всех ссылок измерьте поведение процесса.
- Не используйте map как замену упорядоченной коллекции. Для стабильного результата извлеките ключи и отсортируйте их.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Почему tombstone не всегда можно превратить в пустой слот сразу после delete?</summary>

Поиск мог пройти через полную группу, где лежит удалённый элемент, чтобы найти другую запись. Если удалить след из probe sequence, lookup может завершиться раньше нужного ключа. Senior follow-up: при каких условиях runtime может безопасно пометить слот пустым?

</details>

<details>
<summary>Что означает make(map[K]V, 100) для приложения?</summary>

Это подсказка начальной ёмкости, а не верхняя граница и не контракт точной физической capacity. Размер карты может расти сверх неё, а layout остаётся решением реализации. Senior follow-up: как определить полезность предварительной ёмкости по профилю реальной нагрузки?

</details>

<details>
<summary>Что язык обещает про порядок и вставку элемента во время range?</summary>

Порядок не специфицирован; новая запись может быть выдана или пропущена, а удалённая до достижения не будет выдана. Senior follow-up: какой слой кода должен задать порядок, если он влияет на API-ответ или подпись?

</details>
