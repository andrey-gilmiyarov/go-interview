# Аллокации, layout и плотность указателей

## Коротко

Аллокация — решение компилятора и runtime о времени жизни и размещении значения, а не простой подсчёт вызовов <code>new</code>. Layout структуры влияет на размер, locality и число затрагиваемых cache lines; количество указателей в живых данных влияет на работу GC. Это можно измерять, но конкретные размеры и скорость зависят от архитектуры, сборки и нагрузки.

## Как работает

Порядок полей входит в описание и идентичность типа структуры, но спецификация не обещает переносимые offsets, padding или размер структуры на всех архитектурах. Текущий компилятор добавляет padding, чтобы соблюсти выравнивание полей, заданное ABI целевой платформы. Поэтому два типа с теми же полями в разном порядке могут занимать разный объём. <code>unsafe.Sizeof</code> измеряет непосредственный размер значения: для среза это размер заголовка, а не backing array; для указателя — не размер объекта, на который он ссылается. Внешний код, сохраняющий raw layout или использующий unkeyed composite literals, может сломаться при перестройке полей, поэтому менять публичную структуру ради нескольких байтов нужно как API-изменение.

Размещение объекта также не следует из синтаксиса. Компилятор может держать значение на стеке, убрать его после оптимизации или выделить в куче, если время жизни выходит за кадр. Кучевые объекты под управлением Go становятся работой GC; pointer-free массив значений проще трассировать, чем граф с большим числом ссылок на объекты. Плотность указателей важна поэтому не только для памяти: каждому достижимому указателю сборщику может потребоваться переход и сканирование объекта. Подробная граница escape analysis описана в [соседней теме](./stacks-escape.md).

При проходе только по одному полю часто полезна структура из нескольких срезов: значения нужного столбца лежат рядом, и CPU загружает меньше нерелевантных данных. Массив структур может быть удобнее, если операция почти всегда использует все поля одной записи; его элементы также естественно передавать и хранить как цельный объект. Это trade-off между количеством операций, locality, числом выделений backing arrays и тем, как доменная модель владеет данными, а не универсальное правило «SoA быстрее».

Есть и эффект между потоками. Два независимых счётчика могут находиться на одной cache line; при записи из разных CPU ядрам приходится передавать владение строкой cache, хотя data race нет. Padding может уменьшить false sharing, но увеличит footprint и нагрузку на cache. Добавляйте его только после профиля и проверки конкретной архитектуры.

В Go 1.27 компилятор вызывает специализированные allocator routines для некоторых малых выделений до 80 байт. Release notes сообщают о снижении стоимости отдельных операций до 30% и примерно 1% для allocation-heavy программ, но подчёркивают зависимость от workload. Это ещё одна причина не переносить benchmark цифры на другой сервис или релиз.

## Пример

~~~go
package main

import (
	"fmt"
	"unsafe"
)

type Scattered struct {
	first  byte
	middle uint64
	last   byte
}

type Compact struct {
	middle uint64
	first  byte
	last   byte
}

func main() {
	fmt.Println("Scattered bytes:", unsafe.Sizeof(Scattered{}))
	fmt.Println("Compact bytes:", unsafe.Sizeof(Compact{}))

	values := make([]byte, 64)
	fmt.Println("slice header bytes:", unsafe.Sizeof(values), "length:", len(values))
}
~~~

На распространённой 64-битной архитектуре первый тип занимает 24 байта, второй — 16; точный результат относится к текущей архитектуре, его и показывает <code>unsafe.Sizeof</code>. Размер заголовка среза не включает выделенные 64 байта backing array. Этот пример объясняет layout, но ещё не доказывает, что переупорядочивание ускорило запрос.

## Ошибки и ограничения

- Не называйте число вызовов <code>new</code> числом heap allocations. Посмотрите escape diagnostics и измерьте итоговую сборку.
- Не оптимизируйте размер без учёта alignment, pointer density и того, какие поля код читает вместе.
- Не добавляйте padding для «устранения гонки»: false sharing влияет на скорость согласования cache, а не на корректность синхронизации.
- Не доверяйте одному короткому запуску benchmark. Сравнивайте один и тот же Go, GOARCH, вход и профиль; фиксируйте разброс, аллокации и живую память отдельно.
- Heap profiles содержат выборочные данные: <code>alloc_space</code> полезен для потока выделений, <code>inuse_space</code> — для остающихся достижимыми объектов. Ноль в одном срезе не доказывает нулевые затраты за весь процесс.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Почему Scattered может занимать больше байтов, чем Compact?</summary>

Поле uint64 требует выравнивания, поэтому между ним и соседними байтами появляется padding. Перенос крупных полей ближе друг к другу может убрать часть промежутков, но результат зависит от ABI и архитектуры. Senior follow-up: какие публичные source-compatibility последствия даст перестановка полей структуры?

</details>

<details>
<summary>Почему числовой срез обычно требует меньше tracing-работы, чем срез указателей на объекты?</summary>

Его элементы не содержат ссылок, по которым нужно продолжать обход графа объектов. Срез указателей даёт GC дополнительные переходы и потенциально разрозненные объекты. Senior follow-up: как это соотносится с locality доступа и структурой данных в реальном hot path?

</details>

<details>
<summary>Когда структура из срезов может проиграть массиву структур?</summary>

Если типичная операция читает все поля записи, раздельные срезы требуют нескольких потоков данных и усложняют совместное расширение, синхронизацию индексов и владение. Senior follow-up: как организовать benchmark так, чтобы он отражал долю выборочных и полных проходов приложения?

</details>
