# Время, дедлайны и таймеры

## Коротко

`time.Time` хранит момент времени, `time.Duration` — длительность. Для измерения прошедшего времени используйте `time.Since` или разность значений `Time`, сохраняя монотонную часть; для расписаний, хранения и обмена данными — явно работайте с часовым поясом и календарными правилами. Таймеры и тикеры сигнализируют о времени, но не гарантируют точное исполнение в момент срабатывания.

## Как работает

`time.Now` обычно возвращает значение с wall-clock моментом и скрытой монотонной отметкой. Когда обе сравниваемые величины сохраняют эту отметку, сравнение и вычитание могут опираться на монотонные часы, не зависящие от коррекции системного времени. Сериализация, `Unix`, `UTC`, `Round` и многие операции копирования могут удалить монотонную часть. Поэтому вычисляйте latency до сериализации и не сравнивайте длительность с пользовательским временем из базы как с надёжным источником монотонности.

У момента есть зона отображения. `time.Parse` без зоны трактует значение в UTC, а `time.ParseInLocation` использует заданную IANA-зону для локальной даты без offset. Хранение абсолютного момента удобно в UTC; повторяющееся расписание вроде «каждый день в 09:00 в Париже» требует зоны и календарной логики, а не прибавления 24 часов к предыдущему моменту. Переход на летнее время создаёт локальные часы, которых нет, и часы, встречающиеся дважды; `time.Date` не обещает выбрать одну конкретную интерпретацию во всех таких неоднозначных случаях. Бизнес-правило должно назвать предпочтение и проверять результат.

`time.Timer` отправляет сигнал после истечения длительности, но горутина-получатель может проснуться позже из-за планирования. В Go 1.23 каналы таймеров и тикеров стали синхронными, что устраняет получение устаревшего сигнала после `Stop` или `Reset`. С той же версии сборщик мусора может освобождать недостижимые активные таймеры и тикеры, поэтому немедленно вызывать `Stop` для одной лишь сборки мусора больше не требуется.

В Go 1.23–1.26 новое поведение зависело от версии в `go.mod`: при `go 1.23+` каналы становились синхронными, а более старые версии сохраняли прежний режим. Настройка `asynctimerchan=1` могла вернуть буферизированные каналы. В Go 1.27 настройка удалена, и каналы синхронны при любой строке `go`. Поэтому удалите старое значение из `godebug` в `go.mod` и `//go:debug` в файле пакета `main`: инструментальная цепочка отклонит программу до сборки. `GODEBUG=asynctimerchan=1` в окружении также не возвращает старый режим и вызывает fatal error при запуске, включая саму команду `go`. Значение `=0` в директивах допустимо, но ничего не меняет.

Для одноразовой задержки создавайте `Timer` и выбирайте между его каналом и `ctx.Done()`. Для повторяющегося сигнала `Ticker` нужно остановить, когда владелец больше не читает канал; тикер может пропускать тики при медленном получателе, а не создавать бесконечную очередь событий. Не используйте `time.Sleep` как синхронизацию теста: ожидание по времени не доказывает, что другая горутина достигла нужного состояния.

## Пример

Эта функция ждёт задержку либо завершение контекста. `Stop` здесь выражает прекращение интереса к таймеру при раннем выходе; современный runtime также может собрать недостижимый таймер:

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func wait(ctx context.Context, d time.Duration) error {
	timer := time.NewTimer(d)
	defer timer.Stop()

	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-timer.C:
		return nil
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()
	if err := wait(ctx, 10*time.Millisecond); err != nil {
		fmt.Println("wait:", err)
		return
	}
	fmt.Println("elapsed")
}
```

Если deadline контекста и таймер становятся готовыми одновременно, `select` не обещает приоритет контекста. Здесь длительности выбраны так, чтобы обычный запуск завершил таймер раньше дедлайна, но точный момент всё равно зависит от планирования. Для проверки производственного сценария утверждайте бизнес-результат и границы допуска, а для синхронизации горутин используйте канал, mutex или другой протокол.

## Ошибки и ограничения

- Не сохраняйте монотонную часть `Time` как будто она переживёт JSON, БД или межпроцессную передачу.
- Не моделируйте ежедневное местное расписание постоянным `24*time.Hour` через переходы зоны.
- Не ожидайте точного тайминга от `Timer` или `Ticker`; системная загрузка задерживает обработчик.
- Не предполагайте приоритет одной готовой ветки `select` над другой.
- Не используйте `Sleep` для гарантирования, что параллельная операция завершилась.

Для диагностики выводите время в RFC3339 с offset и отдельно измеряйте задержку монотонной разностью. Для DST-пограничных случаев тестируйте известную именованную зону и явно проверяйте желаемое правило обработки пропущенного или повторного локального часа.
