# HTTP-клиент и сервер

## Коротко

`net/http` задаёт жизненный цикл запроса, ответа и соединения. Повторно используйте `http.Client` и его `Transport`, ограничивайте время через контекст запроса или `Client.Timeout`, проверяйте статус отдельно от ошибки транспорта и закрывайте каждый `Response.Body`. На сервере задавайте сроки чтения и записи, а при остановке прекращайте приём новых соединений и дожидайтесь активных обработчиков в рамках конечного контекста.

## Как работает

`Client.Do` возвращает ошибку для проблем запроса и транспорта, но HTTP-статус вроде `404` сам по себе не является ошибкой Go. После успешного `Do` вызывающий владеет телом ответа и должен закрыть его, даже если статус неожиданный или тело не нужно. Для повторного использования HTTP/1 соединения обычно требуется прочитать тело до конца и закрыть его. В Go 1.27 закрытие `Response.Body` автоматически дочитывает небольшое количество непрочитанного содержимого; полагаться на внутренний предел дочитывания не следует. Для больших или бесконечных тел задайте лимит и принимайте решение о повторном использовании соединения исходя из своей нагрузки.

Клиент безопасен для конкурентного использования, но `Transport` хранит пул соединений, поэтому создавайте клиент один раз для конфигурации, а не на каждый запрос. `Client.Timeout` ограничивает подключение, редиректы и чтение тела ответа; нулевое значение означает отсутствие предела. Контекст запроса удобнее, когда дедлайн зависит от конкретной операции: он продолжает действовать при чтении тела после `Do`. Задавайте сетевые тайм-ауты сервера и лимит тела запроса отдельно: медленный клиент иначе может удерживать горутину и соединение слишком долго.

У `http.Server` есть `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout` и ограничения заголовков. Выбор зависит от протокола: общий `ReadTimeout` может мешать длительной загрузке тела, а слишком короткий `WriteTimeout` — долгим ответам. `Server.Shutdown(ctx)` закрывает слушатели, закрывает простаивающие соединения и ждёт активные; после истечения контекста вызов возвращает его ошибку. Метод не закрывает и не ждёт hijacked-соединения, например некоторые WebSocket-сессии, поэтому их жизненным циклом владеет приложение.

Пишите обработчики через `http.Handler` и проверяйте их с `httptest.NewServer` или `httptest.NewRecorder`, не открывая внешний адрес. Сервер и тестовый клиент можно закрыть через `defer`. Это сохраняет реальные правила маршрутизации и сериализации HTTP, но не проверяет DNS, TLS инфраструктуру, балансировщик и поведение реальной сети.

## Пример

Пример выполняется только на локальном тестовом сервере. Контекст охватывает запрос и чтение тела, а ответ закрывается при любом исходе проверки статуса:

```go
package main

import (
	"context"
	"fmt"
	"io"
	"log"
	"net/http"
	"net/http/httptest"
	"time"
)

func main() {
	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "text/plain")
		_, _ = io.WriteString(w, "ready")
	}))
	defer server.Close()

	ctx, cancel := context.WithTimeout(context.Background(), time.Second)
	defer cancel()
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, server.URL, nil)
	if err != nil {
		log.Fatal(err)
	}
	resp, err := server.Client().Do(req)
	if err != nil {
		log.Fatal(err)
	}
	defer resp.Body.Close()
	body, err := io.ReadAll(io.LimitReader(resp.Body, 1<<20))
	if err != nil {
		log.Fatal(err)
	}
	if resp.StatusCode < 200 || resp.StatusCode >= 300 {
		log.Fatalf("unexpected status %s: %s", resp.Status, body)
	}
	fmt.Println(resp.StatusCode, string(body))
}
```

`LimitReader` защищает память, но не подтверждает, что ответ целиком помещался в один мегабайт. Если API требует целостность документа, прочитайте максимум `limit+1` и явно отклоните переполнение. Производственный клиент дополнительно задаёт проверяемую политику редиректов, TLS, заголовков и повторов; повтор POST без идемпотентного контракта может выполнить действие дважды.

## Ошибки и ограничения

- Не проверяйте только `err == nil`: успешный обмен может вернуть `4xx` или `5xx`.
- Не забывайте закрыть тело ответа на ветках ошибок статуса и декодирования.
- Не делайте неограниченный `io.ReadAll` для тела, размер которого контролирует удалённая сторона.
- Не создавайте новый клиент на каждый запрос: это дробит пул и усложняет управление соединениями.
- Не используйте один короткий timeout сервера для всех типов запросов без оценки потоковых и долгих ответов.
- Не считайте `Shutdown` полной остановкой приложения: фоновые задачи и hijacked-соединения требуют отдельного сигнала и ожидания.

Для диагностики журналируйте метод, выбранный маршрут, статус, длительность и класс ошибки, но не токены и полное тело. В тесте различайте ошибку `Do`, HTTP-статус, ошибку чтения тела и отмену контекста: это разные этапы одного жизненного цикла.

## Практика

Реализуйте `GET /health` и клиентскую функцию, которая возвращает тело только для `2xx`, ограничивает его размер и закрывает ответ. Проверьте через `httptest` успех, `503`, слишком большое тело и отменённый контекст. Отдельно опишите порядок сигнала серверу, вызова `Shutdown` и закрытия фоновых ресурсов.

Упражнения [«Получение URL»](/practice/url-fetcher) и [«HTTP middleware»](/practice/http-middleware) связывают владение ответом с отменой и порядком обработчиков.
