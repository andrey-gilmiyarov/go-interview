# Потоки ввода-вывода и файлы

## Коротко

`io.Reader` и `io.Writer` позволяют связывать файлы, буферы, сетевые соединения и собственные источники данных одним контрактом. `Read` может вернуть одновременно `n > 0` и ошибку: сначала обработайте полученные байты, затем решайте, завершилось ли чтение или произошёл сбой. Владение ресурсом определяется API, который его открыл или явно передал вызывающему коду; каждый владелец должен закрыть ресурс.

## Как работает

`Reader.Read(p)` записывает не более `len(p)` байт и возвращает их количество. Он не обещает заполнить весь буфер за один вызов. Если данные доступны, реализация обычно возвращает то, что есть, вместо ожидания полного `p`. При конце потока допустимы как `(n > 0, io.EOF)`, так и `(n > 0, nil)`, после которых следующий вызов завершится EOF. Поэтому цикл ручного копирования обязан записать `p[:n]` прежде, чем обработает `err`; `io.Copy` и `io.ReadAll` уже корректно реализуют этот протокол.

`io.EOF` означает нормальный конец потока, а не повреждение чтения: функции `io.Copy` не возвращают EOF как ошибку. `io.ErrUnexpectedEOF` полезен, когда вызывающий ожидал точное число байтов, например через `io.ReadFull`. Если одновременно получены байты и другая ошибка, нельзя отбрасывать уже прочитанные данные. Реализации `Reader` не должны сохранять `p` после возврата: его память принадлежит вызывающей стороне и может быть переиспользована.

`os.Open` возвращает `*os.File`, который нужно закрыть. Обычно ответственность за `Close` остаётся у функции, открывшей файл; функция, получившая чужой `io.Reader`, не должна закрывать его без явного контракта передачи владения. Закрытие важно даже после EOF: оно освобождает файловый дескриптор и может сообщить ошибку записи, буферизации или завершения операции. Для потоковой записи создайте файл, проверьте каждую ошибку `Write`, затем проверьте `Close`; `defer f.Close()` удобно для уборки, но само по себе теряет ошибку закрытия.

Обёртки вроде `bufio.Reader`, `io.LimitReader` и `io.TeeReader` меняют способ чтения, не меняя исходное владение нижележащим файлом. Ограничитель полезен для недоверенного или потенциально огромного входа, но достижение лимита не доказывает, что весь документ был прочитан: отдельно проверьте наличие хвоста, если контракт требует полный ввод. При копировании `io.Copy` может использовать оптимизированные методы `WriterTo` или `ReaderFrom`, так что ручной цикл не гарантирует большей скорости и легче ошибается с частичными записями.

## Пример

Здесь владение `io.ReadCloser` явно передаётся функции. Она сохраняет и ошибку чтения, и ошибку закрытия, а частичную полезную нагрузку не возвращает при неуспехе:

```go
package main

import (
	"errors"
	"fmt"
	"io"
	"strings"
)

func readAndClose(r io.ReadCloser) ([]byte, error) {
	data, readErr := io.ReadAll(r)
	closeErr := r.Close()
	if err := errors.Join(readErr, closeErr); err != nil {
		return nil, err
	}
	return data, nil
}

func main() {
	data, err := readAndClose(io.NopCloser(strings.NewReader("report")))
	if err != nil {
		fmt.Println("read:", err)
		return
	}
	fmt.Println(string(data))
}
```

`io.ReadAll` продолжает читать до EOF и не требует, чтобы один `Read` заполнил весь буфер. `errors.Join` сохраняет обе причины для `errors.Is`/`errors.As`; если одной из ошибок нет, она не меняет результат. В реальном API решите отдельно, можно ли вернуть уже полученные данные вместе с ошибкой.

## Ошибки и ограничения

- Не считайте `(0, nil)` концом потока; это может означать, что сейчас не было прогресса. Повторяющийся такой ответ нарушает рекомендации `Reader` и способен вызвать бесконечный цикл.
- Не игнорируйте `n`, когда тот же вызов вернул ошибку: полезные байты идут раньше обработки ошибки.
- Не закрывайте ресурс, чей жизненный цикл принадлежит вызывающему коду, если контракт не передаёт вам владение.
- Не ограничивайте только размер буфера и не делайте вывод, что источник не содержит дополнительных данных.
- Не теряйте ошибку `Close` при записи важных файлов: успешный `Write` не гарантирует успешную финализацию.

Для диагностики проверьте, кто вызывает `Open`, где ресурс закрывается, сколько байтов было принято и какая ошибка вернулась первой. При проблемах с коротким вводом сравните `io.ReadFull` с `io.ReadAll`, чтобы определить, нужен ли контракт «до EOF» или «ровно N байт».
