# JSON в стандартной библиотеке

## Коротко

Для существующих контрактов Go 1.27 сохраняет API и поведение `encoding/json` v1: нулевые и пустые срезы различаются, неизвестные поля по умолчанию игнорируются, повторные имена объекта принимаются, числа в `any` становятся `float64`. Go 1.27 также добавляет `encoding/json/v2` и `encoding/json/jsontext` с явными параметрами и более строгими правилами. Не переносите ожидания v2 на v1 и выбирайте пакет по контракту wire-формата.

## Как работает

`json.Marshal` преобразует значения в JSON-байты, а `json.Unmarshal` сопоставляет объект с экспортируемыми полями или пользовательскими методами `MarshalJSON`/`UnmarshalJSON`. В v1 карта получает ключи, отсортированные при кодировании, но это свойство сериализатора, а не порядка Go-карты. `nil`-срез кодируется как `null`, а `make([]T, 0)` — как `[]`; это различие может менять API-контракт и хранится в упражнении [про nil и пустые значения](/practice/nil-empty-json).

По умолчанию `Unmarshal` игнорирует неизвестные поля. `Decoder.DisallowUnknownFields` полезен для закрытых конфигураций, но не решает все вопросы безопасности: v1 принимает повторные имена объекта, использует нечувствительное к регистру совпадение имён как fallback и допускает некорректные UTF-8 последовательности с заменой. Один вызов `Decoder.Decode` читает одно значение; чтобы принимать ровно один документ из потока, после первого значения вызовите `Decode` ещё раз и потребуйте `io.EOF`, иначе соседний JSON документ останется незамеченным.

Числа в целочисленные поля проверяются по диапазону типа. При декодировании в `any` v1 использует `float64`, где большие целые могут потерять точность; `Decoder.UseNumber` сохраняет исходное числовое написание как `json.Number`, после чего код должен явно проверить диапазон и формат. JSON `null` сбрасывает указатели, интерфейсы, карты и срезы в `nil`; для большинства скалярных полей `null` не меняет значение. Поэтому декодирование поверх уже заполненной структуры может сохранить старое поле вместо явного нуля.

В Go 1.27 `encoding/json/v2` предоставляет отдельный API, а `jsontext` — низкоуровневый синтаксический поток токенов и значений. В отличие от v1, v2 по умолчанию отвергает некорректный UTF-8 и повторяющиеся имена объекта; параметры `Options` позволяют настраивать поведение. Сам пакет `encoding/json` реализован на основе v2, но сохраняет правила v1, хотя текст некоторых сообщений об ошибках может отличаться. Переход на v2 — изменение семантики, а не простая замена импорта: зафиксируйте тестами null, имена, неизвестные поля, дубликаты и числа.

## Пример

Функция принимает одну конфигурацию v1, запрещает неизвестные поля и не теряет точность большого числа. Второй `Decode` обнаруживает дополнительные JSON-значения после первого объекта:

```go
package main

import (
	"encoding/json"
	"errors"
	"fmt"
	"io"
	"strings"
)

type Config struct {
	Name  string      `json:"name"`
	Limit json.Number `json:"limit"`
}

func decodeConfig(r io.Reader) (Config, error) {
	dec := json.NewDecoder(r)
	dec.DisallowUnknownFields()

	var cfg Config
	if err := dec.Decode(&cfg); err != nil {
		return Config{}, err
	}
	var extra any
	if err := dec.Decode(&extra); err != io.EOF {
		if err == nil {
			return Config{}, errors.New("multiple JSON values")
		}
		return Config{}, fmt.Errorf("trailing data: %w", err)
	}
	return cfg, nil
}

func main() {
	cfg, err := decodeConfig(strings.NewReader(`{"name":"batch","limit":9007199254740993}`))
	if err != nil {
		fmt.Println("invalid config:", err)
		return
	}
	fmt.Println(cfg.Name, cfg.Limit.String())
}
```

`DisallowUnknownFields` отклоняет опечатку вроде `limti`, а поле типа `json.Number` сохраняет десятичную запись числа для последующей явной проверки и преобразования. `UseNumber` нужен в другом случае — когда число декодируется в `any`, как описано выше. Пример по-прежнему наследует правила v1 для повторяющихся имён и некорректного UTF-8. Если данные приходят из недоверенного источника и такое поведение неприемлемо, проверьте строгие настройки v2 или добавьте проверку, которая задаёт нужную политику.

## Ошибки и ограничения

- Не полагайтесь на default ignore-unknown для критичной конфигурации: новое поле может быть просто опечаткой.
- Не считайте `DisallowUnknownFields` защитой от дублирующихся ключей или нескольких корневых значений.
- Не декодируйте деньги и большие идентификаторы в `float64`; сохраняйте десятичную форму и проверяйте пределы.
- Не меняйте `encoding/json` на `encoding/json/v2`, пока тесты не зафиксировали wire-совместимость для `null`, имен, полей и ошибок.
- Не используйте текст ошибки как стабильный машинный API; проверяйте типы и обёрнутые ошибки, а поля ошибок форматируйте для диагностики.

При разборе недоверенного ввода ограничьте объём до декодирования, проверьте единственный корневой документ и конкретные бизнес-инварианты после синтаксической проверки. Синтаксически допустимое JSON всё ещё может нарушать лимиты домена, например отрицательное количество или неподдерживаемую версию схемы.

## Практика

Составьте тесты для отсутствующего поля, неизвестного поля, повторяющегося имени, двух последовательных документов, больших целых и `null` в указателе, карте и срезе. Повторите контрактные кейсы отдельно на v1 и v2, явно указав ожидаемое расхождение, а не автоматически исправляя формат.
