# Работа с базой через database/sql

## Коротко

`database/sql` задаёт общий API поверх драйвера, но сам не включает драйвер и не описывает SQL-диалект. `*sql.DB` — конкурентно-безопасный пул соединений, а не одна готовая сессия. Ограничивайте операции через context, закрывайте `Rows`, проверяйте `Rows.Err`, а связанные изменения выполняйте в `Tx` и завершайте явным `Commit` или `Rollback`.

## Как работает

`sql.Open` настраивает handle и часто не устанавливает соединение немедленно; `PingContext` используется, когда приложению нужно проверить доступность при старте. Конкретный driver отвечает за подключение, преобразование типов, поддержку отмены и фактическую семантику SQL. Поскольку драйвер не входит в этот пример, тесты и сервисный код могут принимать готовый `*sql.DB`, а состав приложения отдельно регистрирует утверждённую реализацию.

Pool открывает, повторно использует и освобождает соединения по мере нагрузки. `SetMaxOpenConns` ограничивает число одновременных соединений и фактически становится точкой backpressure: запрос может ждать слот, а вложенный запрос к тому же пулу внутри транзакции способен навсегда ждать свободное соединение. Следите за `DB.Stats`, временем ожидания и числом открытых соединений. Не держите `Rows` или транзакцию дольше, чем нужно: они могут удерживать соединение из ограниченного пула.

`QueryContext` возвращает `Rows`. Цикл `Next` продвигает курсор, `Scan` копирует значения в подходящие типы, а ошибка во время итерации становится доступна через `Rows.Err`. `Rows` обычно закрывается в конце набора, но явный `Close` нужен при раннем выходе и должен принадлежать той функции, которая открыла набор. `QueryRowContext` откладывает ошибку выполнения до `Scan`, поэтому проверяйте именно результат `Scan`. Передавайте аргументы отдельно от текста запроса; параметризация защищает значения, но не имена таблиц или направление сортировки, которые должны выбираться из allowlist.

`BeginTx(ctx, opts)` привязывает `Tx` к одному соединению. Все связанные команды обязаны идти через `tx`, а не через `db`, иначе они могут выполняться вне транзакции. После начала есть один владелец решения о фиксации: завершите `Commit` и обработайте его ошибку либо вызовите `Rollback` при любом раннем выходе. Запрошенный уровень изоляции может быть не поддержан драйвером и привести к ошибке; не считайте `ReadCommitted` или `Serializable` одинаковыми гарантиями во всех базах. Отмена context для транзакции инициирует rollback и должна быть частью контракта запроса.

## Пример

Функция не требует конкретного драйвера. Она владеет `Rows`, закрывает его при любом пути выхода и сохраняет ошибку закрытия вместе с ошибкой сканирования или итерации:

```go
package repository

import (
	"context"
	"database/sql"
	"errors"
)

func listNames(ctx context.Context, db *sql.DB) (_ []string, retErr error) {
	rows, err := db.QueryContext(ctx, "SELECT name FROM users ORDER BY name")
	if err != nil {
		return nil, err
	}
	defer func() {
		retErr = errors.Join(retErr, rows.Close())
	}()

	var names []string
	for rows.Next() {
		var name string
		if err := rows.Scan(&name); err != nil {
			return nil, err
		}
		names = append(names, name)
	}
	if err := rows.Err(); err != nil {
		return nil, err
	}
	return names, nil
}
```

Успешное завершение `Next`-цикла не заменяет проверку `Rows.Err`: ошибка сети или драйвера могла прервать чтение. В этой простой функции SQL не получает входные значения. Если запрос принимает фильтр, используйте `WHERE name = ?` или соответствующий placeholder выбранного драйвера и передайте значение отдельным аргументом; знак placeholder зависит от диалекта.

## Ошибки и ограничения

- Не считайте `sql.Open` доказательством доступности базы; применяйте ограниченный `PingContext`, если это требуется при старте.
- Не забывайте проверить `Rows.Err` после обхода и закрыть `Rows` при раннем возврате.
- Не вызывайте связанные команды через `db`, уже начав транзакцию через `tx`.
- Не интерполируйте пользовательские значения в SQL-строку; параметризация не распространяется на динамические имена таблиц и колонки.
- Не задавайте максимальный пул без оценки конкурентности: ожидание соединения может распространить задержку дальше по сервису.
- Не выводите одинаковую изоляцию или типы результата для всех драйверов и серверов.

Для диагностики сравните latency запроса с ожиданием пула в `DB.Stats`, проверьте context deadline и журналы драйвера. Ошибки `QueryContext`, `Scan`, `Rows.Err`, `Commit` и `Rollback` относятся к разным этапам и должны сохранять исходную причину через `%w` или `errors.Join`.

</details>

<summary>Почему операции внутри транзакции должны использовать `tx`, а не `db`?</summary>

Транзакция закреплена за одним соединением, а вызов через пул может использовать другую сессию и не участвовать в фиксации. Senior follow-up: какие гарантии уровня изоляции реально подтверждены вашим драйвером и базой?
</details>

## Практика

Спроектируйте репозиторий с параметризованным поиском, итерацией строк и атомарным обновлением двух таблиц. Для каждого ресурса отметьте владельца, путь ошибки, отмену и момент освобождения соединения. Напишите тест через интерфейс репозитория или выбранный драйвер отдельно от примера стандартной библиотеки.
