# Функциональные options

## Коротко

Функциональная option — функция, которая меняет конфигурацию объекта при его создании. Такой API позволяет добавлять необязательные настройки, не превращая конструктор в длинный список позиционных параметров. Паттерн полезен, когда есть устойчивые defaults, несколько независимых возможностей и вызывающему коду важно видеть каждую включённую настройку по имени.

Это соглашение поверх обычных типов и функций Go, а не специальная языковая конструкция. Для одной-двух необязательных величин часто яснее обычный аргумент, отдельный конструктор или структура конфигурации. Сравните контракт публичного API в статье [«Пакеты и устойчивые API»](../api/packages-api.md): удобство вызова не должно скрывать правила валидации, повторов и приоритета значений.

## Как работает

Конструктор создаёт внутреннюю конфигурацию с документированными значениями по умолчанию, затем применяет функции-опции по порядку и проверяет итоговые инварианты. Опция обычно захватывает своё значение при создании и меняет только соответствующее поле. После проверки конструктор переносит значения в объект, который не меняет конфигурацию неожиданно при каждом вызове.

Есть несколько допустимых API-форм. Часто экспортируют функции вида `WithTimeout(d)` и непрозрачный тип `Option`; клиент собирает аргументы, но не редактирует внутреннюю конфигурацию напрямую. Если ошибка может быть локально обнаружена при применении опции, тип может возвращать ошибку. Если важна совместимость между несколькими полями, проще применить все настройки и проверить общие инварианты один раз в конструкторе.

Повтор одной и той же опции требует явного правила. «Последняя побеждает» детерминированно и естественно при последовательном применении; отклонение дублей тоже возможно, если повтор означает ошибку конфигурации. Опции лучше делать чистыми присваиваниями: открытие соединения, запуск горутины или запись в глобальный реестр внутри функции-опции превращает сборку конфигурации в частичное выполнение приложения и усложняет откат.

Функциональные options расширяемы, но не бесплатны. Они занимают имена пакета, требуют отдельного кода для каждого поля и могут сделать простой объект труднее читать. Если набор настроек хорошо представлен структурой с осмысленным нулевым значением, конфигурационная структура проще; если настройка меняет поведение или нужна композиция, функции могут быть нагляднее. Это выбор формы публичного API, а не повод поддерживать две формы без потребности.

## Пример

Внутренняя структура сохраняет defaults. Опции устанавливают поля, а конструктор валидирует итог: отрицательное число повторов запрещено, ноль является явным значением и отличается от отсутствующей опции.

~~~go
package main

import (
	"errors"
	"fmt"
	"time"
)

type clientConfig struct {
	timeout time.Duration
	retries int
}

type Option func(*clientConfig)

type Client struct {
	timeout time.Duration
	retries int
}

func WithTimeout(timeout time.Duration) Option {
	return func(config *clientConfig) {
		config.timeout = timeout
	}
}

func WithRetries(retries int) Option {
	return func(config *clientConfig) {
		config.retries = retries
	}
}

func NewClient(options ...Option) (*Client, error) {
	config := clientConfig{timeout: 5 * time.Second, retries: 2}
	for _, option := range options {
		if option == nil {
			return nil, errors.New("nil option")
		}
		option(&config)
	}
	if config.timeout <= 0 {
		return nil, errors.New("timeout must be positive")
	}
	if config.retries < 0 {
		return nil, errors.New("retries must not be negative")
	}
	return &Client{timeout: config.timeout, retries: config.retries}, nil
}

func main() {
	client, err := NewClient(WithTimeout(2*time.Second), WithRetries(0))
	fmt.Println(client.timeout, client.retries, err)

	_, err = NewClient(WithTimeout(-time.Second))
	fmt.Println(err != nil)
}
~~~

Вывод — `2s 0 <nil>` и `true`. Если вызывающий передаст две опции `WithRetries`, вторая перезапишет первую. Такой эффект виден из кода цикла и должен быть описан в комментарии к API, а не оставлен случайным.

## Ошибки и ограничения

- Не используйте options для обязательных аргументов, которые должны быть видны в сигнатуре конструктора.
- Не делайте default нулевым «магическим» значением, если клиент должен уметь явно выбрать ноль. Представьте различие через отдельный флаг, pointer или функцию-опцию.
- Не валидируйте только отдельные присваивания, если корректность зависит от нескольких настроек. Проверяйте итоговую конфигурацию после применения всех опций.
- Не скрывайте порядок и политику дублей. Последняя опция, первая опция, конфликт или ошибка — разные контракты.
- Не выполняйте внешнюю работу при применении опции. Сборка конфигурации должна оставаться безопасной, предсказуемой и дешёвой.
- Не добавляйте функциональную форму лишь ради «расширяемости на будущее». Варианты конструктора и конфигурационная структура тоже могут быть совместимыми путями развития.

При проектировании проверьте типичные вызовы на чтение: defaults без параметров, только одна настройка, явный ноль и конфликтующие значения. Посмотрите также, можно ли будет добавить новую настройку, не меняя семантику старых вызовов.

<details>
<summary>Почему нельзя валидировать каждую настройку только внутри её функции?</summary>

Корректность часто зависит от итогового сочетания полей, которое видно лишь после применения всех опций. Senior follow-up: какие отношения между timeout, числом повторов и бюджетом запроса нужно проверять совместно?
</details>

<details>
<summary>Когда конфигурационная структура проще функциональных options?</summary>

Когда есть естественный набор полей, который вызывающий передаёт целиком, а значения и defaults не требуют композиции поведения. Senior follow-up: как указать, что нулевое значение является явным выбором, а не «не задано»?
</details>

## Практика

Спроектируйте конструктор сетевого клиента с defaults для timeout и максимального числа повторов. Документируйте допустимый ноль, порядок дублей, ошибки и неизменность уже созданного клиента. Сравните чтение трёх вызовов: без настроек, с одной опцией и с двумя конфликтующими опциями. Затем обоснуйте, почему структура конфигурации не проще или почему именно она лучше для этого набора полей.
