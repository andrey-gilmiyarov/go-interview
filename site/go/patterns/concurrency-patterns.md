## Коротко

Параллельный код полезен, когда задача состоит из независимых частей, а не просто потому, что данные проходят по каналам. `worker pool` задаёт предел активной работы; `pipeline` делит обработку на последовательные этапы; `fan-in` сводит несколько потоков к одному. Выбирайте форму по узкому месту и контракту результата: сколько работ допускается одновременно, важен ли исходный порядок, что происходит при ошибке и кто останавливает оставшиеся этапы.

Любой такой шаблон требует владельца запуска и завершения. Канал сам по себе не даёт права закрыть его: закрывает отправитель, который знает, что новых значений больше не будет. Контекст сообщает об отмене, но не прерывает функцию; после отмены нужно присоединиться к каждой запущенной горутине. Подробная модель владения находится в статьях [«Жизненный цикл горутины»](../concurrency/goroutine-lifecycle.md), [«Каналы»](../concurrency/channels.md) и [«Context и отмена»](../concurrency/context.md).

## Как работает

У `worker pool` есть очередь работ и фиксированное число исполнителей. Это ограничивает число одновременных операций, файловых дескрипторов и незавершённых запросов. Индекс задания позволяет собирать результаты в порядке входа, даже если исполнители закончили в другом порядке. Цена — дополнительная очередь и политика ожидания, когда она заполнена.

`Pipeline` отделяет производство, преобразование и потребление. Буфер канала — конечный запас работы: пока в нём есть место, отправитель может опередить получателя; после заполнения отправка создаёт backpressure. Большой буфер меняет допустимый объём очереди и задержку, но не устраняет перегрузку. Если потребитель завершился раньше, каждую потенциально блокирующую отправку и получение нужно разблокировать отменой. `Fan-in` объединяет результаты нескольких входов; он сохраняет порядок внутри отдельного входа, но не создаёт общего порядка между независимыми входами.

Закрытие выходного канала принадлежит той стадии, которая может доказать, что новых отправок не будет. Если отправителей несколько, один координатор сначала ждёт их завершения, а потом закрывает выход. Вход остаётся во владении вызывающей стороны. Нельзя закрывать его из этапа, которому передали только канал для чтения.

До реализации зафиксируйте семантику частичного результата. Например, API может вернуть упорядоченный результат только при успехе, либо сохранить независимые ошибки по каждому элементу. Для первого наблюдённого сбоя нужно отменить соседние операции, передать им контекст и дождаться их возврата. Если callback игнорирует контекст, ограничение на число workers не даёт гарантии конечного завершения. `errgroup` добавляет политику ошибок и join; это не замена явному контракту очереди или порядка — см. [`x/sync`](../concurrency/x-sync.md).

## Пример

Два исполнителя считают квадраты, а сборщик суммирует их, поэтому порядок завершения не влияет на ответ. Единственный производитель закрывает `jobs`, координатор закрывает `results` после завершения всех исполнителей, а главный поток дочитывает результат и присоединяется к производителю.

~~~go
package main

import (
	"fmt"
	"sync"
)

func main() {
	const workers = 2
	jobs := make(chan int)
	results := make(chan int)

	var workerGroup sync.WaitGroup
	workerGroup.Add(workers)
	for i := 0; i < workers; i++ {
		go func() {
			defer workerGroup.Done()
			for value := range jobs {
				results <- value * value
			}
		}()
	}

	producerDone := make(chan struct{})
	go func() {
		defer close(producerDone)
		defer close(jobs)
		for _, value := range []int{1, 2, 3, 4} {
			jobs <- value
		}
	}()

	workersJoined := make(chan struct{})
	go func() {
		workerGroup.Wait()
		close(results)
		close(workersJoined)
	}()

	total := 0
	for value := range results {
		total += value
	}
	<-producerDone
	<-workersJoined
	fmt.Println(total)
}
~~~

Вывод — `30`. В рабочем этапe отправки и получения обычно оборачивают в `select` с `ctx.Done()`; потребитель, который перестал читать, должен отменить общий контекст. Даже когда отправка и отмена готовы одновременно, `select` не гарантирует приоритет отмены. Для полного контракта с упорядоченными значениями есть упражнения [«Worker pool с отменой»](/practice/worker-pool), [«Отменяемый pipeline»](/practice/pipeline) и [«Объединение каналов fan-in»](/practice/fan-in).

## Ошибки и ограничения

- Не увеличивайте буфер, чтобы скрыть медленного потребителя: очередь всё равно конечна, а память и задержка растут.
- Не закрывайте канал, пока другая горутина ещё может отправить в него; такая отправка вызывает `panic`.
- Не рассчитывайте на случайный порядок `fan-in` как на стабильный API. Сортируйте итог либо передавайте ключ и упорядочивайте отдельно.
- Не запускайте горутину на каждый элемент, если вход не ограничен. Лимит workers ограничивает активную обработку, а не обязательно число ожидающих задач.
- Не называйте отмену завершением. Нужен отдельный join, а callbacks должны сотрудничать с контекстом.
- Не используйте конкурентность для крошечной последовательной операции без измеренной причины: координация добавляет аллокации, ветви ошибок и точки блокировки.

## Самопроверка

<details>
<summary>Кто закрывает выход fan-in, если его заполняют несколько читателей?</summary>

Координатор после join всех отправителей. Отдельный читатель не может безопасно решить, что остальные уже закончили. Senior follow-up: как сообщить читателям, что потребитель досрочно перестал принимать результаты?
</details>

<details>
<summary>Почему большой буфер не заменяет отмену?</summary>

Он лишь позволяет временно отправить больше значений без получателя. После заполнения блокировка вернётся, а потерянные ресурсы продолжат удерживать горутины. Senior follow-up: какой предел очереди соответствует допустимой памяти и задержке именно вашего сервиса?
</details>

<details>
<summary>Гарантирует ли worker pool порядок результатов?</summary>

Нет. Он ограничивает число одновременно работающих callbacks. Индекс или отдельный упорядоченный сборщик должен сохранить порядок, если это часть контракта. Senior follow-up: обязателен ли порядок для результата, который можно представить как независимые ошибки по ключам?
</details>

## Практика

Сопоставьте три контракта упражнений: [worker pool](/practice/worker-pool) сохраняет входной порядок, [pipeline](/practice/pipeline) передаёт поток и закрывает свой выход, а [fan-in](/practice/fan-in) сохраняет порядок каждого входа при неопределённом общем порядке. Для каждого запишите, кто создаёт и закрывает каналы, какой этап отменяет контекст и кто ждёт горутины. Затем заставьте потребителя прочитать только первый результат и проверьте, какие отправители иначе зависли бы.
