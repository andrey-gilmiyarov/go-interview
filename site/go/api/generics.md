# Обобщённые функции, типы и методы

## Коротко

Параметры типа описывают семейство функций и типов, а `constraint` ограничивает допустимые аргументы и операции над ними. Используйте generics для алгоритма, который действительно применим к разным типам; не вводите type parameter, если конкретная функция яснее выражает договор.

`Go 1.27.1` также разрешает собственные параметры типа у методов конкретного типа. Методы интерфейсов по-прежнему не могут объявлять собственные параметры типа, и generic-метод не реализует метод интерфейса. Эта новая возможность дополняет общую модель generics, но не заменяет её.

## Как работает

`Constraint` — интерфейс, задающий `type set`. Например, `constraint` с terms `~int | ~int64` объединяет все типы, чьим `underlying type` является `int` или `int64`. Оператор ~ включает именованные типы с таким базовым представлением, например `AccountID` `int`. Объединение `|` допускает несколько непересекающихся групп типов, а код generic-функции вправе использовать только операции, допустимые для всех элементов набора.

Constraint может одновременно требовать методы и типы: `interface{ ~int | ~int64; String() string }` задаёт пересечение множества целых подлежащих типов и типов с методом `String`. Параметр с таким ограничением может вызвать `String()` и участвовать в сложении. Basic interface, состоящий из методов, можно использовать как обычный интерфейсный тип. Интерфейсы с type terms, `comparable` или их сочетанием являются non-basic constraints: их нельзя хранить в переменной или поле как обычное динамическое значение, но можно использовать для ограничения параметра типа.

`any` не даёт операций вроде `==`, сложения или порядка: он лишь допускает любой типовой аргумент. `comparable` разрешает сравнение, но требует внимания к специальному правилу, появившемуся в `Go 1.20`. Сам интерфейсный тип `any` может удовлетворять `comparable` как аргумент типа, потому что значения интерфейсов допускают `==`. Однако конкретное значение внутри `any` может быть срезом: сравнение двух таких динамических значений одного несравнимого типа во время работы вызовет `panic`. Поэтому `comparable` нельзя трактовать как гарантию безусловной безопасности для произвольного payload интерфейса. Параметр другого типа, ограниченный только `any`, сам по себе `comparable` не удовлетворяет.

Для любого параметра `T` можно получить нулевое значение через `var zero T`. Нельзя вернуть `nil` из функции с произвольным результатом `T`: `T` может оказаться `int`, структурой или другим нениллабельным типом. Вывод типов берёт информацию из аргументов вызова и контекста типизированного значения, но не угадывает аргумент, который нигде не задан. Например, `Zero[T]()` требует явного `Zero[int]()`, поскольку `T` встречается только в результате. В Go 1.27 вывод обобщённых функций расширен на дополнительные контексты с ожидаемым типом; при нехватке информации укажите аргумент явно.

В Go 1.27 метод конкретного типа может добавить собственный параметр после имени метода, например `Map[R any]`, при этом receiver-параметры самого типа уже доступны телу. Это удобно для организации цепочек операций вокруг `Box[T]`. Интерфейс может объявлять собственные параметры на уровне типа, а его методы могут их использовать, но метод не может добавить `R` на каждом отдельном вызове. Если нужен динамический выбор реализации, спроектируйте интерфейс с фиксированной сигнатурой или примените generic-функцию к интерфейсу.

Параметры и constraints публичной функции являются частью совместимого API: ужесточение `constraint` может запретить ранее допустимые типы, а слишком слабый `constraint` не позволит выразить нужные операции. Выбирайте минимальный достаточный набор требований и оставляйте пример использования рядом с экспортируемым API.

## Пример

~~~go
package main

import "fmt"

type Integer interface {
	~int | ~int64
}

func Add[T Integer](left, right T) T {
	return left + right
}

type Describable interface {
	~int | ~int64
	String() string
}

type AccountID int

func (id AccountID) String() string {
	return fmt.Sprintf("account-%d", id)
}

func Describe[T Describable](value T) string {
	return value.String()
}

type Box[E any] struct {
	value E
}

func (b Box[E]) Map[R any](convert func(E) R) Box[R] {
	return Box[R]{value: convert(b.value)}
}

func Zero[T any]() T {
	var zero T
	return zero
}

func main() {
	sum := Add(AccountID(20), AccountID(22))
	box := Box[int]{value: 21}
	converted := box.Map(func(n int) string {
		return fmt.Sprintf("item-%d", n)
	})
	fmt.Println(int(sum))
	fmt.Println(Describe(AccountID(7)))
	fmt.Println(converted.value, Zero[int]())
}
~~~

Программа печатает `42`, `account-7` и `item-21 0`. Именованный `AccountID` входит в набор `Integer` благодаря `underlying type` `int`; `Describable` дополнительно требует метод `String()`. `Map` показывает отдельный параметр `R` generic-метода и выводит его из результата callback. `Zero` показывает, что произвольный результат инициализируют переменной нулевого значения, а тип без аргумента не выводится.

## Ошибки и ограничения

- Не считайте `any` ограничением для любой операции. Чтобы использовать сложение, сравнение или метод, `constraint` должен явно гарантировать её для всего `type set`.
- Не используйте interface с `~T` или union как обычный тип поля или переменной: такие non-basic interfaces служат ограничениями параметров типа.
- Не выводите безусловную гарантию отсутствия `panic` из `comparable`, когда допустимый тип-аргумент — интерфейс и его значение может содержать несравнимую динамическую величину.
- Не пытайтесь объявить собственный параметр у метода интерфейса. Интерфейсные методы могут использовать параметры своего интерфейса, но не добавить параметры метода.
- Не ожидайте, что generic-метод с дополнительным параметром типа реализует обычный метод интерфейса с похожим именем.
- Не оставляйте `T` только в позиции результата, ожидая, что компилятор выведет его из назначения. Явно укажите типовой аргумент, если вызов не несёт информации для вывода.

<summary>Что включает `constraint` `~int | ~int64` и почему `AccountID` подходит?</summary>

Он включает типы с `underlying type` `int` либо `int64`; именованное определение `AccountID` `int` удовлетворяет первой части. Код внутри `Add` использует сложение, допустимое для каждого типа в наборе. Senior follow-up: почему добавление float нельзя считать безвредным расширением этого `type set`?

</details>

<details>
<summary>Почему `any` как аргумент типа `comparable` имеет нюанс, которого нет у прямого `[]int`?</summary>

`Go 1.20` разрешил `comparable`-ограничению принимать интерфейсные типы, включая `any`. Значение `any` может содержать срез; сравнение двух интерфейсов с одинаковым таким динамическим типом приводит к runtime `panic`. Прямой `[]int` по-прежнему не удовлетворяет `comparable`. Senior follow-up: как изменить API, если `panic` от произвольного payload неприемлем?

</details>

<details>
<summary>Когда можно вывести `T` и когда нужен `Zero[int]()`?</summary>

Аргументы и совместимый контекст могут дать компилятору сведения о `T`. В `Zero[T]()` параметр не встречается среди входов, поэтому вызову нужно указать тип явно. Senior follow-up: какие параметры generic API должны быть явными, чтобы вызов оставался читаемым?

</details>
