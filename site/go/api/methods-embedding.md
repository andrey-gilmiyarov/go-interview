# Наборы методов и встраивание

## Коротко

Методы принадлежат определённому базовому типу, а набор методов типа определяет, какие интерфейсы он реализует. Значение `T` получает методы с receiver `T`; указатель `*T` получает методы с receiver `T` и `*T`. Для API это статическое правило проверки компилятором, а не вопрос о том, можно ли сейчас вызвать метод через конкретную переменную.

Встраивание продвигает методы вложенного поля наружу по правилам спецификации. Оно сокращает запись селектора, но не создаёт новый метод и не превращает композицию в подтип. Проверяйте набор методов обёртки явно, особенно если она должна реализовать интерфейс.

## Как работает

Для метода `func (t T) M()` receiver — значение `T`, а для `func (t *T) M()` receiver — указатель. Если локальная переменная x адресуемая, выражение `x.M()` может быть сокращено компилятором до `(&x).M()`. Это удобство вызова не меняет набор методов `T`: присвоить самому `x` интерфейсу, которому нужен `M` с pointer receiver, по-прежнему нельзя. Указатель `&x` такой интерфейс удовлетворяет.

У структуры с анонимным встроенным полем `T` продвигаются методы `T`; методы `*T` входят в набор методов указателя на внешнюю структуру. Если встроенное поле имеет тип `*T`, методы `T` и `*T` продвигаются в набор методов и внешнего значения, и внешнего указателя. Поэтому изменение поля с `T` на `*T` способно изменить публичное поведение обёртки, даже когда имя метода снаружи не меняется.

Вызов продвинутого метода передаёт receiver вложенного значения. Если встроенный `*T` равен `nil`, метод всё равно может получить `nil` receiver. Он безопасен лишь тогда, когда его реализация допускает `nil`. Метод, который разыменовывает receiver или поле, вызовет `panic`. Встраивание также может дать конфликт имён или неоднозначный путь к одноимённым методам; тогда селектор нужно уточнить через имя встроенного поля.

Для проверки контракта используйте присваивание интерфейсу на уровне пакета: `var _ Reader = (*Store)(nil)`. Такая строка проверяет именно набор методов, не выполняя вызов. Добавляйте отдельные проверки для `T`, `*T` и обёрток с встроенным значением или указателем, если все эти формы входят в API.

Receiver-указатель обычно подходит объекту с изменяемым состоянием, крупной структурой или методами, которым важно единое состояние. Receiver-значение выражает небольшое значение без идентичности и случайно делает копирование явным. Это не правило производительности: поля-срезы, карты и указатели остаются общими после поверхностной копии. Решение должно совпадать с семантикой владения и ожидаемым интерфейсом.

## Пример

~~~go
package main

import "fmt"

type Reader interface {
	Read() string
}

type Store struct {
	value string
}

func (s *Store) Read() string {
	if s == nil {
		return "<nil>"
	}
	return s.value
}

type ValueEmbed struct {
	Store
}

type PointerEmbed struct {
	*Store
}

func main() {
	store := Store{value: "ready"}
	value := ValueEmbed{Store: store}
	pointer := PointerEmbed{Store: &store}

	_, valueImplements := any(value).(Reader)
	_, pointerValueImplements := any(&value).(Reader)
	_, embeddedPointerImplements := any(pointer).(Reader)

	fmt.Println(valueImplements, pointerValueImplements, embeddedPointerImplements)
	fmt.Println(store.Read())
	var missing *Store
	fmt.Println(missing.Read())
}
~~~

Программа печатает `false true true`, затем `ready` и `<nil>`. Значение `ValueEmbed` не удовлетворяет `Reader`, но `*ValueEmbed` удовлетворяет. Поле `*Store` продвигает pointer-метод даже в набор методов значения `PointerEmbed`. Последний вызов показывает допустимую обработку `nil` receiver; удалите проверку в `Read`, и разыменование уже вызовет `panic`.

## Ошибки и ограничения

- Не выводите реализацию интерфейса из того, что вызов `x.M()` компилируется: адресуемая переменная может получить неявный &, а присваивание интерфейсу такого преобразования не делает.
- Не считайте встраивание безопасным способом расширить API. Продвинутый метод становится доступен клиентам и может менять разрешение селекторов при будущих изменениях.
- Не полагайтесь на `nil` receiver, пока контракт метода явно не определяет его смысл. При необходимости обрабатывайте `nil` в самом методе или не допускайте такого значения на границе.
- Не копируйте тип с mutex или состоянием, для которого важна идентичность. Receiver-значение копирует поля структуры, но вложенные ссылочные данные могут остаться общими.
- Не помещайте проверку интерфейса только в тест, который случайно вызывает метод. Компиляторная проверка фиксирует ожидаемый набор методов без побочных эффектов.

## Самопроверка

<details>
<summary>Почему локальное значение `Store` может вызвать метод с receiver `*Store`, но не присваивается `Reader`?</summary>

Вызов для адресуемой переменной может быть сокращён до вызова на её адресе. Набор методов типа `Store` от этого не меняется; интерфейсу нужен именно метод из набора присваиваемого типа. Senior follow-up: как бы вы записали compile-time assertions для обеих форм и почему они полезны при рефакторинге receiver?

</details>

<details>
<summary>Какие наборы методов получат `ValueEmbed` и `PointerEmbed`?</summary>

При встроенном `Store` методы `*Store` доступны через `*ValueEmbed`, но не через `ValueEmbed`. При встроенном `*Store` методы `*Store` продвигаются и в `ValueEmbed`, и в `*ValueEmbed`. Senior follow-up: что изменится для клиентов, если публичное встроенное поле заменить с `T` на `*T`?

</details>

<details>
<summary>Безопасен ли вызов продвинутого метода, если встроенный указатель равен `nil`?</summary>

Метод может получить `nil` receiver; безопасность зависит от его тела. Разыменование `nil` приводит к `panic`, а явная проверка receiver может определить полезное поведение. Senior follow-up: лучше ли в данном API сохранить `nil`-обработку или отвергнуть пустую обёртку при создании?

</details>
