# Ошибки как публичный контракт

## Коротко

Значение `error` переносит причину неуспешной операции через границы функций и пакетов. Клиент должен распознавать категории через `errors.Is` и `errors.As`, а не разбирать текст Error. Обёртка сохраняет связь с причиной, typed `error` добавляет структурированные данные, а `errors.Join` представляет несколько независимых проблем.

Выбор того, какую причину показать наружу, является частью API. Слишком бедная ошибка заставляет клиента угадывать, а раскрытие внутренней причины связывает клиента с деталями реализации. Решите заранее, какие категории и поля стабильны, и как сохраняется контекст границ.

## Как работает

Тип `error` требует метода `Error() string`. Значение ошибки может также предоставить `Unwrap() error`, а агрегат — `Unwrap() []error`. `errors.Is` ищет совпадение в дереве причин; обычно для поиска категории используют sentinel. `errors.As` ищет первое подходящее значение заданного типа или интерфейса и записывает его в указатель-получатель. Получатель обязан быть корректным ненулевым указателем, иначе As вызывает `panic`.

`fmt.Errorf` с одним `%w` создаёт обёртку, которую можно исследовать через `Is` и `As`. Добавляйте к сообщению действие и локальный контекст, например имя файла или этап операции, но не заставляйте вызывающий код сравнивать форматированную строку. Если нижний уровень вернул ошибку, обычно сохраняйте её причину при пересечении границы, где добавляете новый контекст.

`errors.Join` отбрасывает `nil`-аргументы и возвращает `nil`, если все аргументы `nil`. Иначе результат раскрывает несколько дочерних ошибок для Is и As. Это полезно для независимой проверки нескольких полей, однако не заменяет приоритет выбора. Если ошибки означают одну операцию, где одна первична, сначала решите, следует ли агрегировать их или вернуть наиболее полезную причину. Не делайте порядок текста Join машиночитаемым протоколом.

Sentinel подходит для небольшой стабильной категории: например, `ErrNotFound`, которую множество внутренних реализаций могут оборачивать. Типизированная ошибка подходит, когда вызывающему коду нужны данные, например поле и индекс. Можно дать типу Unwrap, чтобы он одновременно предоставлял данные и сохранял категорию через Is. Не экспортируйте sentinel или тип, если клиенту не нужно ветвление по нему.

Политика границы помогает сохранять свободу реализации: переводите низкоуровневую ошибку в доменную только там, где смысл операции меняется; сохраняйте исходную причину, если потребитель должен её классифицировать; скрывайте чувствительные значения из публичного текста и логов. Стабильность текста, цепочки обёрток и доступность деталей должны быть согласованы, особенно если внешние клиенты зависят от вашей библиотеки.

## Пример

~~~go
package main

import (
	"errors"
	"fmt"
	"strings"
)

var ErrInvalidInput = errors.New("invalid input")

type FieldError struct {
	Field string
	Value string
}

func (e *FieldError) Error() string {
	return fmt.Sprintf("%s: invalid value %q", e.Field, e.Value)
}

func (e *FieldError) Unwrap() error {
	return ErrInvalidInput
}

func validate(name string, age int) error {
	var problems []error
	if strings.TrimSpace(name) == "" {
		problems = append(problems, &FieldError{Field: "name", Value: name})
	}
	if age < 0 {
		problems = append(problems, &FieldError{Field: "age", Value: fmt.Sprint(age)})
	}
	return errors.Join(problems...)
}

func main() {
	err := validate("", -1)
	var field *FieldError
	fmt.Println(errors.Is(err, ErrInvalidInput))
	fmt.Println(errors.As(err, &field), field.Field)
}
~~~

Обе проверки печатают `true`. `Join` сохраняет ошибки двух полей, `Is` распознаёт общий sentinel через `Unwrap`, а `As` получает первую подходящую `FieldError`. Код клиента не зависит от полного текста диагностики.

### Проверка нескольких условий

`ValidateLine` независимо проверяет, есть ли Unicode-цифра, достигла ли строка 20 рун и содержит ли ровно два ASCII-пробела. `utf8.RuneCountInString` считает руны (кодовые точки Unicode), а `strings.Count(line, " ")` считает только U+0020: табы и другие пробельные символы не подходят. Нарушения объединяются через `errors.Join`; вызывающий код классифицирует каждую причину с помощью `errors.Is`, не разбирая текст. Для корректной строки нарушений нет, поэтому `errors.Join` возвращает `nil`.

## Ошибки и ограничения

- Не делайте `err == ErrSentinel` основной политикой поиска обёрнутой причины. Используйте `errors.Is`, чтобы обёртка могла сохранить категорию.
- Не вызывайте `errors.As` с переменной-ошибкой вместо указателя на неё. Правильная форма `var target *FieldError`; `errors.As(err, &target)`.
- Не сравнивайте текст Error для ветвления: формат может измениться, локализоваться или включить новые детали.
- Не возвращайте типизированный `nil` через `error`. Интерфейс с динамическим типом остаётся ненулевым; см. [объяснение интерфейсов](./interfaces.md).
- Не соединяйте ошибки автоматически. При агрегации подумайте о повторяющихся причинах, секретных данных, порядке диагностики и о том, сможет ли клиент принять полезное решение.
- Не предполагайте, что каждый тип ошибки безопасно сравним через ==. Для классификации и извлечения используйте Is и As с корректными целевыми значениями.

## Самопроверка

<details>
<summary>Чем `errors.Is` отличается от `errors.As`?</summary>

Is отвечает на вопрос о категории или sentinel по цепочке обёрток. As извлекает первое подходящее значение конкретного типа или интерфейса и записывает его в указатель. Senior follow-up: где в API предпочтительнее стабильная категория, а где клиенту нужны структурированные данные?

</details>

<details>
<summary>Что вернёт `errors.Join`, если все аргументы равны `nil`?</summary>

Результат равен `nil`. Для ненулевого результата Is и As обходят присоединённые ошибки, поэтому одну проверку можно применить ко всему дереву. Senior follow-up: какие независимые ошибки действительно полезно возвращать вместе, а какие лучше оформить как первичную причину и контекст?

</details>

<details>
<summary>Что стоит сохранять, добавляя ошибку на границе пакета?</summary>

Сохраняйте достаточно причинной связи для обещанной клиентам классификации, добавьте полезный локальный контекст и не раскрывайте секретные детали. Senior follow-up: какая часть цепочки входит в публичную гарантию, а какая остаётся внутренним диагностическим выбором?

</details>
