# Пакеты и устойчивые API

## Коротко

Граница пакета задаёт имена, которые клиент может импортировать, и обязанности, которые клиент может безопасно ожидать. Экспортируемая функция, тип, поле, ошибка, формат и семантика возврата могут стать частью долгосрочного договора. Компактный API проще поддерживать, чем набор возможностей «на всякий случай».

Для динамической подмены реализаций обычно полезен небольшой интерфейс на стороне потребителя: он выражает только нужные операции и не заставляет производителя заранее угадывать все сценарии клиентов. Экспортируйте конкретные типы и функции, которые составляют ваш продукт; оставляйте тестовые и внутренние интерфейсы там, где ими пользуется вызывающий код.

## Как работает

Имя с заглавной буквы доступно из другого пакета, имя со строчной — нет. Импортёр использует экспортируемое имя через путь пакета и его выбранный локальный псевдоним. Публичность не ограничивается сигнатурой: комментарии, допустимый `nil`, владение переданными срезами, порядок результатов, безопасность параллельных вызовов и классы ошибок влияют на возможность мигрировать реализацию.

Не экспортируйте широкий интерфейс только потому, что один тип его реализует. Потребителю может хватить одного метода `Load`; тогда его собственный интерфейс можно реализовать production-типом, фейком или адаптером. Производитель при этом не добавляет методы наугад под всех потенциальных клиентов. Несколько очень маленьких интерфейсов часто выражают возможности яснее, чем один большой Service с десятками обязанностей.

Добавление метода к экспортируемому интерфейсу — источник несовместимости: внешние типы, которые ранее неявно его реализовывали, перестанут удовлетворять новому набору методов. Добавление поля к экспортируемой структуре также может сломать клиентский код с позиционным составным литералом. Если нужна эволюция, рассмотрите конструктор, закрытое внутреннее состояние, новый узкий интерфейс, новую функцию или явную мажорную версию.

Совместимость имеет несколько измерений. Изменение может сохранить компиляцию, но поменять семантику ошибок, `nil`, порядок, таймаут или ownership. Зафиксируйте гарантии, на которые клиент может положиться, и не обещайте свойства, которые вы не готовы тестировать. Комментарии к экспортируемым идентификаторам, примеры и contract tests помогают обнаружить регрессии; они не заменяют ясный выбор публичного договора.

Для Go-модулей мажорная версия 2 и выше получает суффикс пути импорта вроде `/v2`. Это позволяет старой и новой несовместимой версии сосуществовать в графе зависимостей. Перед выпуском меняйте публичный контракт только с планом миграции: опишите причину, примеры замены и срок удаления устаревшего пути. Не запускайте такую миграцию одной механической заменой версий без проверки клиентских мест.

## Пример

~~~go
package main

import (
	"context"
	"fmt"
	"slices"
)

type Snapshot struct {
	IDs []string
}

type Source interface {
	Load(context.Context) (Snapshot, error)
}

func LoadIDs(ctx context.Context, source Source) ([]string, error) {
	snapshot, err := source.Load(ctx)
	if err != nil {
		return nil, err
	}
	return slices.Clone(snapshot.IDs), nil
}

type MemorySource struct {
	ids []string
}

func NewMemorySource(ids ...string) MemorySource {
	return MemorySource{ids: slices.Clone(ids)}
}

func (source MemorySource) Load(ctx context.Context) (Snapshot, error) {
	if err := ctx.Err(); err != nil {
		return Snapshot{}, err
	}
	return Snapshot{IDs: slices.Clone(source.ids)}, nil
}

func main() {
	ids, err := LoadIDs(context.Background(), NewMemorySource("u-1", "u-2"))
	fmt.Println(ids, err)
}
~~~

Потребитель `LoadIDs` зависит только от способности `Load`, а `MemorySource` остаётся конкретной деталью реализации. В реальном многопакетном проекте `Source` обычно объявляется рядом с потребителем; в этом однофайловом примере объявления сведены вместе ради запуска. Копирование среза фиксирует ownership результата: клиент не получает внутренний массив источника.

## Ошибки и ограничения

- Не публикуйте интерфейс, если клиентам не нужна полиморфная подмена. Каждый его метод — обязательство для всех реализаций.
- Не меняйте смысл `nil`, порядка, копирования, повторного вызова или конкурентного использования молча. Эти свойства влияют на клиента не меньше типов в сигнатуре.
- Не возвращайте внутреннюю структуру только потому, что её поля сейчас удобны. Композиционные литералы и экспортируемые поля затрудняют добавление инвариантов.
- Не утверждайте, что интерфейс гарантирует поведение. Он проверяет формы методов, но не подтверждает побочные эффекты, производительность или потокобезопасность.
- Не делайте мажорный bump единственным описанием несовместимости. Клиенту нужны конкретные изменения и маршрут перехода.

<summary>Почему добавление метода к публичному интерфейсу может быть несовместимым?</summary>

Клиентские типы реализуют интерфейс неявно. После изменения они должны предоставить новый метод или перестанут компилироваться в местах присваивания. Senior follow-up: как добавить новую возможность без принуждения всех старых реализаций?

Изменение ownership, значения `nil`, порядка, таймаута, семантики повторов или ошибок может сохранить сигнатуру, но изменить поведение клиента. Senior follow-up: какие из этих гарантий в вашей системе должны быть закреплены контрактным тестом?
