## Коротко

Интерфейсный тип описывает набор методов, а конкретный тип реализует его неявно, если имеет нужные сигнатуры. Интерфейс полезен, когда вызывающему коду нужна возможность, а не вся конкретная структура. Маленький интерфейс упрощает подмену реализации, но его поведение и семантика должны быть понятны по контракту.

Удобная семантическая модель непустого интерфейсного значения — динамический конкретный тип плюс динамическое значение этого типа. Это объясняет method dispatch, assertions и typed `nil`. Это модель поведения языка, а не обещание `ABI`, размера или физической раскладки памяти.

## Как работает

Пустой интерфейс `any` может хранить значение любого типа; интерфейс с методами хранит только значения типов, набор методов которых подходит этому интерфейсу. При вызове метода компилятор проверяет статический интерфейсный контракт, а во время исполнения выбирается реализация динамического типа. У интерфейса нет объявлений implements: новая реализация может удовлетворить интерфейс без изменения своего пакета.

Нулевой интерфейс — это отсутствие и динамического типа, и значения, поэтому его сравнение с `nil` даёт `true`. Иначе ведёт себя интерфейс, куда записали `nil`-указатель: динамический тип присутствует, следовательно, интерфейс не равен `nil`. Метод на таком указателе может корректно обработать `nil` receiver или упасть при разыменовании. Проверка только `err == nil` не обнаружит typed `nil`, если функция вернула типизированный `nil` через error.

Проверка утверждения `v.(*File)` проверяет конкретный динамический тип, а форма `v.(*File)` с двумя результатами позволяет обработать несовпадение без `panic`. Type switch удобен, когда вызывающий код сознательно поддерживает несколько конкретных форм. Частые assertions к закрытому списку типов могут означать, что интерфейс слишком общий или что API на самом деле требует tagged union.

При сравнении двух интерфейсов с одинаковым динамическим типом хранимое значение должно быть сравнимым. При одинаковом динамическом несравнимом типе, например `[]int`, сравнение двух интерфейсов вызывает `panic` во время исполнения. Сравнение с `nil` проверяет отсутствие динамического значения и само по себе не перебирает содержимое среза. Поэтому интерфейс `any` не является универсальной безопасной заменой deep equality. Если контракт требует равенства, задайте сравнение явно или ограничьте допустимые типы.

Вызов через интерфейс удобен для тестирования и смены реализации, но интерфейс не определяет побочные эффекты, порядок операций, потокобезопасность, владение данными или обработку ошибок. Эти гарантии нужно описать отдельно. Не обещайте клиентам машинное представление интерфейса: компилятор и runtime выбирают внутреннюю реализацию, а публичный договор остаётся на уровне языка.

## Пример

~~~go
package main

import "fmt"

type Printer interface {
	String() string
}

type Widget struct {
	value string
}

func (w *Widget) String() string {
	if w == nil {
		return "<nil widget>"
	}
	return w.value
}

func main() {
	var absent Printer
	var widget *Widget
	var typed Printer = widget

	fmt.Println(absent == nil, typed == nil, typed.String())
	got, ok := typed.(*Widget)
	fmt.Println(ok, got == nil)
}
~~~

Результат — `true false <nil widget>`, затем `true true`. Первый интерфейс пуст. Во втором динамический тип — `*Widget`, хотя хранимое значение указателя `nil`. Assertion извлекает именно это типизированное `nil`-значение. Уберите `nil`-проверку из String, и вызов `typed.String()` завершится `panic`.

## Ошибки и ограничения

- Не возвращайте интерфейс с типизированным `nil`, если API обещает `nil` как признак отсутствия ошибки. Возвращайте буквально `nil` или меняйте представление результата.
- Не сравнивайте значения `any` с недоверенным динамическим содержимым без проверки сравнимости. Паника может возникнуть далеко от места, где значение впервые попало в интерфейс.
- Не используйте reflection как автоматический обход typed `nil`. Сначала решите, допускает ли контракт `nil`-указатель, `nil`-map, `nil`-slice и другие нулевые формы.
- Не создавайте интерфейс из одного метода «на будущее». Узкий интерфейс рядом с потребителем обычно легче реализовать и сохранить совместимым.
- Не делайте вывод о runtime `ABI` из семантической пары тип-значение. Детали компоновки меняются и не являются публичной гарантией языка.

## Самопроверка

<details>
<summary>Почему интерфейс с `nil`-указателем не равен `nil`?</summary>

У значения есть динамический тип `*Widget`, поэтому это не нулевой интерфейс. Сам указатель внутри значения может быть `nil`, и вызов метода зависит от поведения `nil` receiver. Senior follow-up: как проверить обязательную зависимость в конструкторе, если параметр имеет тип интерфейса?

</details>

<details>
<summary>Когда сравнение двух интерфейсов может привести к `panic`?</summary>

Когда динамические типы одинаковы, а значение этого типа нельзя сравнивать, например два интерфейса со значением-срезом. Сравнение с `nil` не выполняет такое сравнение содержимого. Senior follow-up: какая явная функция равенства подходит, если API принимает произвольный тип?

</details>

<details>
<summary>Гарантирует ли интерфейс потокобезопасность реализации?</summary>

Нет. Интерфейс гарантирует только набор вызываемых методов; синхронизация, владение и допустимый параллелизм требуют отдельного контракта. Senior follow-up: какой тест или документация покажет потребителю, можно ли разделять один объект между запросами?

</details>
