# Модель памяти и атомарные операции

## Коротко

При конкурентном доступе к данным важны не только значения, но и порядок, в котором одна горутина публикует запись, а другая её наблюдает. Модель Go задаёт отношение happens-before: оно объединяет порядок операций внутри одной горутины и связи синхронизации между горутинами. Data race возникает, когда конфликтующие обращения к одной ячейке памяти не упорядочены happens-before, хотя бы одно из них — запись, а хотя бы одно — обычное, не синхронизирующее обращение. Физически выполняться одновременно им не нужно: гонку определяет отсутствие порядка happens-before. Если оба обращения атомарны, data race нет, хотя логическая гонка, например потеря обновления, возможна.

Программа без гонок ведёт себя так, как если бы операции её горутин исполнялись в некотором последовательном порядке, сохраняющем их локальный порядок. Это DRF-SC — гарантия для race-free программы. `sync/atomic` даёт атомарные операции над отдельным значением, но не превращает несколько полей или несколько вызовов в одну транзакцию.

## Как работает

Happens-before — транзитивное замыкание `sequenced before` внутри горутины и `synchronized before` между операциями синхронизации. Чтобы обычная запись стала видна обычному чтению, запись должна произойти happens-before чтения и не быть заменена более поздней упорядоченной записью. Простая надежда, что планировщик «уже переключился», такого отношения не создаёт.

Некоторые полезные границы заданы спецификацией и пакетами. Оператор `go` упорядочен перед началом новой горутины, поэтому начальные данные, записанные до запуска, видны ей; обратной гарантии при выходе горутины нет. Send предшествует завершению соответствующего receive; закрытие канала предшествует receive, который сообщает о закрытии. У mutex более ранний `Unlock` синхронизируется перед последующим `Lock`; завершение, учтённое в `WaitGroup`, синхронизируется перед возвратом разблокированного `Wait`. Эти ребра можно составить транзитивно, чтобы доказать публикацию результата.

Буфер канала меняет точку подтверждения: соответствующий send может завершиться до того, как получатель прочитал значение. Для ёмкости `C` завершение k-го receive предшествует завершению (k+C)-й отправки. Это позволяет моделировать ограниченный семафор, но не означает, что любая ранняя запись автоматически видна любой поздней горутине без соответствующего канального порядка.

Атомарные операции пакета `sync/atomic` выполняются как единый последовательный порядок атомарных операций. Если загрузка наблюдает эффект более ранней атомарной операции, та синхронизирована перед этой загрузкой. Это позволяет безопасно публиковать неизменяемый снимок через `atomic.Pointer`. Все обращения к такому состоянию должны соблюдать единый контракт: смешивать атомарные операции с обычным чтением или записью того же поля нельзя.

`Load` с вычислением и `Store` — две атомарные операции, а не атомарное «прочитать-изменить-записать». При двух обновляющих горутинах обе могут загрузить старое значение и перезаписать друг друга. Это логическая гонка с потерей обновления, но не data race: сами `Load` и `Store` атомарны, а последовательность read-modify-write — нет. Для отдельного счётчика используйте `Add` или цикл CAS; для инварианта между балансом и версией используйте одну блокировку либо публикуйте новый неизменяемый объект целиком. Не пытайтесь чинить несколько взаимосвязанных полей отдельными атомиками: читатель всё равно может увидеть комбинацию из разных обновлений.

## Пример

```go
package main

import (
	"fmt"
	"sync/atomic"
	"time"
)

type Config struct {
	Host    string
	Timeout time.Duration
}

var current atomic.Pointer[Config]

func publish(next Config) {
	snapshot := next
	current.Store(&snapshot)
}

func readConfig() (Config, bool) {
	snapshot := current.Load()
	if snapshot == nil {
		return Config{}, false
	}
	return *snapshot, true
}

func main() {
	publish(Config{Host: "api.internal", Timeout: time.Second})
	if config, ok := readConfig(); ok {
		fmt.Println(config.Host, config.Timeout)
	}
}
```

Структура полностью собрана до `Store`, поэтому читатель, который загрузил этот указатель, может читать обе её поля. В примере снимок после публикации не меняется. Если добавить в `Config` map, срез или указатель на изменяемый объект, их тоже нужно скопировать и дальше считать неизменяемыми либо защищать отдельной синхронизацией. Атомарный указатель не делает граф объектов под ним потокобезопасным.

## Ошибки и ограничения

- Не полагайтесь на sleep, логирование или «обычно этот поток уже успевает». Они не создают гарантии happens-before.
- Не считайте завершение горутины само по себе публикацией её записей. Используйте наблюдаемое завершение через канал, mutex, `WaitGroup` или другой задокументированный механизм.
- Не используйте `atomic.Load` + `atomic.Store` для инкремента под конкуренцией: применяйте `Add` либо цикл сравнения-и-замены.
- Не защищайте одним mutex только запись, оставляя обычные читательские обращения параллельно. Все конкурирующие доступы к области данных должны следовать общему протоколу.
- Не считайте два независимых атомика транзакцией для общего инварианта. Один читатель может увидеть поля из разных версий состояния.
- Не интерпретируйте отсутствие сообщений race detector как доказательство отсутствия гонки: проверяются только реально выполненные пути и расписания.

`go test -race` — сильный динамический инструмент для тестируемых путей, а не анализ всех возможных запусков. Для диагностики полезно записать, кто пишет каждое поле и какой именно синхронизирующий вызов связывает писателя с читателем. Если такую цепочку нельзя объяснить, код остаётся подозрительным даже после множества успешных запусков.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Почему запуск через go f() упорядочивает начальные данные, но не даёт результата f()?</summary>

Сам `go` упорядочен перед стартом новой горутины. Её выход не синхронизирован автоматически с последующими действиями вызывающей горутины. Senior follow-up: какое завершение можно наблюдать, чтобы получить связь в обратном направлении?

</details>

<details>
<summary>Почему Load затем Store не равны атомарному инкременту?</summary>

Каждая операция атомарна отдельно. Несколько горутин могут загрузить одно старое значение и сохранить одинаковое следующее, потеряв обновление. Senior follow-up: когда подходит `atomic.Add`, а когда mutex или CAS-loop?

</details>

<details>
<summary>Что защищает атомарный указатель на неизменяемую Config и чего он не защищает?</summary>

Он атомарно публикует сам указатель и предшествующее заполнение объекта. Он не синхронизирует дальнейшие изменения полей, карты или среза, на которые тот указывает. Senior follow-up: где проходит граница копирования снимка?

</details>
