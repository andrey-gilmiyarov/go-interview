# Жизненный цикл горутины

## Коротко

Оператор `go` запускает функцию конкурентно и сразу продолжает вызывающий поток. Возврат функции, которая выполнила `go`, не означает, что дочерняя работа закончилась. Для каждого запуска нужен явный ответ на три вопроса: кто сообщает, что работу пора остановить; кто гарантирует, что горутина завершилась; кто владеет ресурсами и каналами, которые она использует.

Отмена и ожидание решают разные задачи. `context.Context` сообщает о дедлайне или отмене, но не прерывает код принудительно. `sync.WaitGroup` или канал завершения позволяет дождаться выхода, но сам по себе не останавливает застрявшую работу. Часто нужны оба механизма: сначала отменить, затем присоединиться к дочерним горутинам и только после этого освобождать общие ресурсы.

## Как работает

Горутина — единица выполнения рантайма, а не обещание отдельного ядра или потока ОС. После `go f()` вызывающая функция может продолжить и даже вернуться раньше `f`. Выход горутины сам по себе не создаёт гарантии видимости её записей для другой горутины. Если результат должен быть наблюдаем, свяжите действия каналом, блокировкой, атомарной операцией или ожиданием подходящего примитива синхронизации. Подробная причинная модель разобрана в [модели памяти и атомарных операциях](./memory-model-atomic.md).

Контекст отмены кооперативный: библиотечный вызов остановится только тогда, когда умеет принимать контекст, а собственный цикл должен периодически выбирать `ctx.Done()`. Даже если отмена уже произошла, горутина может ещё выполнять текущую операцию. Поэтому владелец группы не должен закрывать файл, канал или клиент, пока подчинённая работа всё ещё может к ним обратиться. Сначала попросите её остановиться, затем дождитесь завершения, после чего закройте ресурс.

Завершение полезно представлять как контракт владения. Запустивший горутину компонент обычно отвечает за её контекст и ожидание; производитель канала закрывает его после последней отправки; потребитель, который перестал читать раньше времени, должен отменить работу, иначе отправитель может навсегда заблокироваться. Если есть несколько отправителей, один координатор закрывает канал только после того, как присоединился ко всем отправителям. Конкретные правила передачи и закрытия разобраны в разделе [«Каналы»](./channels.md).

В Go 1.27.1 `WaitGroup.Go` позволяет связать запуск и учёт задачи одним вызовом. Он ждёт вызванную функцию через `Wait`, но не принимает контекст и не перехватывает ошибку. Функция, переданная в `Go`, не должна паниковать. Счётчик группы не заменяет политику остановки: если работа может зависнуть, `Wait` тоже будет ждать бесконечно. Для старых версий языка остаются `Add`, `go` и `defer Done`, причём положительный `Add`, начинающий пустую группу, должен произойти до `Wait`.

## Пример

```go
package main

import (
	"context"
	"fmt"
)

func double(ctx context.Context, in <-chan int, out chan<- int) {
	for {
		select {
		case <-ctx.Done():
			return
		case n, ok := <-in:
			if !ok {
				return
			}
			select {
			case out <- n * 2:
			case <-ctx.Done():
				return
			}
		}
	}
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	in := make(chan int, 2)
	in <- 2
	in <- 3
	close(in)

	out := make(chan int, 2)
	done := make(chan struct{})
	go func() {
		defer close(done)
		defer close(out)
		double(ctx, in, out)
	}()

	for n := range out {
		fmt.Println(n)
	}
	<-done
}
```

Буфер `out` ограничен двумя результатами, поэтому пример не запускает производителя, способного бесконечно накапливать данные. Обёртка владеет единственным отправителем и закрывает `out` после его выхода. `range` видит конец потока, а чтение из `done` отдельно подтверждает, что обёртка тоже завершилась. Если потребитель решит выйти из цикла раньше, он должен вызвать `cancel`, иначе отправка может ждать читателя.

## Ошибки и ограничения

- Не рассчитывайте на автоматическую остановку: `cancel()` закрывает `Done`, но не прерывает произвольную функцию и не делает `Wait` неблокирующим.
- Не закрывайте общие ресурсы до ожидания всех горутин, которые ещё могут их использовать.
- Не считайте возврат запускающей функции присоединением к запущенной горутине. Иначе ошибки и финальная запись могут потеряться.
- Не запускайте горутину без ясного владельца завершения. Проверяйте ранние выходы потребителя, ошибки, тайм-ауты и остановку сервера.
- Не ждите функцию, которая ожидает сигнала от самой ожидающей стороны: ошибочное владение остановкой превращается в deadlock.
- `WaitGroup` не ограничивает число горутин и не распространяет отмену. Для связи отмены, ошибки и ожидания группы есть отдельные средства; выбор зависит от требуемого поведения.

При диагностике сначала найдите владельца каждого `go`, затем перечислите все его блокирующие точки и события, которые могут разблокировать каждую из них. `runtime/pprof` goroutine-профиль и трассировка помогают увидеть ожидания в живом процессе; профиль `goroutineleak`, доступный в Go 1.27, находит класс безвозвратно заблокированных горутин по достижимости, но не доказывает отсутствие всех утечек.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Что гарантирует возврат функции, выполнившей go worker()?</summary>

Только то, что эта функция дошла до возврата. Она не ждала `worker`. Если вызывающей стороне нужен результат или безопасное закрытие ресурса, требуется отдельный сигнал завершения или ожидание. Senior follow-up: как выбранный примитив создаёт порядок видимости для результатов?

</details>

<details>
<summary>Почему одного вызова cancel недостаточно перед закрытием ресурса?</summary>

Отмена кооперативная. Горутина может ещё обрабатывать текущую операцию или игнорировать `Done`; ресурс безопасно закрывать после подтверждённого завершения. Senior follow-up: какое поведение у операции, если она не поддерживает контекст?

</details>

<details>
<summary>Кто должен закрыть канал, если в него отправляют несколько горутин?</summary>

Координатор, который знает, что все отправители завершились. Любой отправитель может закрыть свой выход только если он единственный владелец отправок. Senior follow-up: каким способом координатор присоединится ко всем производителям?

</details>
