# Оператор select

## Коротко

`select` выбирает одну готовую отправку или приём среди веток. Если готовы несколько, спецификация разрешает выбрать любую из них с равновероятным псевдослучайным выбором. Порядок веток в исходнике не задаёт приоритет. Если ни одна операция не готова, `select` блокируется; `default` вместо ожидания выполняется сразу.

Это примитив арбитража и ожидания, а не планировщик с обещанной справедливостью. Отмена через `ctx.Done()` тоже не имеет приоритета: если бизнес-операция и отмена одновременно готовы, может победить любая ветка. Если контракт зависит от отмены, результат нужно проверять и согласовывать явно.

## Как работает

При входе в `select` Go вычисляет выражения каналов, а также правую часть каждой отправки ровно один раз и в исходном порядке. Это происходит до выбора ветки и независимо от того, будет ли выбранная коммуникация выполнена. Значит, вызов функции справа от `case ch <- f()` не откладывается до выбора отправки: `f()` уже выполнится.

Затем рантайм определяет готовые коммуникации. Receive готов, если есть отправитель, значение в буфере или закрытие; send готов, если получатель уже ждёт или в буфере есть место. Готовая ветка выбирается по правилу спецификации. Иначе выполняется `default`, если он есть, или текущая горутина блокируется до изменения ситуации.

Receive из закрытого канала остаётся готовым навсегда; после прочтения буфера он выдаёт нулевое значение и `ok == false`. Если такой канал оставить в цикле, ветка может выбираться снова и снова. Обычно канал после обнаружения закрытия присваивают `nil`, выключая соответствующий case. Нулевой канал также отключает ветку выбора. Детали закрытия и владения каналом описаны в статье [«Каналы»](./channels.md).

Наличие `default` часто скрывает намерение: цикл с `default` немедленно повторяется и расходует процессор, если он не делает полезной работы. Для неблокирующей попытки это осознанный контракт, но для ожидания обычно нужен блокирующий `select` или иной примитив. Если одному событию нужен приоритет, одного расположения его case первым недостаточно; используйте явный протокол проверки состояния и определите, какое событие побеждает при гонке.

## Пример

```go
package main

import "fmt"

func receive(left, right <-chan string) string {
	select {
	case value := <-left:
		return "left: " + value
	case value := <-right:
		return "right: " + value
	}
}

func main() {
	left := make(chan string, 1)
	right := make(chan string, 1)
	left <- "A"
	right <- "B"

	first := receive(left, right)
	second := receive(left, right)
	fmt.Println(first, second)
}
```

Обе ветки готовы при первом вызове, поэтому результат может начинаться как с `left: A`, так и с `right: B`. После первого чтения второе значение остаётся в другом буфере, и второй вызов получает его. Значения детерминированы, порядок первого выбора — нет. В программе нет горутины-производителя, которую надо останавливать, и буферы заведомо вмещают все отправленные значения.

## Ошибки и ограничения

- Не пытайтесь задать приоритет перестановкой case. При двух готовых операциях порядок исходника не является гарантией.
- Не считайте выбор веток гарантирующим продвижение каждого case. Не стройте контракт на справедливом расписании нескольких операций.
- Не используйте `default` в цикле ожидания без паузы или иной работы: такой polling обычно превращается в busy loop.
- Не забывайте про вычисление выражений при входе. Изменение счётчика или дорогой вызов справа от send произойдёт даже при выборе другой ветки.
- При приёме учитывайте `ok`, если нулевое значение может быть обычными данными. Иначе закрытие может выглядеть как ещё одно сообщение.
- Не предполагая приоритет отмены, проверьте `ctx.Err()` после выбора, если действие ещё не должно фиксироваться после дедлайна. Определите поведение для операции, уже пересёкшей точку фиксации.

Для отладки сначала выпишите готовые операции в момент каждого входа в `select`. Затем отметьте побочные эффекты вычисляемых выражений и проверьте повторные итерации после закрытия канала. Гонка выбора не является гонкой данных: порядок может быть недетерминированным, но каждая допустимая ветка всё равно должна соблюдать прикладной инвариант.
