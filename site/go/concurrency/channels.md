## Коротко

Канал передаёт значения между горутинами и создаёт точку координации. Небуферизованный send ждёт встречного receive, поэтому производитель получает обратное давление от потребителя. Буфер ограничивает очередь, но не освобождает программу от решения, что делать при заполнении, отмене или прекращении чтения.

Канал имеет направление и владельца жизненного цикла. Создавший поток данных обычно закрывает канал после последней отправки. Читатель обычно не закрывает входной канал: он не знает, есть ли ещё отправители. `close` сообщает «новых значений больше не будет», но не отменяет горутину и не освобождает её автоматически.

## Как работает

У небуферизованного канала send и receive образуют rendezvous: обе стороны должны быть готовы. Для канала ёмкости `C` отправка может завершиться, если в очереди есть место; когда буфер заполнен, отправитель блокируется. Это вводит верхнюю границу количества значений, ожидающих чтения. Выбор буфера — часть политики нагрузки и памяти, а не универсальная оптимизация скорости.

У закрытого канала уже отправленные значения можно дочитать. После опустошения receive немедленно возвращает нулевое значение и `ok == false`, а send в закрытый канал паникует. Повторный `close` тоже паникует. Поэтому закрывать канал должен владелец, способный доказать, что все отправки уже закончились. Если отправителей несколько, нужен координатор: он ждёт их, затем закрывает общий выход.

Нулевой `chan T` равен `nil`. Отправка и получение из него навсегда блокируются, а ветка такого канала в `select` отключена. Это бывает полезно для явного выключения направления выбора, но забытое nil-значение может превратить цикл в зависание. Каналы можно безопасно читать из нескольких горутин, однако многократные читатели распределят значения между собой; каждый потребитель не получит каждое сообщение.

Пакетная передача не копирует весь объект рекурсивно: значение передаётся по обычным правилам Go. Если по каналу отправили указатель, срез или карту, стороны всё ещё могут разделять изменяемую память. Канальная отправка сама по себе не даёт эксклюзивного владения объектом — это соглашение API. За причинный порядок между отправкой и получением отвечает модель памяти; подробности — в статье [«Модель памяти и атомарные операции»](./memory-model-atomic.md).

## Пример

```go
package main

import (
	"context"
	"fmt"
)

func stream(ctx context.Context, values []int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, value := range values {
			select {
			case <-ctx.Done():
				return
			case out <- value:
			}
		}
	}()
	return out
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	for n := range stream(ctx, []int{2, 4, 6}) {
		fmt.Println(n)
	}
}
```

Функция отдаёт читателю только направление receive, а внутренний производитель — единственный отправитель и владелец `close(out)`. Небуферизованный канал заставляет производителя ждать, пока `main` получит очередное число. Если потребитель решит остановиться до конца, он должен вызвать `cancel`; без этого производитель может остаться на send навсегда. В промышленном конвейере стоит также явно определить, кто присоединяется к производителю; соответствующая политика описана в будущей статье [«Параллельные шаблоны»](../patterns/concurrency-patterns.md).

## Ошибки и ограничения

- Не закрывайте канал «для безопасности» со стороны читателя: параллельная отправка после close приводит к panic.
- Не используйте `len(ch)` как гарантию свободного места или будущего значения. После проверки состояние может изменить другая горутина.
- Не путайте close с сигналом отмены. Буфер может ещё содержать значения, а производитель может быть заблокирован на другом канале.
- Не ставьте большой буфер без причины: он превращает обратное давление в очередь, которая удерживает память и увеличивает задержку.
- Не считайте, что несколько читателей получают broadcast. Каждый элемент будет получен одним из них; для broadcast требуется отдельная модель уведомления.
- Зафиксируйте семантику ошибок и частичных результатов рядом с контрактом канала. Закрытие означает только конец потока, а не успех обработки.

При поиске зависания нарисуйте для каждой send/receive пару, которая способна её завершить, и проверьте ветви раннего выхода. Отдельно спросите, может ли потребитель закончить раньше, чем производитель, и кто при этом отменяет контекст. Работающий процесс можно исследовать через goroutine-профиль и execution trace; вывод `select` и владение каналами изучаются отдельно, чтобы не принять случайный порядок за гарантию.

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Что вернёт receive из закрытого и опустошённого канала chan int?</summary>

Ноль типа (`0`) и `ok == false`. Одно значение без проверки `ok` не отличит этот случай от реально отправленного нуля. Senior follow-up: какие формы обработки конца потока использует `range`?

</details>

<details>
<summary>Чем буфер помогает и какую проблему он не решает?</summary>

Он допускает ограниченное число отправок без одновременного receive; полный буфер снова блокирует отправителя. Он не отменяет работу и не задаёт действия при остановке читателя. Senior follow-up: как размер буфера связан с верхней границей памяти на элемент?

</details>
