# Context и отмена

## Коротко

`context.Context` переносит через границы вызовов дедлайн, сигнал отмены и небольшие значения, относящиеся к запросу. Он не убивает горутины и не гарантирует прерывание произвольного вызова: каждая операция должна сама реагировать на `Done()` или принять контекст в API.

Обычно вызывающая сторона владеет контекстом верхнего запроса и передаёт его первым аргументом; каждый слой прокидывает его дальше. Функция, создавшая дочерний контекст, обязана вызвать cancel, чтобы освободить связанное состояние даже при успехе. Отмена сообщает причину завершения, но присоединение к горутине и закрытие ресурсов остаются отдельной работой.

## Как работает

`WithCancel`, `WithDeadline` и `WithTimeout` создают производный контекст, который отменяется вместе с родителем или по собственному условию. Если у родителя дедлайн наступает раньше запрошенного дочернего, действует более ранний дедлайн: дочерняя работа не может продлить срок жизни родителя. `Done()` закрывается один раз; `Err()` сообщает `context.Canceled` или `context.DeadlineExceeded`. Проверка `Err` полезна на границе операций, но не заменяет `select` вокруг потенциально блокирующей отправки или получения.

`WithCancelCause` добавляет прикладную причину через `CancelCauseFunc`. `ctx.Err()` по-прежнему сообщает общий класс завершения, а `context.Cause(ctx)` возвращает сохранённую причину. У дерева контекстов срабатывает первая причина, отменившая узел или одного из его предков; более поздний вызов cancel не переписывает уже выбранную причину. Это полезно для диагностики «какой этап завершил работу», если вызывающая сторона должна различать тайм-аут и отказ конкретного этапа.

`WithoutCancel(parent)` наследует значения, но убирает дедлайн, `Done`, `Err` и причину отмены родителя. Его `Done()` равен `nil`, поэтому ветка `<-ctx.Done()` в `select` отключается. Это сознательное отделение жизненного цикла, например для короткой записи аудита после ответа клиенту; обычно такой этап нужно заново ограничить собственным `WithTimeout`, иначе запрос может породить бесконечную фоновую работу. Сохранение значений также удерживает цепочку родительских данных; не переносите лишние или чувствительные значения дальше необходимого срока.

Значения контекста не должны подменять параметры функции, настройки или канал общего состояния. Иначе зависимость становится невидимой в сигнатуре и трудно проверяется. Контекст предназначен для передачи request-scoped метаданных и отмены через API-границы; объект запроса и бизнес-данные передавайте отдельными аргументами. `select` не гарантирует, что отмена победит одновременно готовую работу: политика результата при такой гонке остаётся частью контракта вызывающей операции.

## Пример

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

func run(parent context.Context, work func(context.Context) error) error {
	ctx, cancel := context.WithCancelCause(parent)
	defer cancel(nil)

	if err := work(ctx); err != nil {
		cancel(fmt.Errorf("run work: %w", err))
	}
	if cause := context.Cause(ctx); cause != nil {
		return cause
	}
	return nil
}

func main() {
	err := run(context.Background(), func(context.Context) error {
		return errors.New("upstream rejected the request")
	})
	fmt.Println(err)
}
```

Внутренняя ошибка записывается как причина отмены дочернего контекста и при этом сохраняет исходное значение для `errors.Is`/`errors.As` через `%w`. Если родитель успел отмениться раньше, его причина уже определяет результат. Реальная `work` должна сама прокидывать `ctx` в блокирующие операции; отмена не заставляет её немедленно вернуться. Если `work` запускает горутины, `run` также должен отдельно дождаться их завершения.

## Ошибки и ограничения

- Не создавайте `Background()` глубоко внутри запроса, если работа должна прекращаться вместе с вызывающим кодом. Так теряются дедлайн и отмена.
- Не забывайте `cancel` у созданных тайм-аутов и дочерних контекстов. Это освобождает ресурсы дерева раньше истечения дедлайна.
- Не ожидайте от `cancel` принудительного прерывания. Ваша горутина должна проверять `Done`, а нижележащая библиотека — поддерживать контекст.
- Не полагайтесь на приоритет ветки `<-ctx.Done()` в `select`. При одновременно готовых ветках результат выбирается без пользовательского приоритета.
- Не применяйте `WithoutCancel` без нового срока жизни для отсоединённой работы. Иначе отцепленный участок теряет deadline и может остаться навсегда.
- Не используйте контекст как сумку произвольных параметров. Несущественные значения сложнее валидировать и безопасно логировать.

Для зависшей работы логируйте deadline и причину на границах этапов, затем проверяйте, доходит ли сигнал до сетевого вызова и всех внутренних циклов. Причина `context.Canceled` сама по себе не доказывает, кто инициировал остановку; для внутренней диагностики нужна причина отмены или отдельный структурированный журнал. Об отмене недостаточно знать только по ошибке: проверьте, были ли дочерние горутины присоединены до возврата.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Чем различаются ctx.Err() и context.Cause(ctx)?</summary>

`Err` возвращает стандартную категорию отмены или дедлайна; `Cause` возвращает конкретную сохранённую причину, заданную `WithCancelCause`, либо унаследованную от родителя. Senior follow-up: что произойдёт, если родитель отменится раньше дочернего вызова cancel?

</details>

<details>
<summary>Почему select с веткой ctx.Done() может всё же выполнить другую операцию?</summary>

Если обе ветки готовы, `select` не обещает приоритет отмены. Операции нужно определить точку фиксации и проверить контекст до или после неё согласно контракту. Senior follow-up: можно ли откатить уже отправленный внешний запрос?

</details>

<details>
<summary>Какое скрытое поведение получает контекст из WithoutCancel?</summary>

Его `Done` равен `nil`, а deadline, `Err` и cause отсутствуют; ветка ожидания `Done` никогда не готова. Senior follow-up: какой новый предел времени должен ограничивать cleanup, отделённый от запроса?

</details>
