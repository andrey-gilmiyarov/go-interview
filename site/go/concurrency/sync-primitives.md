# Примитивы пакета sync

## Коротко

Примитив синхронизации должен отражать инвариант, который защищает. `Mutex` делает критическую секцию взаимоисключающей; `WaitGroup` считает задачи, завершения которых ждёт вызывающая сторона; `Once` выполняет одно действие; `Cond` позволяет спать до изменения состояния под блокировкой. Они не взаимозаменяемы: ожидание окончания не отменяет работу, а сигнал не хранит прикладной результат.

Блокировки и объекты `sync` после первого использования нельзя копировать. Если структура содержит mutex, передавайте её обычно по указателю. Выбирайте самый простой примитив, который делает все совместные чтения и изменения понятными одной областью владения.

## Как работает

`Mutex` сериализует критические секции. Данные, защищённые им, следует читать и менять только под той же блокировкой; тогда несколько операций можно составить в одну транзакцию, например «проверить лимит и списать баланс». `RWMutex` позволяет нескольким читателям удерживать read-lock одновременно, но не является гарантированным ускорением: конкуренция за write-lock и дополнительный учёт могут ухудшить частый короткий путь. Нельзя повышать `RLock` до `Lock` или брать `RLock` рекурсивно при ожидающем писателе.

`WaitGroup` нужен, чтобы присоединиться к известному набору завершений. В Go 1.27.1 предпочтительный короткий API — `wg.Go(f)`: он сам увеличивает и уменьшает счётчик; `f` не должна паниковать. `WaitGroup` не собирает ошибки и не рассылает отмену. `Add`/`Done` остаются полезны, когда учёт и запуск разделены; положительный `Add`, начинающий пустую группу, должен произойти до `Wait`.

`Once.Do` подходит для инициализации, выполняемой ровно один раз, но не для бесконечного повтора до успеха. Если функция паникует, `Once` считает её завершённой и следующий `Do` не повторит её. `Cond` привязан к `Locker`: изменение предиката и проверка состояния выполняются под этим lock. `Wait` атомарно освобождает его и засыпает, а перед возвратом снова захватывает; после пробуждения код обязательно проверяет условие в цикле, поскольку другой потребитель мог уже забрать ресурс.

Для простого широковещательного сигнала закрытие канала обычно проще `Cond.Broadcast`; `Signal` ближе к передаче единичного события. `Cond` полезен, когда предикат — сложное состояние под уже существующей блокировкой или когда закрытие канала неудобно. Сама синхронизация не задаёт прикладной политики очереди, отмены или ошибок.

Все эти механизмы участвуют в отношениях «happens-before». Например, unlock публикует защищённые изменения для последующей блокировки; ожидание группы связывает завершение учтённой задачи с возвратом `Wait`. Это гарантия видимости и порядка, а не только «чтобы горутины случайно не столкнулись»; её точная модель разобрана в статье [«Модель памяти и атомарные операции»](./memory-model-atomic.md).

## Пример

```go
package main

import (
	"fmt"
	"sync"
)

type Counter struct {
	mu sync.Mutex
	n  int
}

func (c *Counter) Add(delta int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n += delta
}

func (c *Counter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.n
}

func main() {
	var counter Counter
	var tasks sync.WaitGroup
	for i := 0; i < 4; i++ {
		tasks.Go(func() { counter.Add(1) })
	}
	tasks.Wait()
	fmt.Println(counter.Value())
}
```

Одна блокировка защищает и чтение, и изменение `n`; после `Wait` все четыре вызова завершились, поэтому результат равен `4`. `Value` тоже берёт mutex: даже если текущий пример читает после ожидания, публичный метод может быть вызван одновременно с новой записью. Метод с pointer receiver сохраняет одну общую структуру и не копирует mutex.

## Ошибки и ограничения

- Не копируйте `Mutex`, `RWMutex`, `Once`, `Cond` или `WaitGroup` после первого использования; скрытое копирование структуры часто разрывает защиту состояния.
- Не берите lock и не вызывайте внутри критической секции внешний callback, RPC или код с неизвестным порядком блокировок без необходимости. Так легко создать долгую задержку или deadlock.
- Не считайте `WaitGroup.Wait` заменой cancel. Если задача зависла, счётчик не уменьшится и ожидание не вернётся.
- Не используйте `Once` для операции, которую нужно повторить после ошибки. Храните состояние и ошибку под явной синхронизацией либо определите политику повторов.
- Не вызывайте `Cond.Wait` вне цикла предиката. Сигнал не означает, что условие всё ещё истинно к моменту повторного захвата lock.
- Не добавляйте `RWMutex` по ощущению «чтений больше»: сначала измерьте конкурентную нагрузку и длину защищённого участка.

При расследовании блокировок запишите, какая горутина держит mutex и какое условие должна изменить ожидаемая горутина. Для `WaitGroup` проверьте все пути возврата и panic между учётом и `Done`; при `WaitGroup.Go` помните контракт отсутствия panic. Стандартные mutex/block профили и race detector отвечают на разные вопросы: ожидание блокировки не обязательно означает гонку данных.

<summary>Почему после Cond.Wait нужно заново проверить предикат?</summary>

Lock возвращается вызывающей горутине после пробуждения, но до этого другая горутина могла забрать ресурс или изменить состояние. Senior follow-up: почему ожидание должен вызывать код, уже удерживающий тот же `Cond.L`?

<summary>Почему RWMutex может оказаться медленнее Mutex?</summary>
