# Расширения golang.org/x/sync

## Коротко

`golang.org/x/sync` дополняет стандартный `sync` несколькими координационными политиками. `errgroup` объединяет ожидание горутин с первой ошибкой и производным контекстом; `singleflight` подавляет одинаковую работу, пока она уже выполняется; `semaphore.Weighted` ограничивает суммарную стоимость параллельных операций. Эти пакеты отвечают на разные вопросы и не являются взаимозаменяемыми.

В этом репозитории установлен `golang.org/x/sync v0.22.0`; ниже версия поведения сверена с этим исходным кодом и документацией Go 1.27.1. При обновлении модуля перепроверьте контракт пакета и используемую реализацию. Само наличие готовой примитивной абстракции не определяет политику ошибок, очередь, отмену или владение задачами вашего API.

## Как работает

`errgroup.WithContext` возвращает группу и контекст, который отменяется при первой ненулевой ошибке callback или при возврате `Wait`. `Go` добавляет функцию и запускает её; `Wait` ждёт все уже добавленные функции и возвращает первую сохранённую ошибку. Вызванные до возникновения ошибки задачи могут продолжить работу, поэтому callback должен уважать свой контекст. Если нужно ограничить число одновременно активных функций, вызовите `SetLimit(n)` до запуска работы. Следующий `Go` блокируется при заполненном лимите. `TryGo` вместо ожидания сообщает, удалось ли запустить функцию. Лимит нельзя менять, пока задачи активны.

Контекст из `WithContext` — это контекст группы, а не гарантированный итоговый код функции. `Wait` отменяет его и после успешного ожидания; поэтому проверяйте родительский `ctx`, если функция должна сообщить о внешней отмене даже для пустого набора задач. `SetLimit` ограничивает активные функции группы, но не задаёт отдельную очередь, вес ресурсов или приоритет отмены. Это не полноценный worker-pool с политикой результатов и backpressure; такие решения раскрывает будущая страница [«Параллельные шаблоны»](../patterns/concurrency-patterns.md).

`singleflight.Group.Do(key, fn)` обеспечивает, что при одинаковом ключе одновременно исполняется одна функция: остальные вызовы ждут её результат и получают признак `shared`. Это дедупликация работы «пока выполняется», а не кэш: после завершения следующий вызов снова запускает `fn`. Пакет не принимает `context.Context`. `Do` нельзя отменить со стороны ожидающего вызова; `DoChan` позволяет конкретному ожидающему перестать ждать через собственный `select`, но сама общая работа продолжится. Если callback захватывает контекст первого запроса, именно этот запрос фактически владеет общей работой; это нужно определить заранее, иначе его отмена повредит другим ожидающим.

`semaphore.Weighted` представляет ёмкость числом единиц ресурса. `Acquire(ctx, n)` ждёт доступные `n` единиц или отмену; только после успешного захвата вызывающая сторона обязана ровно один раз сделать `Release(n)`. Если запрошенный вес больше общей ёмкости, успешное получение невозможно и вызов ждёт отмены. В реализации `v0.22.0` ожидающие лежат в очереди: меньший запрос за большим не обгоняет его, даже если свободного веса уже достаточно для меньшего. Это уменьшает риск голодания крупного запроса, но создаёт head-of-line blocking. Порядок очереди и справедливость — свойство реализации этой версии, а не обещание произвольного семафора как общей идеи.

## Пример

```go
package parallel

import (
	"context"

	"golang.org/x/sync/errgroup"
)

func CheckHosts(ctx context.Context, hosts []string, check func(context.Context, string) error) error {
	if err := ctx.Err(); err != nil {
		return err
	}

	group, workCtx := errgroup.WithContext(ctx)
	group.SetLimit(4)
	for _, host := range hosts {
		group.Go(func() error { return check(workCtx, host) })
	}
	if err := group.Wait(); err != nil {
		return err
	}
	return ctx.Err()
}
```

Здесь фиксированный положительный лимит четыре ограничивает число активных проверок. `Go` блокирует отправителя новых задач, когда все места заняты, а `Wait` присоединяется ко всем добавленным функциям и возвращает первую ошибку. `workCtx` нужно передавать в блокирующие операции внутри `check`. После `Wait` проверяется исходный контекст: контекст группы отменяется при возврате `Wait` даже после успеха. Сам `errgroup` не задаёт admission policy для callback, ещё не начавших полезную работу; если их нужно пропустить после отмены, проверку перед пользовательским callback добавляет обёртка. Полный контракт такого случая находится в упражнении [«Пакет задач с errgroup»](/practice/errgroup-batch).

## Ошибки и ограничения

- Не ожидайте, что ошибка `errgroup` принудительно остановит callback. Она лишь отменяет производный контекст; блокирующая операция без поддержки отмены задержит `Wait`.
- Не считайте `SetLimit` очередью с отдельной ёмкостью ожидания: вызов `Go` блокирует отправителя задач, пока не освободится место.
- Не считайте `singleflight` кэшем или механизмом распределённой дедупликации. Его область — конкретная `Group` в одном процессе и только совпадающий ключ.
- Не связывайте все одинаковые запросы с контекстом случайного первого клиента без решения, кто владеет общей работой и что делать, когда этот клиент уходит.
- Не забывайте `Release` после успешного `Acquire`; освобождение лишнего веса вызывает panic. Используйте `defer` сразу после удачного захвата.
- Не выводите гарантии fairness из одного названия `semaphore`. Для `v0.22.0` цена защиты крупного waiter — ожидание позади него для меньших запросов.

При разборе зависания проверьте, кто блокируется внутри `Group.Go`, какое выполнение должно освободить лимит и реагирует ли оно на ошибку. Для семафора сравните запрошенный вес и очередь ожидающих; для singleflight проверьте ключ, длительность общей функции и контекст её фактического владельца. `errgroup` не отменяет необходимость явного join: `Wait` — та граница, после которой вызывающая функция знает, что запущенные callbacks вернулись.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Почему нельзя возвращать groupCtx.Err() после успешного group.Wait()?</summary>

Контекст, созданный `WithContext`, отменяется при первом возврате `Wait` независимо от того, была ли ошибка. Для внешней отмены после успешных задач проверяйте исходный родительский context. Senior follow-up: что должна вернуть операция, если parent отменился одновременно с последним успешным callback?

</details>

<details>
<summary>Когда вызовы singleflight с одним ключом выполнят callback дважды?</summary>

Одновременно выполняющиеся вызовы разделят работу, но вызов после удаления завершённой операции запустит новую. `singleflight` не хранит результат как cache. Senior follow-up: где разместить TTL, eviction и кэширование результата?

</details>

<details>
<summary>Почему справедливый порядок ожидания semaphore может задержать малый запрос?</summary>

Очередь не пропускает крупного первого ожидающего ради маленького запроса, поэтому крупный не голодает из-за бесконечных мелких захватов. Цена — блокировка меньших запросов при нехватке веса для head waiter. Senior follow-up: как head-of-line blocking отразится на latency разных классов нагрузки?

</details>
