# Модульные и интеграционные тесты

## Коротко

Модульный тест проверяет небольшую часть поведения при контролируемых зависимостях. Интеграционный тест проверяет, как несколько частей системы работают через реальную границу: HTTP, SQL-драйвер, файловую систему или очередь. Граница важнее названия: тест с фальшивой базой не становится интеграционным только из-за размера набора данных, а тест HTTP-обработчика через настоящий клиент уже проверяет больше, чем прямой вызов функции.

В Go тест находится рядом с пакетом в файле с суффиксом _test.go. Команда <code>go test ./...</code> обнаруживает и запускает тестовые функции вида <code>TestXxx(*testing.T)</code>.

## Как работает

Пакет <code>testing</code> предоставляет тесту контекст <code>*testing.T</code>: через <code>Error</code> и <code>Fatal</code> он сообщает неуспех, через <code>Run</code> запускает под-тест, через <code>Cleanup</code> освобождает ресурс после завершения теста. Таблица случаев делает контракт обозримым: вход, ожидаемый результат и имя под-теста находятся рядом. Указывайте в проверке фактическое и ожидаемое значение; сообщение «не совпало» без контекста увеличивает время диагностики.

Для модульного теста замените внешние зависимости на управляемые границы, если цель — проверить бизнес-правило при разных результатах зависимости. Не подменяйте объект, который и есть предмет проверки: собственный мок HTTP-клиента может подтвердить только ваше ожидание от мока. Интеграционный тест, напротив, должен включить реальный адаптер или протокол, поведение которого вы хотите проверить. Выбирайте наименьшую реальную границу, достаточную для вопроса: <code>httptest.NewServer</code> проверит маршрутизацию, кодирование и работу клиента без публичной сети; настоящий SQL-драйвер и изолированная база нужны, если проверяется SQL или транзакция.

Функции и ресурсы теста имеют срок жизни. Зарегистрируйте закрытие сервера через <code>defer</code> или <code>t.Cleanup</code>, чтобы оно сработало и при неуспехе. Не используйте общий изменяемый объект в тестах, которые выполняются через <code>t.Parallel</code>, без отдельной синхронизации. Под-тест, вызвавший <code>Parallel</code>, продолжится позже; это меняет расписание и требует проверить, что его данные не разделяются с соседями. Современная семантика переменных цикла помогает при захвате переменной, объявленной через <code>:=</code>, но не исправляет общий указатель, map или ресурс. Для деталей HTTP см. [клиенты и серверы net/http](../stdlib/net-http.md).

## Пример

Таблица ниже тестирует чистую функцию без сети и диска. Второй тест проходит через HTTP-клиент и сервер <code>httptest</code>: он остаётся быстрым и самодостаточным, но проверяет реальный обмен запросом и ответом.

~~~go
package ports

import (
	"errors"
	"net/http"
	"net/http/httptest"
	"strconv"
	"testing"
)

func parsePort(raw string) (int, error) {
	port, err := strconv.Atoi(raw)
	if err != nil {
		return 0, err
	}
	if port < 1 || port > 65535 {
		return 0, errors.New("port out of range")
	}
	return port, nil
}

func TestParsePort(t *testing.T) {
	cases := []struct {
		name    string
		input   string
		want    int
		wantErr bool
	}{
		{name: "minimum", input: "1", want: 1},
		{name: "maximum", input: "65535", want: 65535},
		{name: "zero", input: "0", wantErr: true},
		{name: "too large", input: "65536", wantErr: true},
		{name: "not a number", input: "abc", wantErr: true},
	}

	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			got, err := parsePort(tc.input)
			if (err != nil) != tc.wantErr {
				t.Fatalf("parsePort(%q) error = %v, wantErr %t", tc.input, err, tc.wantErr)
			}
			if err == nil && got != tc.want {
				t.Fatalf("parsePort(%q) = %d, want %d", tc.input, got, tc.want)
			}
		})
	}
}

func HealthHandler() http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusNoContent)
	})
	return mux
}

func TestHealthEndpoint(t *testing.T) {
	server := httptest.NewServer(HealthHandler())
	defer server.Close()

	response, err := server.Client().Get(server.URL + "/health")
	if err != nil {
		t.Fatal(err)
	}
	defer response.Body.Close()

	if response.StatusCode != http.StatusNoContent {
		t.Fatalf("status = %d, want %d", response.StatusCode, http.StatusNoContent)
	}
}
~~~

Первый тест фиксирует границы допустимого порта и отличает ошибочный ввод от корректного значения. Второй проходит через mux и HTTP-транспорт. Он не доказывает, что сервис развёрнут с правильной конфигурацией: такой вопрос требует отдельной проверки окружения и инфраструктурных интеграций.

## Ошибки и ограничения

- Не называйте тест unit-тестом, если он обращается к общей базе, публичной сети или случайному состоянию машины: он будет медленнее и менее воспроизводим.
- Не сравнивайте только код HTTP-ответа, если контракт включает заголовки, тело или закрытие ресурса.
- Не скрывайте проверяемые детали за универсальным мок-фреймворком: управляемая ручная заглушка часто точнее показывает ожидание.
- Не полагайтесь на порядок выполнения тестов. Каждый тест должен создавать нужное состояние сам и освобождать его.
- Не запускайте параллельно тесты, которые меняют общую директорию, переменные окружения или таблицу в общей базе.
- Не проверяйте одну и ту же деталь на каждом уровне. Модульный тест локализует правило; интеграционный тест подтверждает совместную работу выбранных компонентов.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Что делает тест интеграционным: объём кода или выбранная граница?</summary>

Выбранная граница. Маленький тест с настоящим SQL-драйвером проверяет интеграцию с базой; крупный тест с поддельными зависимостями может оставаться модульным. Углубление: какую именно гарантию даёт каждый слой и какой слой обнаружит ошибку wire-формата?

</details>

<details>
<summary>Почему httptest.NewServer и прямой вызов handler проверяют разное?</summary>

Прямой вызов проверяет обработчик; HTTP-клиент через тестовый сервер также проверяет маршрутизацию, request/response и транспортный путь. Углубление: когда достаточно httptest.NewRecorder, а когда нужен настоящий тестовый сервер?

</details>

<details>
<summary>Когда допустим t.Parallel?</summary>

Когда тест изолирует изменяемое состояние и освобождает собственные ресурсы; сам вызов не делает данные потокобезопасными. Углубление: как параллельное выполнение повлияет на фикстуры и время удержания соединений?

</details>

## Практика

Возьмите один контракт из проекта и разделите вопросы: что можно доказать модульным тестом с управляемой зависимостью, а что требует настоящего адаптера? Если для примера нужен HTTP, начните с <code>httptest</code>; не отправляйте публичный запрос из теста.
