# Профилирование и execution trace

## Коротко

Профиль суммирует конкретный вид события: CPU sample, живую память, все накопленные аллокации, блокировки или стеки горутин. Execution trace показывает временную последовательность событий планировщика, GC, системных вызовов и синхронизации. Сначала сформулируйте наблюдаемый симптом, затем соберите подходящий сигнал: pprof отвечает «где накапливается стоимость», trace — «что происходило и в каком порядке».

## Как работает

CPU-профиль семплирует выполнение; он помогает найти функции, которые тратят заметное процессорное время, но короткие редкие участки может не показать. Heap-профиль отражает живые объекты на момент последнего GC, а профиль <code>allocs</code> по умолчанию показывает суммарный объём выделений, включая уже собранные объекты. Они отвечают на разные вопросы: удержание памяти и churn нельзя оценивать по одной цифре. Block-профиль показывает места ожидания синхронизации, mutex-профиль — contention в критических секциях. Эти виды профилей требуют включить соответствующий сбор и его частоту; сбор и анализ добавляют нагрузку.

Профилирование бенчмарка можно начать командой <code>go test -run '^$' -bench '^BenchmarkMapLookup$' -cpuprofile cpu.out -memprofile mem.out</code>, затем открыть CPU-данные командой <code>go tool pprof cpu.out</code> и выбрать <code>top</code> или <code>list</code>. Трассу тестов собирает <code>go test -run '^TestPipeline$' -trace trace.out .</code>; <code>go tool trace trace.out</code> открывает анализ событий. Сопоставляйте сбор до и после изменения при одинаковой нагрузке и наборе данных. Не сравнивайте профиль тестового стенда с production-инцидентом так, будто это один сценарий.

В Go 1.27 профиль <code>goroutineleak</code> из <code>runtime/pprof</code> стал обычной возможностью стандартной библиотеки; отдельный experiment для него удалён. Запрос профиля запускает цикл GC с обнаружением утечек и затем фильтрует стеки. Это помогает находить горутины, навсегда заблокированные на каналах, блокирующем select и примитивах <code>sync</code>. Механизм опирается на reachability: если примитив достижим через глобальную переменную или runnable goroutine, leak может быть пропущен. Ожидания на нетиповом блокировании, например I/O или system call, также не входят в область обнаружения. Поэтому профиль дополняет тесты и обычный goroutine profile, а не гарантирует отсутствие любой утечки.

HTTP endpoint пакета <code>net/http/pprof</code> удобен для работающего процесса, но профили могут раскрыть имена функций, стеки и признаки внутреннего трафика. Подключайте его к закрытому диагностическому listener, ограничивайте доступ и собирайте данные на период, который нужен для вопроса. Детали управления памятью описаны также в статье [сборщик мусора](../runtime/garbage-collector.md).

## Пример

Функцию можно использовать для записи текстового снимка leak-профиля в выбранный диагностический writer. Запись профиля запускает механизм обнаружения; передавайте сюда контролируемый файл или защищённый поток, а не публичный HTTP-ответ.

~~~go
package diagnostics

import (
	"errors"
	"io"
	"runtime/pprof"
)

func writeGoroutineLeaks(dst io.Writer) error {
	profile := pprof.Lookup("goroutineleak")
	if profile == nil {
		return errors.New("goroutineleak profile is unavailable")
	}
	return profile.WriteTo(dst, 1)
}
~~~

В профиле важен стек блокировки и то, на каком примитиве ждёт горутина. Если профиль пуст, это говорит только, что данный механизм в момент снимка не нашёл утечки в обнаруживаемом им классе. Для ожиданий, задержек и загруженности планировщика соберите trace отдельно: трасса не заменяет profile, и profile не показывает полный порядок событий.

## Ошибки и ограничения

- Не выбирайте CPU-профиль для симптома задержки на mutex, пока не проверили block или mutex profile.
- Не путайте heap с allocs: первый отвечает про live set, второй — про накопленный churn.
- Не интерпретируйте профиль как точную бухгалтерию каждого вызова: CPU samples и heap snapshots имеют метод выборки и временную границу.
- Не собирайте профили непрерывно без бюджета на CPU, память, дисковое место и защиту данных.
- Не считайте отсутствие записи в goroutineleak профиле доказательством отсутствия утечки; глобальная достижимость и I/O ограничивают детектор.
- Не оставляйте <code>net/http/pprof</code> доступным из публичной сети без отдельного решения по аутентификации и сетевой границе.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Когда выбрать trace вместо CPU-профиля?</summary>

Когда нужно увидеть последовательность планирования, ожиданий, GC и системных событий; CPU-профиль агрегирует места использования процессора. Углубление: какой trace-интервал захватит событие, которое проявляется только при очереди?

</details>

<details>
<summary>Что измеряет allocs по умолчанию, и чем он отличается от heap?</summary>

Allocs показывает суммарные байты выделений с начала работы; heap по умолчанию показывает живые объекты на последнем GC. Углубление: какой профиль поможет объяснить высокий churn при стабильном live set?

</details>

<details>
<summary>Какие утечки может пропустить goroutineleak?</summary>

В частности, заблокированные горутины, чьи примитивы остаются достижимыми из глобальных переменных или runnable goroutines, и ожидания на неподдерживаемом I/O. Углубление: как ограничить владение примитивом, чтобы диагностика могла связать блокировку с завершённым жизненным циклом?

</details>

## Практика

Для [worker pool](/practice/worker-pool) соберите тестовую трассу только после того, как тест стал детерминированным, и используйте goroutineleak profile для диагностики навсегда заблокированных workers. Отдельно сформулируйте, какие классы блокировок этот профиль принципиально не может обнаружить.
