# Гонки и конкурентные тесты

## Коротко

Конкурентный код нужно проверять на две разные вещи: отсутствие гонок памяти и корректность поведения при разных допустимых расписаниях. Детектор гонок обнаруживает некоторые конкурентные конфликты доступа в реально исполненных путях; он не доказывает, что программа свободна от гонок. Тестовая практика с <code>testing/synctest</code> позволяет детерминированно управлять временем и ждать, пока горутины внутри изолированной области достигнут устойчивой блокировки.

## Как работает

Флаг <code>-race</code> включает динамический инструментатор. Он сообщает о конфликтующих обращениях к одной памяти, когда минимум одно обращение — запись, а обращения не упорядочены отношением happens-before. Утверждения о наблюдаемом результате остаются задачей теста: код может быть без гонки и всё равно терять сообщения, закрывать канал не тем владельцем или возвращаться раньше фоновой работы. Детектор увидит лишь пути, которые действительно выполнялись с инструментированной сборкой.

Сценарий гонки должен создавать реальное конкурентное выполнение. Тесты без <code>-race</code> иногда скрывают дефект порядком планировщика; тесты только с <code>-race</code> могут не попасть в редкую ветку. Поэтому сочетайте проверки инвариантов, тесты отмены и завершения, <code>go test -race</code>, а также повторение нужного пакета через <code>-count</code>. Модель happens-before и атомарность операций описаны в разделе [модели памяти](../concurrency/memory-model-atomic.md).

В Go 1.25 появилась стандартная <code>testing/synctest</code>; в Go 1.27.1 она остаётся частью стандартного инструментария тестов. <code>synctest.Test</code> помещает функцию и созданные внутри неё горутины в bubble с виртуальными часами. <code>synctest.Wait</code> ждёт, пока все остальные горутины bubble завершатся или устойчиво заблокируются на поддерживаемых синхронизациях, например канале bubble или <code>time.Sleep</code>. Когда bubble простаивает, виртуальное время может перейти к следующему таймеру. Это убирает реальные задержки и делает проверки порядка событий повторяемыми.

Bubble не является полной виртуальной машиной. Сетевой ввод-вывод, системные вызовы и захват mutex не считаются устойчивой блокировкой, потому что их может разблокировать внешнее событие. Не запускайте внутри неё тестовый под-процесс, публичный запрос или горутину, которой владеет другой тест. Создавайте все каналы, таймеры и WaitGroup внутри bubble и завершайте принадлежащие тесту горутины.

## Пример

Проверка подтверждает, что worker не завершился до сигнала и завершился после него. Канал <code>done</code> передаёт наблюдаемый факт тесту; общая переменная состояния не нужна.

~~~go
package worker

import (
	"testing"
	"testing/synctest"
)

func TestWorkerWaitsUntilReleased(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		release := make(chan struct{})
		done := make(chan struct{})

		go func() {
			<-release
			close(done)
		}()

		synctest.Wait()
		select {
		case <-done:
			t.Fatal("worker finished before release")
		default:
		}

		close(release)
		synctest.Wait()
		select {
		case <-done:
		default:
			t.Fatal("worker did not finish")
		}
	})
}
~~~

Первая точка ожидания даёт worker-у дойти до блокировки на <code>release</code>; вторая ждёт его завершения после закрытия канала. Здесь нет таймаута, сна реального времени или предположения о скорости машины. Такой тест полезен для воспроизведения конкретного порядка событий, но сам по себе не заменяет запуск всего конкурентного пакета с <code>-race</code>.

## Ошибки и ограничения

- Не трактуйте успешный <code>go test -race</code> как доказательство отсутствия гонки: он проверяет только исполненные варианты.
- Не считайте дедлок и утечку горутины гонкой данных. Для проверки владения, отмены и join нужны явные ожидания завершения.
- Не используйте <code>time.Sleep</code> в обычном тесте как доказательство, что другая горутина успела выполнить действие.
- Не читайте разделяемую переменную сразу после запуска горутины без канала, mutex или другого happens-before.
- Не вызывайте сетевой I/O внутри bubble в ожидании, что <code>Wait</code> определит его завершение.
- Не запускайте <code>t.Parallel</code> внутри функции bubble: API ограничивает операции над вложенным <code>*testing.T</code>.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Чем запуск с -race отличается от проверки всех возможных расписаний?</summary>

Детектор инструментирует только выполненные обращения и сообщает о найденных конфликтах памяти; полного перебора планировщика нет. Углубление: какую проверку семантики нужно добавить для потери или дублирования сообщения?

</details>

<details>
<summary>Что именно гарантирует synctest.Wait?</summary>

Он ждёт устойчивой блокировки остальных горутин своей bubble на поддерживаемых событиях; это не ожидание произвольного сетевого или системного ввода-вывода. Углубление: как моделировать сетевую границу, если она участвует в конкурентном контракте?

</details>

<details>
<summary>Почему проверка done через канал лучше, чем общая bool-переменная?</summary>

Закрытие и получение канала дают синхронизацию и создают наблюдаемый факт завершения без конкурентного чтения общей памяти. Углубление: где должен жить канал done и кто обязан его закрыть в worker pool?

</details>

## Практика

Запустите тесты отмены и завершения в [worker pool](/practice/worker-pool) и [pipeline](/practice/pipeline), затем повторите подходящую группу с <code>go test -race</code>. Утверждайте порядок только там, где его гарантирует контракт; общий порядок конкурентных результатов не фиксируйте.
