# Fuzz-тестирование

## Коротко

Fuzz-тест получает множество входов, часть которых генерирует coverage-guided движок. Его ценность зависит от свойства, которое проверяет тест: генерация мусора сама по себе не является спецификацией. В Go fuzz-тест объявляется функцией <code>FuzzXxx(*testing.F)</code>. Добавленные через <code>f.Add</code> начальные случаи запускаются и обычной командой <code>go test</code>; режим fuzzing ищет дополнительные входы и сохраняет воспроизводящий контрпример.

## Как работает

Fuzzing многократно вызывает функцию с новыми значениями, использует покрытие для выбора перспективных входов и сокращает найденный сбой до более простого примера. Когда вход ломает утверждение или вызывает panic, движок сохраняет его в corpus каталога <code>testdata/fuzz/&lt;имя&gt;</code>. Такой corpus становится regression-кейсом: обычный запуск теста воспроизводит его без продолжения поиска. Команда <code>go test -fuzz=FuzzParsePort -fuzztime=30s</code> запускает поиск для одной функции; без времени fuzzing продолжается до прерывания.

Начальные значения задают важные классы: пустой ввод, граничные числа, неверную кодировку или известный исторический дефект. Они помогают покрыть базовый контракт, но не ограничивают пространство поиска. Проверка должна формулировать инвариант или проверяемое отношение: например, успешный parse обязан вернуть значение в диапазоне, а повторный parse канонической записи должен дать то же число. Если проверять только отсутствие panic, тест пропустит неверный, но формально безопасный результат.

Fuzz-функция должна быть детерминированной и изолированной: не обращайтесь к публичной сети, текущему времени, случайному внешнему состоянию или общему файлу. Ограничивайте размер обработки, рекурсию и выделение памяти, если вход может заставить парсер тратить непропорциональные ресурсы. Не переносите тяжёлые фикстуры в тело callback без причины: они выполняются много раз. Для состояния, которое нельзя безопасно создавать повторно, сначала выделите чистую функцию и fuzz-тестируйте её контракт.

Обычный запуск воспроизводит seed corpus, а режим поиска использует несколько процессов/горутин в зависимости от окружения. Поэтому fuzz callback не должен менять package-global состояние и не должен полагаться на порядок вызовов. После найденного сбоя сначала изучите сокращённый вход, сохраните regression-файл и добавьте понятную проверку контракта. Подробнее об обычных тестах — в статье [модульные и интеграционные тесты](./unit-integration.md).

## Пример

Тест ниже утверждает два свойства парсера: принятый порт лежит в допустимом диапазоне, а его десятичная запись разбирается обратно в то же значение. Seed corpus включает важные границы и некорректные значения.

~~~go
package ports

import (
	"errors"
	"strconv"
	"testing"
)

func parsePort(raw string) (int, error) {
	port, err := strconv.Atoi(raw)
	if err != nil {
		return 0, err
	}
	if port < 1 || port > 65535 {
		return 0, errors.New("port out of range")
	}
	return port, nil
}

func FuzzParsePort(f *testing.F) {
	for _, seed := range []string{"", "1", "65535", "0", "65536", "abc"} {
		f.Add(seed)
	}

	f.Fuzz(func(t *testing.T, input string) {
		port, err := parsePort(input)
		if err != nil {
			return
		}
		if port < 1 || port > 65535 {
			t.Fatalf("accepted port outside range: %d", port)
		}

		roundTrip, roundErr := parsePort(strconv.Itoa(port))
		if roundErr != nil || roundTrip != port {
			t.Fatalf("canonical round trip = %d, %v; want %d, nil", roundTrip, roundErr, port)
		}
	})
}
~~~

Инвариант проверяет не каждую бизнес-ошибку парсера. Для точных ожиданий на известных значениях оставьте обычные табличные тесты; fuzzing расширяет входное пространство и ищет неожиданные взаимодействия между символами, длиной и границами числа.

## Ошибки и ограничения

- Не используйте fuzz-тест вместо спецификации: неверное ожидаемое свойство заставит движок искать именно неверный класс поведения.
- Не считайте прохождение текущего corpus доказательством корректности для всех входов.
- Не делайте callback зависимым от порядка, времени, сети или случайности; повтор входа должен воспроизводить тот же результат.
- Не оставляйте найденный corpus только в локальном рабочем каталоге: сохранённый seed нужен в репозитории и CI.
- Не запускайте поиск на неограниченном вводе, если парсер может выделить объём памяти, пропорциональный входу без допустимого предела.
- Не убирайте семантические проверки ради повышения coverage: покрытая ветка не равна проверенному контракту.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Что происходит с входом, который нашёл дефект?</summary>

Go сокращает его и сохраняет в fuzz corpus; обычный запуск затем повторяет его как регрессионный пример. Углубление: как превратить минимальный пример в сообщение, которое объясняет нарушенный контракт?

</details>

<details>
<summary>Почему проверка «функция не паникует» обычно слаба?</summary>

Она не замечает тихий неверный результат, выход за диапазон или нарушение отношения между вызовами. Углубление: сформулируйте инвариант для декодера, нормализатора или сериализатора.

</details>

<details>
<summary>Что fuzzing говорит о входах, для которых не найден дефект?</summary>

Только то, что пройденные входы и время поиска не нашли нарушения проверяемых свойств; это не доказательство для всего входного пространства. Углубление: какие seed-классы и ограничения ресурсов нужны вашему конкретному парсеру?

</details>

## Практика

Добавьте fuzz-тест к чистому парсеру или нормализатору из проекта. Опишите проверяемый инвариант до запуска, положите регрессионные corpus-файлы в репозиторий и запустите как обычные тесты, так и ограниченный поиск fuzzing.
