# Бенчмарки

## Коротко

Бенчмарк измеряет стоимость операции в контексте текущей машины, компилятора, входных данных и нагрузки. Он помогает сравнить два варианта при контролируемом эксперименте, но не задаёт универсальную константу производительности. В новых тестах используйте <code>b.Loop</code>: он управляет таймером и сохраняет живыми аргументы, результаты вызовов и присваиваемые переменные внутри точного тела <code>for b.Loop()</code>. Поэтому для обычного локального результата не нужен package-level sink.

## Как работает

Benchmark-функция имеет вид <code>BenchmarkXxx(*testing.B)</code>. Пакет testing подбирает количество итераций, чтобы длительность измерения была достаточно стабильной. В Go 1.24 добавлен <code>B.Loop</code>, и в Go 1.27.1 он доступен для новых бенчмарков. Подготовьте fixture до цикла: первая проверка таймера начинает измерение, а когда цикл завершён, оно останавливается. В точной форме <code>for b.Loop()</code> компилятор автоматически сохраняет живыми аргументы и результаты вызовов, а также присваиваемые переменные внутри тела; поэтому локальный результат lookup не исчезнет при оптимизации. Эта защита не распространяется на строки вне тела цикла. Не оборачивайте <code>b.Loop</code> ещё и ручным циклом по <code>b.N</code>.

Граница измерения должна совпадать с вопросом. Если нужно сравнить алгоритм на готовом срезе, создайте срез до цикла и измеряйте алгоритм; если создание данных входит в рабочий контракт, включите его явно. Вынос подготовительной работы может многократно изменить итог. У старого цикла по <code>b.N</code> нет автоматической защиты <code>B.Loop</code>: если результат операции иначе нигде не используется, компилятор может удалить работу, поэтому примените наблюдаемое использование или внешний sink. Запись в sink сама входит в измеряемую операцию и может исказить микробенчмарк. Результат или работа вне точного тела <code>b.Loop</code> не защищены этим механизмом; внешний sink сохраняет значение, но не включает setup или cleanup в таймер. Проверку корректности результата держите в обычном тесте или отдельно от измеряемого пути.

Запустите узкий тестовый набор без обычных тестов и сохраните несколько измерений: <code>go test -run '^$' -bench '^BenchmarkMapLookup$' -benchmem -count=10 .</code>. Флаг <code>-benchmem</code> показывает выделения и байты на операцию. Сравнивайте варианты на одном toolchain, одной машине, с одинаковым вводом и параметрами. Разброс, температура, параллельная нагрузка и профилировщик могут менять цифры. Инструмент <code>benchstat</code> полезен для статистического сравнения повторов; это отдельный инструмент, его не требуется добавлять в проект. Об аллокациях и расположении данных см. [память и layout объектов](../runtime/allocations-layout.md).

## Пример

Карта и ключ строятся до цикла. Бенчмарк измеряет lookup, оставляя результат локальной переменной в защищённом теле; на каждой итерации нет записи в глобальный sink.

~~~go
package cache

import "testing"

func BenchmarkMapLookup(b *testing.B) {
	entries := map[string]string{
		"user:42": "found",
		"user:43": "other",
	}
	key := "user:42"
	b.ReportAllocs()

	for b.Loop() {
		result := entries[key]
		_ = result
	}
}
~~~

Присваиваемая переменная <code>result</code> и результат lookup находятся внутри точного тела <code>b.Loop</code>, поэтому текущий toolchain сохраняет их живыми автоматически. После проверки корректности обычным тестом запускайте только этот benchmark и фиксируйте вывод целиком вместе с версией Go и условиями машины. Для сравнения двух реализаций меняйте только реализацию; если одновременно меняется fixture, рабочий каталог и компилятор, причина разницы остаётся неизвестной.

## Ошибки и ограничения

- Не делайте вывод о приложении из микробенчмарка одной операции без оценки реального профиля нагрузки.
- Не смешивайте подготовку и измерение, если не можете объяснить, почему setup входит в контракт.
- Не используйте ручное чтение <code>b.N</code> вместе с <code>b.Loop</code>.
- Не переносите измеряемое выражение за пределы точного тела <code>for b.Loop()</code>: автоудержание результата действует только внутри него, а setup до цикла исключён из таймера.
- В цикле <code>b.N</code> результат, который иначе нигде не используется, может быть оптимизирован; для такого legacy-бенчмарка используйте наблюдаемый результат или внешний sink и учитывайте цену его записи.
- Не сравнивайте одну выборку с другой после смены версии Go, частоты процессора или параметров GC.
- Не запускайте профилировщик во время финального точного сравнения: его накладные расходы меняют измеряемую систему.

## Самопроверка

Разверните каждый вопрос после самостоятельного ответа.

<details>
<summary>Что входит во время измерения при b.Loop?</summary>

Только тело цикла; setup до первого вызова и cleanup после выхода не учитываются. Внутри точной формы <code>for b.Loop()</code> присваиваемые переменные и результаты вызовов сохраняются живыми. Углубление: когда для старого цикла <code>b.N</code> нужен внешний sink и как его запись меняет измерение?

</details>

<details>
<summary>Почему абсолютное ns/op нельзя считать обещанием для каждого запуска?</summary>

На результат влияют машина, toolchain, нагрузка, состояние CPU и статистический разброс. Углубление: как организовать сравнение до и после изменения так, чтобы отделить сигнал от шума?

</details>

<details>
<summary>Когда нужен benchstat?</summary>

Когда нужно сравнить несколько повторных измерений и оценить, превышает ли разница обычный разброс. Углубление: какие условия должны совпадать у двух наборов перед статистическим сравнением?

</details>

## Практика

Измерьте упражнение [«Сборка строки»](/practice/allocations) через <code>-benchmem</code>. Сначала проверьте равенство результата, затем сравните несколько повторов без утверждения об абсолютном выигрыше на любой машине.
