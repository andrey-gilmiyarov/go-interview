# Топики, партиции и журнал

## Коротко

Kafka хранит записи в разделённых на партиции журналах. Ключ сообщения помогает клиенту выбрать партицию, а порядок существует только внутри одной партиции; сначала договоритесь о ключе и числе партиций, затем обсуждайте порядок событий заказа. Compaction — фоновое хранение последнего состояния по ключу, а не немедленное удаление дублей.

## Как работает

Топик — имя потока, разделённого на одну или несколько партиций. Каждая партиция — упорядоченный append-only журнал с собственными offsets. Offset обозначает позицию в одной партиции, а не глобальный номер сообщения в кластере. Одинаковый номер offset может встречаться в разных партициях.

Запись состоит как минимум из key и value; client API также передаёт заголовки и timestamp. Брокер не знает, что ключом является номер заказа и что два сообщения с одинаковым value означают повтор. Producer/client выбирает партицию: явным назначением либо стратегией partitioner. Если один и тот же ключ стабильно направляется в одну партицию, порядок записей этого ключа можно читать в порядке журнала. Между партициями общего порядка нет. Изменение числа партиций может изменить результат хеширования ключа и распределить последующие события существующего заказа в другую партицию. Такой переход требует отдельного плана, если потребителю нужен порядок на уровне заказа.

При политике retention delete Kafka удаляет целые сегменты по временным или размерным порогам; это не таймер на каждую запись. При compaction cleaner в фоне удаляет устаревшие записи с тем же key, оставляя финальное состояние. Null value с key — tombstone; маркер удаления также хранится ограниченное время, затем может быть очищен. Чистка не обязана завершиться сразу после записи нового значения. Offset не перенумеровывается, поэтому после compaction читающий клиент может увидеть пропуски в наблюдаемой последовательности offsets. Компактированный топик нельзя использовать как механизм оперативной дедупликации обработки.

Лабораторный контракт заказа строже многих production JSON-контрактов: `event_id` и `order_id` непустые, поддерживается только `order.created` версии 1 с положительным `amount_cents`, неизвестные поля и лишний JSON после объекта отклоняются. Новое поле нельзя объявить обратно совместимым без изменения decoder и согласованного выпуска producer/consumer. Дата проверки документации: 2026-09-29; Kafka 4.3.1 рассматривается как основная версия, 3.9.2 — как версия сравнения.

## Ошибки и ограничения

- Нельзя делать вывод о глобальном порядке по одному offset: позиции независимы для каждой партиции.
- Увеличение числа партиций меняет область параллелизма и может изменить mapping key → partition у partitioner.
- Один популярный ключ концентрирует нагрузку на одной партиции; случайный ключ улучшает распределение, но ломает порядок на уровне заказа.
- Compaction асинхронна и оставляет прежние offsets; увидеть пропуски — не признак порчи журнала.
- Retention удаляет данные по сегментам. Срок хранения должен превышать максимальный согласованный период восстановления потребителя.
- Tombstone — значение null с key, а не JSON-текст `null`; срок хранения маркера ограничивает медленный bootstrap.

## Самопроверка

Разверните ответ после самостоятельной попытки.

<details>
<summary>Какая гарантия порядка действует для двух событий с ключом одного заказа?</summary>

Они могут быть прочитаны в порядке записей, только если producer направляет их в одну и ту же партицию. Порядка между двумя партициями или двумя топиками Kafka не обещает. Ответ зависит от конкретного partitioner и способа назначения партиции.

</details>

<details>
<summary>Что доказывает пропуск offsets в compacted topic?</summary>

Сам по себе пропуск не доказывает потерю записи: cleaner удаляет старые записи, но сохраняет offsets оставшихся позиций. Потребитель должен продолжать чтение с позиции журнала, а не предполагать, что видимые номера обязаны идти подряд.

</details>

<details>
<summary>Решение: после добавления партиций старые и новые события одного заказа оказались в разных партициях. Что изменить?</summary>

Не склеивать offsets между партициями и не утверждать, что новый consumer восстановит единый порядок. Увеличение числа партиций способно сменить mapping ключа у hash-partitioner. До изменения нужно выбрать миграционный контракт: например, остановить и переключить producer вместе с читателем, записать версию маршрутизации, либо ввести новую тему и контролируемо перенести поток. После изменения проверить, что для одного заказа события не обрабатываются одновременно из старой и новой партиций. Дедупликация по event_id не восстанавливает порядок.

</details>
