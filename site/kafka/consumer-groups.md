# Consumer groups

## Коротко

Consumer group распределяет партиции подписанных топиков между участниками с одним group ID. Внутри группы у партиции есть один активный владелец в назначении; дополнительный consumer не увеличит параллелизм, если партиций меньше, чем участников. Rebalance меняет назначение, но не блокирует уже начавшиеся внешние операции старого участника.

## Как работает

Coordinator хранит membership группы и committed offsets; выбранный protocol определяет, как вычисляется и распространяется assignment. Когда consumer присоединяется, уходит, теряет heartbeat или меняется подписка/число партиций, группа запускает rebalance. При простом примере из четырёх партиций и двух consumers каждой стороне достанется часть работы. При шести consumers два останутся без партиций, пока число партиций не увеличится.

Kafka 3.9 включала KIP-848 как early-access направление, а Kafka 4.0 вывела новый Consumer rebalance protocol в GA. В Kafka 4.3 новый протокол активирует клиентская конфигурация; наличие поддержки на брокере само по себе не меняет protocol существующей группы. Лаборатория на обеих версиях оставляет традиционные balancers, чтобы сравнивать назначение и lifecycle без opt-in протокола.

В pinned Go client важно различать две сущности с похожими именами. GroupProtocol() в franz-go v1.22.1 задаёт старый тип JoinGroup protocol и не означает Java-настройку group.protocol=classic|consumer. Для KIP-848 используется ServerSideBalancer(); она требует Kafka 4.0+ и совместимый RangeBalancer или StickyBalancer, иначе клиент переходит на classic protocol. Из-за прежнего STALE_MEMBER_EPOCH поведения документация pinned client рекомендует Kafka 4.3+ для этого нового пути. Лаборатория не включает эту опцию. Не переносите property names из Java API в Go.

Assignment контролирует только чтение из Kafka. Если старый consumer завис в HTTP или SQL-запросе, coordinator может назначить партицию новому участнику; старый запрос способен завершиться уже после смены assignment. Поэтому внешний эффект защищают event ID, транзакцией или fencing-механизмом приложения. Факт «у нас один активный владелец партиции» не является блокировкой в PostgreSQL.

## Ошибки и ограничения

- Число активных обработчиков одной группы ограничено числом назначенных партиций, а не числом процессов.
- Разные приложения, которые должны прочитать каждую запись независимо, используют разные group ID.
- Rebalance — нормальная передача назначения, а не подтверждение, что старый внешний запрос завершён.
- Длинная обработка в poll loop может мешать обслуживанию группы; параллелизм требует собственной схемы завершения, контроля in-flight и корректного commit.
- group.protocol из Java client и GroupProtocol() из pinned kgo не являются эквивалентными именами API.
- Переключение protocol требует совместимых broker, client и balancer опций; сначала проверяют целевые версии и поддержку в установленном теге клиента.

## Самопроверка

<details>
<summary>Что будет при шести consumers в одной группе и четырёх партициях?</summary>

Одновременно назначить Kafka может не более четырёх партиций внутри этой группы, поэтому как минимум два участника останутся без назначенной партиции. Это не мешает другой группе независимо прочитать те же записи.

</details>

<details>
<summary>Почему старый consumer может продолжить внешний запрос после rebalance?</summary>

Rebalance меняет membership и назначение на стороне Kafka, но не отменяет уже отправленный SQL/HTTP запрос. Новый владелец может начать обработку, пока старый эффект ещё завершается. Для внешней системы нужен собственный механизм идемпотентности или fencing.

</details>

## Практика

В [лаборатории](/kafka/lab) запустите один consumer и второй экземпляр с тем же group ID; посмотрите выдачу партиций и поведение после остановки экземпляра. Команды, topics и группы перечислены в README. Тест не должен опираться на фиксированную последовательность имён consumers: assignment зависит от protocol и balancer.

<details>
<summary>Решение: второй consumer поднят, но его вывод пустой. Это зависание?</summary>

Не обязательно. Если первый уже владеет единственной партицией тестового топика, второй остаётся участником группы без назначенной работы. Сначала проверьте число партиций и assignment группы, затем остановите владельца и дождитесь rebalance. Для реальной системы увеличение partitions требует отдельной оценки влияния на key mapping и порядок.

</details>
