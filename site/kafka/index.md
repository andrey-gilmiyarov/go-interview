# Kafka

Раздел помогает пройти путь от записи заказа в Kafka до безопасной обработки повторов в PostgreSQL. Главная мысль сквозного примера: ключ `order_id` задаёт локальную область порядка, а `event_id` отличает конкретное бизнес-событие от повторной попытки доставки.

Проверка первичной документации выполнена 2026-09-29. Материалы ориентированы на брокер Apache Kafka 4.3.1; совместимые темы сверяются также с 3.9.2. Лаборатория использует Go-клиент `franz-go v1.22.1`. Это три разных версии: брокера, клиента и протокольных возможностей, согласуемых между ними. Ссылка `/43/` ведёт к документации ветки Kafka 4.3, а не заменяет точную версию образа в Compose.

## Маршрут

1. [Топики, партиции и журнал](/kafka/topics-partitions) — выбрать ключ и понять, где Kafka сохраняет порядок.
2. [Репликация и запись](/kafka/replication) — разобрать leader, ISR, `acks=all`, `min.insync.replicas` и отказ брокера.
3. [Consumer groups](/kafka/consumer-groups) — связать число партиций, число потребителей и rebalance.
4. [Offsets и повторная доставка](/kafka/offsets-delivery) — расположить обработку, внешний эффект и commit offset в безопасном порядке.
5. [Идемпотентность и транзакции Kafka](/kafka/transactions) — ограничить exactly-once границей Kafka-to-Kafka.
6. [Дедупликация и внешние эффекты](/kafka/deduplication) — связать уникальный ID события и изменение PostgreSQL одной транзакцией.
7. [Transactional outbox](/kafka/outbox) — атомарно сохранить заказ и намерение опубликовать событие.
8. [Обработка сбоев](/kafka/failures) — выбрать поведение для временной ошибки, poison message, DLQ и lag.

Для упражнений открывайте [локальную лабораторию](/kafka/lab) после глав 1–4. Она запускается отдельно от самого справочника: Docker нужен для инфраструктуры, Go-программы выполняются на хосте. [README лаборатории](./lab) — единственный источник точных команд, портов, переменных и сценариев; страница лаборатории включает его без второй копии.

## Сквозной пример

Каждое сообщение — отдельное событие. `order_id` используется как ключ Kafka, чтобы выбранный partitioner направлял события одного заказа в ту же партицию; `event_id` остаётся стабильным при повторной доставке того же события.

```json
{
  "event_id": "evt-01",
  "order_id": "ord-42",
  "type": "order.created",
  "version": 1,
  "amount_cents": 12500
}
```

После создания заказа в рабочем коде лаборатории создаётся только событие `order.created`: контракт версии 1 проверяет этот тип, положительную сумму и отклоняет неизвестные поля. `order.paid` и `order.cancelled` ниже — будущие события в концептуальной модели, а не допустимые команды текущего producer. Kafka гарантирует порядок только внутри одной партиции и только относительно порядка записей в ней. Она не задаёт общий порядок между партициями или темами, а клиентская стратегия выбора партиции — часть этого контракта. Увеличение числа партиций может изменить распределение ключей у partitioner, который пересчитывает хеш по новому числу партиций.

`event_id` — идентификатор события, а не идентификатор попытки. Если producer повторно отправляет то же событие, он должен сохранять `event_id`; новое бизнес-событие получает новый ID, даже если тип и заказ совпадают.

## Версии и клиент

У Kafka есть отдельные роли данных и метаданных. Брокеры хранят журналы партиций и обслуживают produce/fetch; controller координирует состояние кластера и лидерство. ZooKeeper в старом режиме хранит координационные метаданные, но не события. В KRaft для метаданных используется отдельный Raft-quorum контроллеров; репликация журналов партиций между брокерами остаётся отдельным механизмом. Kafka 3.9 умеет работать как с ZooKeeper, так и с KRaft; в 4.x ZooKeeper mode удалён. Переход существующего ZooKeeper-кластера к версии 4 требует отдельного плана миграции через поддерживаемую промежуточную версию, а не простого переключения конфигурации. В локальной лаборатории 3.9.2 запускается как учебная ZooKeeper-среда, 4.3.1 — как KRaft.

В Kafka 3.9 новый consumer rebalance protocol KIP-848 оставался ранним доступом; в Kafka 4.0 он получил статус GA, а в 4.3 его можно включать клиентом. Лаборатория намеренно использует традиционные balancers. В `franz-go v1.22.1` `GroupProtocol()` задаёт старый тип JoinGroup protocol, а не аналог настройки Java-клиента `group.protocol`; новый broker-side balancing включается отдельной опцией `ServerSideBalancer()` с совместимым balancer и брокером. Не переносите имена или значения Java-настроек напрямую в Go API.

Примеры написаны только для выбранного `franz-go`. Для сравнения: `confluent-kafka-go` — Go-обёртка над C-библиотекой `librdkafka` с другим профилем сборки и операционных зависимостей. Это сравнение клиента и способа связывания библиотек, а не утверждение о взаимозаменяемости API или о «лучшем» клиенте.

Учебная среда использует PLAINTEXT внутри локальной Docker network, а опубликованные порты брокеров привязаны к loopback. Это не конфигурация для общей сети или production. В реальном кластере настраивают TLS, SASL и ACL, не помещая рабочие секреты в исходный код, Markdown или общие Compose-файлы.

## Источники и границы

Версионные отличия в главах указаны только там, где они меняют механизм или эксплуатационный вывод. Producer- и consumer-настройки из документации Kafka описывают клиентские протоколы и Java API; в лаборатории им соответствуют конкретные вызовы `franz-go`, показанные из исходных файлов Go, а не механическая подстановка Java-имён.
