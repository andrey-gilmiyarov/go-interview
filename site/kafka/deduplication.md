# Дедупликация и внешние эффекты

## Коротко

Consumer может получить одно Kafka-событие повторно, поэтому внешний бизнес-эффект проектируют идемпотентным. Для эффекта в PostgreSQL положите event_id в таблицу inbox с уникальным ограничением и изменяйте бизнес-строку в одной DB-транзакции. Затем commit offset Kafka: порядок оставляет окно повтора, которое закрывается уникальностью inbox.

## Как работает

event_id должен идентифицировать бизнес-событие, а не конкретное чтение consumer-а. Один заказ может иметь несколько различных событий с разными event_id; одно событие может быть доставлено несколько раз с тем же ID. Kafka key order_id нужен для маршрутизации и локального порядка, но не заменяет уникальность события.

В схеме лаборатории уникальный ключ — пара `(consumer_id, event_id)`. `consumer_id` — стабильное имя логического эффекта (например, `order-totals-v1`), а не group member, hostname или конкретный процесс. Если сменить это имя без миграции inbox, тот же event_id станет новым для дедупликации и эффект применится снова.

Транзакционный алгоритм получателя:

1. Начать PostgreSQL transaction.
2. Вставить пару `(consumer_id, event_id)` через `INSERT ... ON CONFLICT DO NOTHING` и проверить, создала ли команда строку.
3. Если вставка создала строку, применить бизнес-изменение заказа в той же транзакции. Если строка уже была, не выполнять эффект повторно.
4. Commit DB transaction.
5. Подтвердить Kafka offset.

Если две горутины или два сервиса одновременно получают тот же ID, уникальный индекс сериализует конфликтующие вставки. Один transaction вставляет inbox record и меняет заказ; конкурентный повтор после разрешения конфликта видит уже существующий ID и не выполняет изменение. Важно, чтобы приложение принимало решение по результату insert в этой же DB transaction, а не делало отдельный SELECT, затем незащищённый INSERT.

Падение после commit базы, но до Kafka commit означает повтор сообщения. Inbox row уже сохранён, поэтому повтор безопасно пропускает бизнес-изменение и подтверждает Kafka позицию. Падение до DB commit откатывает обе DB-операции, после чего повтор может применить их заново. Именно атомарное объединение inbox и результата защищает от окна между двумя запросами к PostgreSQL.

Это exactly-once бизнес-эффект только в пределах этой базы, уникального event_id и времени хранения inbox. Удаление inbox row, изменение правил идентичности, другие независимые consumer group или внешняя система снова создают окно. Вызов внешнего HTTP API нельзя отменить DB rollback-ом; передайте downstream idempotency key, используйте отдельную outbox/saga границу или предусмотрите компенсацию.

## Ошибки и ограничения

- Уникальность нужна по стабильному event_id, не по Kafka offset или ID попытки.
- Inbox insert и бизнес update должны commit-иться одной DB transaction.
- `consumer_id` входит в область уникальности; его переименование без переноса inbox меняет семантику дедупликации.
- Если insert использует ON CONFLICT DO UPDATE, повтор может незаметно повторить или изменить состояние; для маркера обработки часто безопаснее отличить «вставлено» от «уже было».
- Отдельный SELECT перед INSERT под конкурентной нагрузкой создаёт race.
- Commit offset до commit DB оставляет путь к потере бизнес-эффекта.
- Дедупликация PostgreSQL не делает HTTP-вызов атомарным с этой БД.

## Самопроверка

<details>
<summary>Почему одного уникального inbox.event_id недостаточно, если обновление заказа выполняется отдельной транзакцией?</summary>

Падение между inbox commit и обновлением заказа оставит событие отмеченным обработанным, хотя бизнес-эффект не состоялся. Маркер и изменение должны входить в одну PostgreSQL transaction.

</details>

<details>
<summary>Что произойдёт, если два consumer-а одновременно вставят один event_id?</summary>

Уникальное ограничение разрешит только одну запись inbox. Конкурентная транзакция дождётся результата блокирующего конфликта и не применит бизнес-изменение, если обработчик привязывает эффект к факту успешного insert.

</details>

## Практика

Запустите consumer сценарий из [лаборатории](/kafka/lab) дважды на одном event_id и повторите его конкурентно. Проверьте число строк inbox и бизнес-эффект; затем используйте failpoint после DB apply и до Kafka commit. Не меняйте event_id между повтором, иначе это новое событие.

<details>
<summary>Решение: PostgreSQL уже применил заказ, а consumer упал до commit Kafka. Как пройти повтор?</summary>

Повторно начать DB transaction, попробовать вставить прежний event_id и увидеть конфликт. Не обновлять заказ повторно, успешно завершить DB transaction, затем commit Kafka offset. Если бизнес-изменение и inbox не были в одной транзакции, повтор не может надёжно определить, состоялся ли эффект.

</details>
