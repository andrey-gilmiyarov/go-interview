# Репликация и запись

## Коротко

У партиции есть лидер и реплики; ISR — реплики, которые сейчас считаются достаточно синхронизированными с лидером. При `acks=all` producer ждёт подтверждения от всех текущих ISR. `min.insync.replicas` задаёт нижний порог ISR для такой записи, а не число подтверждений, которое Kafka выбирает из ISR.

## Как работает

Клиент пишет в leader partition. Реплики забирают записи у лидера; состав in-sync replicas может меняться при отставании или восстановлении брокеров. Для `acks=all` лидер завершает запись после подтверждения от текущего ISR. `min.insync.replicas` проверяется как порог при `acks=all`: если число ISR меньше него, брокер откажет в записи. Если ISR равен трём и порог равен двум, это не означает, что достаточно двух acknowledgements: пока все три реплики входят в ISR, запись ждёт все три; после выпадения одной — две. Kafka 4.3 документация отдельно описывает ограничения этой формулировки при включённой функции Eligible Leader Replicas.

Учебный расчёт: replication factor 3, `min.insync.replicas=2`, producer ждёт all ISR. При трёх живых синхронных репликах запись ждёт три подтверждения. При отказе одного брокера оставшиеся две образуют допустимый ISR, и запись может продолжиться. Если ISR сожмётся до одной, новая запись с `acks=all` будет отклонена. Это сознательный выбор: остановить приём новых записей, пока кластер не восстановит порог, вместо того чтобы незаметно ослабить выбранную гарантию.

Producer timeout или закрытие соединения не доказывают, что запись отсутствует: Kafka могла принять её, а ответ мог потеряться. При прикладном retry сохраняйте исходный event_id и проектируйте downstream обработку на повтор. Это иное окно, чем автоматический protocol retry идемпотентного producer.

В `franz-go v1.22.1` нельзя считать контекст `ProduceSync` жёстким deadline для уже отправленной idempotent-записи: ожидание может продолжиться ради корректности sequence state. `RecordDeliveryTimeout` также не является безусловным wall-clock пределом. В лаборатории ограничено ожидание приложения через асинхронный delivery callback; если этот бюджет истёк, исход доставки остаётся неизвестным, а не автоматически «запись отсутствует».

С Kafka 4.0 доступен Eligible Leader Replicas (ELR); на новых кластерах он включён по умолчанию начиная с 4.1. При строгом правиле min ISR некоторые реплики вне обычного ISR могут попасть в ELR и стать допустимым лидером без потери подтверждённого high watermark. Поэтому в 4.3 нельзя описывать каждый election исключительно как «только ISR»; проверяйте состояние ELR и параметры кластера. ELR — отдельная политика выборов лидера, а не unclean election. В 3.9 этой функции нет. Изменение topic/cluster `min.insync.replicas` влияет на ELR state, поэтому это операционная настройка, а не переключатель для эксперимента на работающем кластере.

Параметры producer-конфигурации в документации Kafka описывают Java client. В Go-лаборатории подтверждение выбирается через API pinned `franz-go`, показанный в файле producer; название или тип из Java properties не следует копировать как Go-флаг. Дата проверки источников — 2026-09-29.

## Ошибки и ограничения

- Нельзя заменить `acks=all` фразой «подтверждает большинство»: Kafka использует динамический ISR, а не фиксированное большинство из replication factor.
- `min.insync.replicas=2` не означает два подтверждения, когда в ISR три реплики.
- Одноузловой broker может принять запись, но не демонстрирует защиту от отказа узла.
- Высокая надёжность записи не покрывает удаление топика, повреждение всех копий, ошибочный ключ или внешнюю БД.
- В Kafka 4.3 при ELR нужно отличать допустимого отстающего лидера от unclean election; это разные механизмы и условия выбора.
- При нехватке ISR отказ producer — сигнал о потере требуемой доступности записи, а не повод бесконечно игнорировать ошибку.

## Самопроверка

<details>
<summary>В RF=3, если ISR содержит три реплики, `acks=all` и min ISR равен двум, сколько реплик должны подтвердить запись?</summary>

Все три участника текущего ISR. Значение min ISR — проверка минимально допустимого размера ISR, а не количество acknowledgements, которое берётся из полного набора.

</details>

<details>
<summary>Что произойдёт, если ISR станет меньше min ISR?</summary>

При `acks=all` новая запись не пройдёт порог и producer получит ошибку. Так настройка предпочитает временно отказаться от записи с недостаточным числом актуальных копий. Это не означает, что уже подтверждённые записи становятся автоматически доступными при любом отказе.

</details>

<details>
<summary>Решение: что говорит модель, если ISR упал с трёх реплик до двух, а затем до одной?</summary>

При ISR из двух реплик запись может пройти, ожидая обе; при ISR из одной Kafka должна отклонить запись `acks=all` ниже min ISR=2. Это рассуждение о пороге отдельной партиции. В учебном трёхузловом compose broker-ы совмещены с controller-ами, поэтому остановка двух узлов также теряет KRaft controller quorum и не изолирует один только min ISR. Лаборатория проверяет один broker failover; для восстановления дождитесь возврата реплики в ISR, а не только запуска контейнера.

</details>
