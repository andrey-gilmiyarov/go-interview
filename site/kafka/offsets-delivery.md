# Offsets и повторная доставка

## Коротко

Порядок двух операций определяет базовую семантику consumer. Если сначала сделать внешний эффект, а потом commit offset, падение между ними приводит к повторной обработке; если сначала commit, можно потерять эффект. Для учебной схемы выбираем повтор вместо потери и делаем бизнес-операцию идемпотентной.

## Как работает

Consumer получает записи своей партиции и хранит committed offset отдельно для каждой пары group/topic/partition. Commit задаёт позицию, с которой группа может продолжить; принятая Kafka convention — записать следующую позицию после успешно обработанного record. В компактированном топике между полученными records могут быть gaps, поэтому приложение не должно вычислять «предыдущий offset» вычитанием единицы.

Разберём порядок «обработать → commit». Consumer получил заказ на offset 18, записал результат в базу, но процесс упал до commit позиции 19. После restart группа может снова получить запись 18. Это at-least-once доставка: эффект может повториться, но запись не потеряется из-за commit, выполненного заранее. Повтор обрабатывается тем же event_id. При порядке «commit → обработать» падение после commit, но до записи результата приводит к пропуску эффекта.

Группа коммитит позицию, а не доказательство того, что внешний эффект точно произошёл. Для одного consumer можно дождаться завершения эффекта и затем commit; для параллельной обработки внутри одной партиции нужен contiguous completed prefix. Если offsets 10 и 11 выполняются в отдельных goroutine, но 11 завершился раньше 10, нельзя commit следующую позицию после 11: при падении запись 10 будет пропущена. Партиции независимы, поэтому при нескольких партициях можно продвигать подтверждённый prefix каждой отдельно.

Rebalance может отдать партицию другому участнику, а commit старого клиента может не пройти или прийти после изменений в группе. Новая группа иногда начинает с позиции, выбранной reset policy, если у неё ещё нет committed offset. Проверяйте это значение явно для новых групп: «начать с начала» и «читать только новое» — разные бизнес-решения. Ключевой порядок остаётся per partition, не глобальный.

## Ошибки и ограничения

- Commit до бизнес-эффекта даёт at-most-once поведение при падении между этими действиями.
- Эффект до commit допускает повтор; без идемпотентности внешняя БД может применить заказ второй раз.
- Нельзя commit более поздний offset из той же партиции, пока есть незавершённая более ранняя запись.
- Commit offset одной партиции не продвигает позицию остальных partitions.
- Повтор после rebalance возможен даже если старая goroutine ещё не получила сигнал остановки.
- DLQ тоже внешний эффект: его отправка и commit входного offset имеют собственное окно повторной доставки.

## Самопроверка

<details>
<summary>Почему effect → commit называют at-least-once, а не exactly-once?</summary>

После завершения эффекта процесс может упасть до подтверждения позиции. Kafka повторно отдаст запись, поэтому эффект может быть вызван ещё раз. Идемпотентный receiver может сделать наблюдаемый результат однократным, но транспорт по-прежнему допускает повтор.

</details>

<details>
<summary>Offsets 10 и 11 обрабатываются конкурентно; 11 закончился первым. Какую позицию безопасно подтвердить?</summary>

Нельзя перескочить завершённый только offset 11, пока результат offset 10 неизвестен. Нужно дождаться 10 и после непрерывного завершённого префикса подтвердить следующую позицию после последнего последовательного record. Коммит для другой партиции при этом может продвигаться независимо.

</details>

<details>
<summary>Решение: запись о заказе появилась в PostgreSQL, затем consumer упал до Kafka commit. Что должно произойти?</summary>

После восстановления Kafka может доставить тот же offset повторно. У события сохраняется исходный event_id; consumer должен выполнить вставку inbox с уникальным ключом и менять состояние заказа в той же PostgreSQL-транзакции. Если inbox row уже существует, бизнес-изменение не повторяется, после чего consumer может продвинуть offset. Сам commit не отменяет возможность повторного вызова обработчика.

</details>
