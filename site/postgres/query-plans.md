# Планировщик и диагностика запросов

## Коротко

EXPLAIN показывает план; EXPLAIN ANALYZE **исполняет** запрос и добавляет
измерения. Сравнивайте ожидаемое и фактическое число строк, повторения узлов,
фильтрацию и buffers. Стоимость planner не измеряется в миллисекундах.

## Как работает

Planner выбирает способ чтения и соединения таблиц по оценкам стоимости.
Оценки cardinality опираются на статистику: доли NULL, distinct values,
распределения частых значений и гистограммы. После существенного изменения
данных ANALYZE может исправить устаревшие оценки; корреляции нескольких полей
иногда требуют extended statistics.

| Наблюдение | Что выяснить дальше |
| --- | --- |
| actual rows значительно больше estimated rows | Статистика, skew, коррелированные predicates |
| Небольшой узел имеет огромное loops | Сколько общей работы порождает внешний цикл |
| Много Rows Removed by Filter | Можно ли сократить входящие строки раньше |
| Sort пишет на диск | Размер входа, порядок индекса, память на операцию |
| Много shared read blocks | Объём данных и состояние cache; это не обязательно физический диск |

Nested Loop многократно вызывает внутреннюю сторону и может быть хорош с
маленькой внешней выборкой и индексом. Hash Join строит hash table одной стороны;
рост объёма может приводить к batches и временным файлам. Merge Join использует
сортированные потоки; получение такого порядка тоже стоит ресурсов.

Начинайте с места первого существенного расхождения estimates и actuals.
Дорогой верхний узел может быть следствием неверной оценки глубже. В текстовом
плане actual time/rows при нескольких loops обычно представлены на один loop:
не складывайте времена родителей и детей, поскольку они включают друг друга.

## Пример

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
SELECT id FROM history
WHERE customer_id=42 ORDER BY created_at DESC LIMIT 20;
```

Подготовка: `./lab.sh run query-plan`. Сценарий создаёт данные, выполняет ANALYZE,
печатает план до индекса и после него, проверяет совпадение результата.
Не фиксируем единственный правильный plan node: planner учитывает среду.

На интервью проговорите порядок: формулирую проблему → получаю параметры и
репрезентативные данные → смотрю план → выбираю одну гипотезу → меняю один фактор
→ сравниваю работу, время и цену записи. Ускорение на пустой таблице не отвечает
на вопрос о рабочей нагрузке.

## Ошибки и ограничения

- ANALYZE в EXPLAIN выполняет INSERT/UPDATE/DELETE. В учебной БД можно обернуть
  в BEGIN/ROLLBACK; sequence и внешние эффекты функций не обязательно откатятся.
- `work_mem` — не общий бюджет сервера: одновременно могут работать несколько
  узлов, workers и сессий. Глобальное увеличение по одному запросу опасно.
- Buffer hit не означает отсутствие работы; CPU, сортировка и обработка tuples
  остаются. Buffer read может быть обслужен OS cache.
- Принудительное отключение Seq Scan помогает исследованию, но не является
  доказательством, что новый индекс хорош для production.
- Параметры prepared statement могут иметь разную селективность; сравнивайте
  generic/custom plan в условиях, близких к клиентскому вызову.

## Самопроверка

1. Почему одинаковый SQL имеет разное время на повторных запусках?
2. Что означает 10 строк при loops=10000?
3. Почему ANALYZE не всегда исправляет плохую оценку?

<details><summary>Разбор</summary>

1. Cache, конкурентная нагрузка, IO и выбор плана различаются. Зафиксируйте
   условия и не делайте вывод по одному запуску.
2. В среднем узел выдаёт 10 строк за вызов, то есть порядка 100000 за все вызовы.
   Учитывайте формат отображения и округление.
3. Обычная статистика может не описывать корреляции predicates или редкие
   значения достаточно хорошо. Нужна проверка гипотезы, а не повтор ANALYZE вслепую.
</details>
