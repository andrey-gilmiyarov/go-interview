# Хранение и MVCC

## Коротко

MVCC позволяет читателю видеть согласованный набор версий строк, пока другой
клиент изменяет данные. UPDATE обычно создаёт новую версию, а прежняя остаётся
доступной старым snapshots. Поэтому число логических строк, число физических
версий и размер таблицы — разные величины.

## Как работает

Обычная таблица хранится в heap-страницах; индексы задают дополнительные пути
доступа к версиям строк. Заголовок tuple содержит информацию о создавшей и
изменившей её транзакциях. Видимость определяется snapshot и состояниями
транзакций; сравнение одного `xmin` с текущим ID не является алгоритмом MVCC.
`ctid` указывает физическое расположение версии, а не постоянный бизнес-ID.

```text
heap:  версия A ──UPDATE──> версия B
          ↑                   ↑
     старый snapshot      новый snapshot
          └──── очистка A разрешена, когда она больше никому не нужна
```

HOT может позволить обновление без новых записей в обычных индексах, если
изменения индексируемых значений не требуют их обновления и на heap-странице
есть место. Это оптимизация, а не обещание для любого UPDATE. Широкие строки,
частые обновления и количество индексов влияют на стоимость записи.

VACUUM делает место умерших версий повторно используемым, обслуживает visibility
map и freezing. Autovacuum запускает эту работу автоматически; ANALYZE собирает
статистику для планировщика и решает другую задачу. Отключение autovacuum на
рабочей системе ради скорости откладывает стоимость и создаёт новые риски.

Долго живущий snapshot может удерживать версии. Важна не просто давность BEGIN:
лаборатория использует Repeatable Read и выполняет чтение, чтобы действительно
зафиксировать snapshot. Диагностируйте `backend_xmin`, возраст транзакции и
wait events вместе, не объявляйте любую долгую сессию виновником.

## Пример

Из каталога лаборатории выполните `./lab.sh run long-transaction`.

| Шаг | Сессия A | Сессия B |
| --- | --- | --- |
| 1 | BEGIN REPEATABLE READ; чтение 1000 старых значений | — |
| 2 | Snapshot остаётся открытым | UPDATE всех значений; COMMIT |
| 3 | Повторное чтение видит прежние значения | VACUUM VERBOSE сообщает об очистке |
| 4 | COMMIT | Второй VACUUM получает возможность убрать старые версии |

Эксперимент печатает отчёт VACUUM. Его сравнивают с результатом SELECT; точный
размер relation не используется как критерий успешности.

## Ошибки и ограничения

- MVCC не означает отсутствие блокировок: писатели могут ждать писателей,
  а DDL — конфликтовать с читателями.
- Обычный VACUUM обычно оставляет освобождённое место внутри файла. VACUUM FULL
  переписывает таблицу и требует сильной блокировки; это отдельная операция.
- DELETE миллионов строк не обещает немедленного возврата дискового пространства.
- Большой `n_dead_tup` — оценка для диагностики, не точный счётчик каждой версии.
- Долгие snapshots — не единственный фактор: также проверяют replication slots,
  нагрузку записи и способность autovacuum успевать за ней.

## Самопроверка

1. Почему после удаления половины данных файл почти не уменьшился?
2. Чем idle connection отличается от idle in transaction со snapshot?
3. Почему добавление индекса может ухудшить UPDATE?

<details><summary>Разбор</summary>

1. Удаление меняет видимость. После очистки пространство может остаться для
   последующих записей; уменьшение файла не входит в обещание обычного DELETE.
2. Соединение без транзакции не удерживает её snapshot. Открытая транзакция
   также может удерживать locks; смотрите фактическое состояние, а не только uptime.
3. Новые версии требуют обслуживания индексов; индексируемое изменение может
   исключить HOT. Выигрыш чтения надо сравнивать с стоимостью записи и очистки.
</details>
