# Индексы: путь чтения и цена записи

## Коротко

Индекс — дополнительная структура, которая может уменьшить работу чтения,
но требует места и обслуживания при записи. Его выбирают под запрос и
распределение данных; наличие индекса не обязывает planner его использовать.

## Как работает

| Тип | Полезный сценарий | Цена или ограничение |
| --- | --- | --- |
| B-tree | Равенство, диапазон, ORDER BY | Порядок столбцов должен соответствовать доступу |
| GIN | Несколько ключей внутри значения, например JSONB containment | Стоимость обновлений и выбор operator class |
| BRIN | Очень большая таблица с корреляцией значений и физического порядка | Lossy диапазоны страниц требуют recheck |

В PostgreSQL 17 составной B-tree особенно эффективен при ограничениях по
ведущим колонкам. Индекс `(customer_id, created_at DESC)` подходит для истории
конкретного клиента. Для общей ленты по времени он не эквивалентен индексу
`(created_at DESC)`. Это не значит, что любой запрос без первого столбца
физически не может использовать индекс; вопрос в объёме просматриваемой структуры.

Partial index хранит только строки, удовлетворяющие predicate. Planner должен
доказать, что условие запроса подразумевает predicate; параметризованный запрос
и generic plan могут мешать такому доказательству. Expression index полезен
для согласованного выражения, например `lower(email)`, но выражение и collation
должны соответствовать запросу.

INCLUDE добавляет данные, нужные для результата, без включения их в ключ
поиска. Index-only scan всё равно зависит от visibility map: если видимость
heap-страницы нельзя подтвердить по ней, потребуются Heap Fetches. Индекс
«покрывает колонки» не означает «heap никогда не читается».

## Пример

`./lab.sh run query-plan` создаёт 100000 заказов и сравнивает планы:

```sql
CREATE INDEX history_customer_created
ON history(customer_id, created_at DESC) INCLUDE(id);

SELECT id FROM history
WHERE customer_id=42 ORDER BY created_at DESC LIMIT 20;
```

Фильтр ограничивает клиента; порядок индекса позволяет искать последние
заказы без сортировки всей его истории. В реальной пагинации добавьте
детерминированный tie-breaker `id`, если времена могут совпасть: тогда запрос,
индекс и cursor должны использовать `(created_at, id)` согласованно.

Для active orders можно рассмотреть partial index с `WHERE status='active'`.
Перед добавлением измерьте долю active, нагрузку UPDATE статуса и существующие
индексы: полезность не определяется одним названием поля.

## Ошибки и ограничения

- Индекс по низкоселективному признаку не обязательно выгоден для большой доли таблицы.
- Несколько одиночных индексов не всегда заменяют составной индекс с нужным ORDER BY.
- OFFSET должен пройти пропускаемые строки. Keyset pagination меняет контракт
  курсора и требует полного устойчивого порядка.
- JSONB не отменяет проектирование: часто используемый атрибут может быть лучше
  отдельной колонкой с типом и ограничением.
- Удаление «неиспользуемого» индекса требует репрезентативного окна наблюдения:
  редкий важный запрос тоже имеет значение.

## Самопроверка

1. Почему planner выбрал Seq Scan при наличии индекса?
2. Почему Index Only Scan показал Heap Fetches?
3. Подойдёт ли `(tenant_id, created_at)` для поиска по одному created_at?

<details><summary>Разбор</summary>

1. Сравните селективность, размер таблицы, estimates и стоимость случайного
   доступа. Индекс может требовать больше работы, чем последовательное чтение.
2. Наличие колонок в индексе не доказывает видимость версий для snapshot;
   соответствующие heap-страницы пришлось проверить.
3. Такой запрос может затрагивать большую часть индекса. Для PostgreSQL 17
   оценивайте реальный план и объём чтения, не переносите оптимизации другой major.
</details>
