# PostgreSQL из Go

## Коротко

Для PostgreSQL-сервиса лаборатория использует pgxpool. Pool разделяется между
обработчиками; транзакция привязана к одному соединению. Корректность требует
явного завершения транзакций, освобождения rows и обработки неопределённого
исхода записи, а не только проверки `err != nil`.

## Как работает

| Задача | database/sql | Нативный pgx |
| --- | --- | --- |
| Пул | sql.DB | pgxpool.Pool |
| Транзакция | sql.Tx | pgx.Tx |
| Нет строки | sql.ErrNoRows | pgx.ErrNoRows |
| PostgreSQL-возможности | Через драйвер/адаптер | CopyFrom, SendBatch, специализированные типы |
| Отмена Begin | Context BeginTx связан с жизнью sql.Tx | Context Begin/BeginTx не обеспечивает автоматический rollback |

Для pgx после успешного Begin сразу планируйте rollback; после commit повторный
rollback безвреден в смысле данных, но возвращает ошибку закрытой транзакции.
Cleanup должен иметь отдельный короткий context, потому что request context
мог уже истечь. Одно pgx.Conn нельзя использовать как общий конкурентный pool.

Размер пула выбирается совместно с лимитом БД и количеством экземпляров сервиса.
Большой pool не устраняет блокировки, медленные запросы или неверные границы
транзакции. Метрики ожидания acquire и занятых connections помогают отличить
насыщение пула от времени выполнения SQL.

Query возвращает поток rows: закрывайте его и проверяйте `rows.Err()` после
итерации. Нельзя оставить недочитанный результат и считать connection свободным.
BatchResults тоже нужно закрыть; ошибки могут появляться при чтении результатов
и Close. CopyFrom удобен для массовой загрузки, но не отменяет constraints.

## Пример

Каноническая покупка, идемпотентность, claim/ACK и чтение находятся в отдельных
небольших файлах операций. Полный код виден в [разборах](practice/), чтобы не
раскрывать условия раньше времени.

```go
// После успешного Begin:
defer func() {
    cleanup, cancel := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel()
    _ = tx.Rollback(cleanup)
}()
// Все связанные запросы выполняются через tx, затем проверяется tx.Commit(ctx).
```

`./lab.sh run go-pool` удерживает единственное соединение, проверяет deadline
второго acquire, отменяет долгий запрос и доказывает возможность снова читать
данные после cleanup. Выполняемый пример CopyFrom/batch проверяется командой
из [README лаборатории](lab).

### Политика ошибок

| Ошибка | Действие учебного клиента |
| --- | --- |
| 40001 / 40P01 | Ограниченно повторить всю транзакцию и перечитать данные |
| 23505 | Разобрать нарушенный бизнес-ключ; не повторять вслепую |
| Deadline / cancellation | Завершить операцию, освободить ресурсы |
| Сетевой сбой COMMIT | Исход неизвестен; восстановить результат по ключу |

Retry helper не оборачивает внешние эффекты. Его тест внедряет транспортную
ошибку и доказывает один вызов; это unit-проверка политики, не эмуляция настоящего
разрыва сети после server commit.

## Ошибки и ограничения

- Открыть транзакцию и вызвать `pool.Exec` вместо `tx.Exec` — выполнить запрос
  на другом соединении, за пределами нужной атомарности.
- Deadline может истечь, когда сервер уже применил запись. Ошибка клиента
  не равна доказательству отсутствия эффекта. Закрытие соединения после отмены
  может завершаться асинхронно: мгновенное NOWAIT не является проверкой
  корректного cleanup; ограничивайте ожидание и наблюдайте итог.
- Подключение к PgBouncer и режим prepared statements требуют отдельной проверки
  конфигурации; эту топологию лаборатория не моделирует.
- Стандартный database/sql тоже подходит для production. Нативный pgx выбран
  ради PostgreSQL API, а не обещания универсального ускорения любого сервиса.

## Самопроверка

1. Почему размер pool=100 может ухудшить latency?
2. Достаточно ли defer rows.Close без rows.Err?
3. Что произойдёт с pgx-транзакцией после отмены request context?

<details><summary>Разбор</summary>

1. Больше активных запросов конкурируют за ресурсы и locks; нужно ограничивать
   параллелизм в соответствии с capacity, а не только увеличивать очередь внутри БД.
2. Нет: итерация может завершиться из-за ошибки, которую сообщает rows.Err.
3. Нельзя полагаться на автоматический rollback. Явно завершите транзакцию
   отдельным cleanup-context и проверьте поведение соединения.
</details>
