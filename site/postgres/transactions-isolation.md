# Транзакции и изоляция

## Коротко

Транзакция объединяет изменения, но сама по себе не делает корректным алгоритм
«прочитай, реши, запиши». Уровень изоляции определяет допустимые наблюдения.
Правильный выбор начинается с бизнес-инварианта: например, невозможно продать
больше единиц товара, чем есть на складе.

## Как работает

Atomicity означает общий исход изменений транзакции; consistency требует
корректных ограничений и алгоритма приложения. Isolation ограничивает влияние
конкурентных транзакций. Durability зависит от настроек подтверждения записи и
хранилища; отдельно она разбирается в главе эксплуатации.

| PostgreSQL 17 | Snapshot чтения | Главная граница |
| --- | --- | --- |
| Read Committed, по умолчанию | Новый для каждого statement | Два SELECT одной транзакции могут различаться |
| Repeatable Read | От первого statement, которому нужен snapshot | Стабильное чтение не исключает write skew |
| Serializable | Snapshot плюс обнаружение опасных зависимостей | Возможен abort; приложение должно повторить транзакцию |

Read Uncommitted в PostgreSQL ведёт себя как Read Committed. PostgreSQL
Repeatable Read предотвращает phantom reads, но не все serialization anomalies.
Собственные изменения видны транзакции; sequence имеет отдельную семантику и
не откатывает выданные значения вместе с ней.

Write skew: два склада содержат по единице товара. Правило — нельзя убрать
последнюю доступную единицу из всей сети. Обе транзакции видят сумму 2 и
обнуляют разные строки. Конфликта записи одной строки нет, но общий инвариант
нарушен. Возможные решения: Serializable с повтором, явная общая блокировка
или изменение модели инварианта. Выбор зависит от contention и границ операции.

## Пример

`./lab.sh run isolation` воспроизводит смену видимости и write skew.

| Шаг | A | B |
| --- | --- | --- |
| 1 | Читает сумму 2 | Читает сумму 2 |
| 2 | Обнуляет склад 1 | Обнуляет склад 2 |
| 3 | COMMIT | COMMIT |

В Repeatable Read обе транзакции могут завершиться. В Serializable такое
расписание приводит к `40001`; повтор должен заново прочитать данные и
переоценить решение. Лаборатория не требует, чтобы проиграла конкретная сессия.

Для одного остатка часто достаточно условного UPDATE:

```sql
UPDATE products SET stock=stock-1 WHERE id=1 AND stock>=1 RETURNING stock;
```

Ноль строк — бизнес-результат «товара недостаточно», не повод бесконечно
повторять запрос. Если создаётся заказ, INSERT и UPDATE принадлежат одной
транзакции; иначе можно списать остаток без заказа.

## Ошибки и ограничения

- Повторять только упавший statement недостаточно: решение принято по старым данным.
- Ошибка соединения при COMMIT не доказывает rollback. Проверяйте результат по
  бизнес-ключу; автоматический повтор может дублировать эффект.
- Serializable не делает внешнее письмо или HTTP-вызов откатываемым.
- Долгая транзакция увеличивает окно конфликтов. Не держите её открытой во время
  пользовательского ввода или сетевого запроса к стороннему сервису.

## Самопроверка

1. Предотвращает ли Repeatable Read потерянное обновление в любом приложении?
2. Почему retry обязан повторять проверку остатка?
3. Можно ли выбрать победителя Serializable заранее?

<details><summary>Разбор</summary>

1. Конкурентное изменение одной строки внутри RR может завершиться ошибкой,
   но чтение вне этой транзакции и последующая запись готового значения всё
   равно требуют анализа. Названия уровня недостаточно для доказательства.
2. После abort другая транзакция могла изменить условия. Повтор старого решения
   сохраняет ошибку даже при успешном новом COMMIT.
3. Нельзя строить бизнес-логику на том, кто будет abort-нут. Проверяют общий
   инвариант и обрабатывают ошибку у любой стороны.
