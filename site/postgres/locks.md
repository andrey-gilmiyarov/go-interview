# Блокировки и конкурентная работа

## Коротко

Блокировки защищают конфликтующие операции. Ожидание блокировки не равно
deadlock: deadlock требует цикла зависимостей. На собеседовании полезнее
нарисовать граф «кто кого ждёт», чем перечислить все имена lock modes.

## Как работает

PostgreSQL сочетает table-level и row-level locks. Обычный SELECT берёт
ACCESS SHARE; его конфликт с ACCESS EXCLUSIVE важен для DDL. UPDATE и
SELECT FOR UPDATE участвуют в блокировке строк. Совместимость зависит от
режима, а не только от того, «чтение» это или «запись».

```text
A держит строку 1 ──ждёт строку 2──> B
A <──ждёт строку 1── B держит строку 2
```

После обнаружения deadlock одна транзакция получает `40P01`. Остальные могут
продолжиться, когда её locks освобождены. Сокращение timeout не исправляет
порядок захвата. Общий порядок по ID устраняет этот конкретный цикл, если все
участники соблюдают его для всех нужных ресурсов.

`FOR UPDATE` применим, когда решение требует прочитать и затем изменить строку
под защитой транзакции. Условный UPDATE проще для одношагового инварианта.
`NOWAIT` превращает невозможность немедленного захвата в ошибку.
`SKIP LOCKED` пропускает занятые строки и подходит для конкурентной выборки работ;
это не согласованный обзор всей таблицы и не гарантия справедливости.

Advisory locks координируют договорённость приложения. База не знает, какие
данные они должны защищать. Session lock живёт на соединении; transaction lock
ограничен транзакцией. Вернуть connection с session lock в pool без освобождения
опасно. Лаборатория удерживает guard connection до завершения сценария.

## Пример

`./lab.sh run deadlock` сначала воспроизводит цикл, затем единый порядок.
Для ручной диагностики:

```sql
SELECT pid, state, xact_start, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocked_by
FROM pg_stat_activity WHERE datname=current_database();
```

Сначала найдите блокирующую цепочку, затем причину долгой транзакции. Запрос,
который сейчас ничего не делает, может удерживать lock после предыдущего
statement. Текст текущего query не описывает всю историю транзакции.

## Ошибки и ограничения

- Row lock не обязательно представлен отдельной очевидной строкой в pg_locks:
  ожидание может отражаться как ожидание transaction ID.
- `lock_timeout` ограничивает ожидание lock; `statement_timeout` — выполнение
  statement в целом. Это разные бюджеты.
- Locks обычно живут до конца транзакции; rollback к savepoint может освободить
  locks, приобретённые после него.
- Не держите транзакцию claim во время долгой обработки очереди. Для обработки
  вне транзакции нужны lease, восстановление и защита от устаревшего worker.

## Самопроверка

1. Как отличить медленный SQL от ожидания lock?
2. Почему SKIP LOCKED не обеспечивает exactly-once эффект?
3. Решает ли увеличение pool проблему блокирующей транзакции?

<details><summary>Разбор</summary>

1. Проверьте wait_event и blocking PID, возраст транзакций и план. Один только
   elapsed time не показывает, где прошло время.
2. После эффекта worker может упасть до ACK. Повторный worker не знает, был ли
   эффект выполнен; нужен идемпотентный получатель или другая атомарная граница.
3. Нет: появятся дополнительные ожидающие соединения и нагрузка. Исправляют
   долгую транзакцию, порядок захвата и бюджеты ожидания.
</details>
