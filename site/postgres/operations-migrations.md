# Миграции и эксплуатация

## Коротко

Миграция должна быть совместима с одновременно работающими версиями приложения.
Время SQL на пустой таблице не описывает время ожидания locks на рабочей БД.
Безопасный порядок — расширить схему, перевести запись, заполнить старые данные,
проверить инвариант и только затем убрать прежний контракт.

## Как работает

Expand/contract разделяет изменения по времени. Например, новая обязательная
колонка сначала nullable. Новый код начинает её заполнять; backfill обновляет
старые строки ограниченными диапазонами PK. После перевода всех writers
проверяют заполненность и усиливают constraint. Старый код должен оставаться
совместимым до явно определённого cutover.

`CHECK ... NOT VALID` не сканирует старые строки при добавлении, но новые
изменения уже обязаны соблюдать constraint. VALIDATE проверяет историю с
более мягким режимом блокировки, чем многие DDL. Для NOT NULL валидированный
CHECK может позволить избежать повторного полного сканирования, однако lock
на короткую DDL-операцию всё равно нужен.

CREATE INDEX CONCURRENTLY позволяет продолжать обычные записи, но делает
дополнительную работу и может ждать старые транзакции. Его нельзя включать в
transaction block. После ошибки проверьте `indisvalid`: неудачная попытка может
оставить invalid index, который надо разобрать перед повтором.

### WAL и подтверждение записи

WAL описывает изменения для восстановления. Правило write-ahead требует
необходимую запись журнала до сохранения соответствующей изменённой страницы.
Checkpoint задаёт границу восстановления и работу записи dirty pages; это
не commit каждой отдельной транзакции.

При обычной синхронной локальной записи COMMIT ждёт нужного flush WAL. Это
не означает, что бизнес-строка уже записана в основной файл таблицы или доступна
на асинхронной реплике. `synchronous_commit=off` меняет момент подтверждения и
риск потери недавно подтверждённых изменений при crash. Отключение fsync —
другая, значительно более опасная настройка, не учебная оптимизация.

Чтение с asynchronous replica может отставать от записи на primary.
Read-your-writes требует выбранного маршрута чтения или координации по позиции
репликации. Сам факт успешного COMMIT на primary этого не решает.

## Пример

В лаборатории `examples/migration.sql` выполняет backfill, NOT VALID/VALIDATE
и concurrent index build. Проверка запускается так:

```sh
go test -tags=integration ./internal/lab -run TestMigrationAndBulkExamples -v
```

Пример использует маленький диапазон ID, а не обещает безостановочную миграцию
любой таблицы. Для production заранее определяют размер batch, нагрузочный
бюджет, lock timeout, контроль оставшихся строк и совместимость writers.

При инциденте: отделите wait от compute, найдите blocking PID, проверьте возраст
транзакций, активность autovacuum и состояние диска/WAL. Прерывание blocking
session — операционное решение с последствиями rollback, не первый рефлекс.

## Ошибки и ограничения

- Долгое ожидание короткого ALTER TABLE может задерживать очередь запросов.
- Backfill одной большой транзакцией увеличивает WAL, locks и время восстановления.
- NOT VALID — не разрешение писать новые невалидные строки.
- CONCURRENTLY не означает бесплатно, мгновенно или без любых ожиданий.
- Успешный healthcheck контейнера не доказывает исправность бизнес-запроса.

## Самопроверка

1. В каком порядке вводить обязательную колонку, если старый код ещё работает?
2. Почему concurrent index build может долго ждать?
3. Почему после COMMIT чтение с реплики не находит запись?

<details><summary>Разбор</summary>

1. Сначала совместимое расширение, затем перевод writers и backfill,
   проверка данных, constraint, позднее удаление старого пути.
2. Он координируется с транзакциями и snapshots; проверьте конкретную фазу и
   долгие транзакции, а не только процент CPU.
3. Асинхронное применение WAL может отставать. Определите гарантию чтения
   и маршрут на primary или механизм ожидания нужной позиции.
</details>
