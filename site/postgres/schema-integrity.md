# Схема и целостность

## Коротко

Схема — часть алгоритма корректности. Проверка в Go «такой записи ещё нет»
не защищает от конкурентной вставки. Инварианты, которые PostgreSQL способен
проверять, закрепляйте constraints, а бизнес-ошибки отделяйте от сбоев БД.

## Как работает

PRIMARY KEY даёт уникальную идентичность и NOT NULL. UNIQUE защищает ключ
при конкурентной записи; обычный UNIQUE допускает несколько NULL, если не
выбран `NULLS NOT DISTINCT`. CHECK запрещает строки с результатом false,
но unknown/NULL не заменяет NOT NULL. FOREIGN KEY поддерживает ссылочную
целостность, однако индекс на ссылающейся стороне автоматически не создаётся.

CHECK отдельной строки не защищает произвольный агрегат по другим строкам.
Для инварианта «суммарный запас положителен» нужна другая модель или
конкурентный протокол. В задаче остатков CHECK(stock>=0) не предотвращает
создание двух заказов после записи одним и тем же прочитанным значением.

| Данные | Решение и существенная граница |
| --- | --- |
| Идентификатор | identity удобен, но gaps нормальны; это не номер без пропусков |
| Деньги | bigint в минимальных единицах либо numeric с явными правилами масштаба; float не даёт точной десятичной арифметики |
| Момент события | timestamptz; отдельно хранить исходную зону, если она часть бизнес-смысла |
| Дополнительные атрибуты | JSONB с понятным контрактом; часто используемые ограничения удобнее в типизированных колонках |

`timestamptz` представляет момент времени и отображается в зоне сессии;
исходное имя зоны не сохраняется. `now()` фиксируется на начале транзакции,
а `clock_timestamp()` меняется во время неё — различие существенно для lease.

## Пример

`./lab.sh run idempotency` запускает два одинаковых запроса создания заказа.
Ключ запроса защищён UNIQUE; первый INSERT использует ON CONFLICT DO NOTHING.
Если конкурент уже создал строку, отдельный SELECT в Read Committed читает
результат и сравнивает product/quantity.

```sql
INSERT INTO orders(request_key,product_id,quantity)
VALUES ('request-1',1,1)
ON CONFLICT(request_key) DO NOTHING
RETURNING id;
```

Пустой RETURNING не равен «заказа нет». Конфликтующая строка могла быть невидима
snapshot этого statement. Следующий statement получает новый snapshot.
В учебном контракте ключи не удаляются во время запросов; для retention ключей
в production надо отдельно определить срок действия идемпотентности.

Новый заказ и списание stock выполняются в одной транзакции. Если stock
недостаточен, INSERT откатывается. Повтор с другим payload — отдельная ошибка,
а не молчаливое возвращение заказа с другим смыслом.

## Ошибки и ограничения

- UPSERT не выбирает бизнес-политику конфликта за разработчика.
- FK не заменяет проверку полномочий клиента и принадлежности tenant.
- Sequence не доказывает порядок COMMIT, а её gaps не доказывают потерю данных.
- JSONB-индекс должен соответствовать используемым операторам.
- Ошибки constraints анализируют по SQLSTATE и полям PgError, не по локализованному тексту.

## Самопроверка

1. Достаточно ли SELECT перед INSERT для уникальности email?
2. Почему UNIQUE nullable-поля может допустить «дубликаты»?
3. Можно ли повторить создание заказа после обрыва COMMIT?

<details><summary>Разбор</summary>

1. Нет, между проверкой и записью другой клиент может вставить ту же запись.
   UNIQUE — арбитр; приложение переводит конфликт в свой контракт.
2. По умолчанию NULL не считается равным другому NULL. Уточните нужную
   семантику, NOT NULL или NULLS NOT DISTINCT.
3. Только с протоколом восстановления результата: например, тем же бизнес-ключом
   и проверкой payload. Сетевой сбой не сообщает, состоялся ли commit.
</details>
