# PostgreSQL handbook для Go backend developer

Статус: утверждена пользователем 2026-10-03; реализация завершена и проверена.
Дата: 2026-10-03.

## Цель и согласованные решения

Самодостаточный русскоязычный раздел существующего handbook для повседневной
работы с PostgreSQL и углублённой подготовки к Senior Go/backend-собеседованиям.
Маршрут: механизм PostgreSQL → backend-сценарий → задача на собеседовании.
Читатель уже знает базовый SQL; полноценный курс JOIN, GROUP BY, CTE и оконных
функций не входит в объём. PostgreSQL-специфичные конструкции объясняются на месте.

Пользователь выбрал отдельную PostgreSQL-лабораторию с Docker Compose и нативный
`pgx` + `pgxpool` как основной Go API. `database/sql` разбирается отдельно для
сопоставления API и поведения, без дублирования всей практики.
Сайт предназначен для чтения и разбора, выполнение SQL и Go-кода — локально.

Остальные детали ниже — предлагаемое устройство раздела для утверждения этой
спецификации. Результат реализации и проверки зафиксирован в [отчёте](../reports/postgresql-verification.md).

## Содержание

Восемь глав составляют основной маршрут. Индекс, лаборатория и интервью-практика
имеют отдельные страницы и не входят в счётчик глав.

| ID | Глава | Обязательные темы и результат |
| --- | --- | --- |
| `storage-mvcc` | Хранение и MVCC | Heap, страницы, версии строк, snapshots, видимость, UPDATE/DELETE, HOT, VACUUM и autovacuum. Читатель объясняет связь долгих транзакций, очистки и роста таблицы. |
| `transactions-isolation` | Транзакции и изоляция | ACID в границах PostgreSQL, Read Committed, Repeatable Read, Serializable, lost update, write skew, полный повтор транзакции. Читатель прогнозирует расписание двух сессий. |
| `locks` | Блокировки и конкурентная работа | Row/table locks, FOR UPDATE, deadlock, порядок захвата, lock timeout, advisory locks и SKIP LOCKED. Читатель находит блокирующую сессию и выбирает корректный способ координации. |
| `indexes` | Индексы | B-tree, составные, partial, expression, INCLUDE, index-only scan и visibility map, назначение GIN/BRIN, цена записи. Читатель аргументирует индекс под фильтрацию, сортировку и пагинацию. |
| `query-plans` | Планировщик и диагностика запросов | EXPLAIN (ANALYZE, BUFFERS), estimated/actual rows, loops, scans, joins, statistics, ANALYZE, sort/spill. Читатель отличает неверную оценку, лишнюю работу и ожидание ресурса. |
| `schema-integrity` | Схема и целостность | PK/FK/UNIQUE/CHECK, NULL, identity/sequence, numeric и деньги, timestamptz, JSONB, ON CONFLICT, идемпотентность. Читатель переносит инварианты из ненадёжной проверки перед INSERT в ограничения БД. |
| `go-access` | PostgreSQL из Go | pgxpool, acquire/release, rows lifecycle, context, транзакции, SQLSTATE, retry, неопределённый исход COMMIT, CopyFrom и batch. Отдельный подраздел сопоставляет database/sql и pgx, включая отмену и завершение транзакции. |
| `operations-migrations` | Изменения и эксплуатация | DDL locks, expand/contract, backfill, concurrent index build, NOT VALID/VALIDATE, pg_stat_activity/pg_locks, WAL, checkpoint, durability и вводные границы репликации. Читатель составляет порядок безопасного изменения схемы и диагностики. |

Каждая глава сохраняет семь разделов существующего шаблона: Коротко, Как работает,
Пример, Ошибки и ограничения, Самопроверка, Практика, Источники.
Senior-углубления оформляются подразделами внутри этой структуры.
Минимум три содержательных вопроса самопроверки на главу; ответы объясняют
механизм, условия применимости и компромиссы. Они не подменяют отдельные задания.

Основной текст должен позволять понять тему без перехода во внешний курс.
Официальные версионные документы PostgreSQL, pgx и Go подтверждают утверждения;
дата проверки источников записывается только после фактической проверки.

## Практика

Учебная предметная область — товары, остатки и заказы. Очередь фоновых работ
используется только в сценарии конкурирующих обработчиков. Каждый сценарий
получает собственную подготовку данных и не требует прохождения предыдущего.

Восемь практических единиц включают воспроизводимый эксперимент и отдельную
интервью-задачу с условиями, подсказками и разбором:

| ID | Эксперимент и задача | Проверяемый результат |
| --- | --- | --- |
| `stock-race` | Два покупателя последнего товара; исправление read-modify-write | При исправленном алгоритме ровно одна покупка успешна, остаток неотрицателен. |
| `isolation` | Расписания двух сессий и write skew | Видимые данные и результат commit соответствуют заявленному уровню; retry сохраняет бизнес-инвариант. |
| `deadlock` | Обратный порядок захвата строк | Воспроизведён deadlock; показаны диагностика и исправленный порядок без цикла ожидания. |
| `idempotency` | Повторное создание заказа и конфликт содержимого | Повтор не создаёт второй заказ; другой payload под тем же ключом явно отклоняется. |
| `query-plan` | Выборка заказов на подготовленном наборе данных | Разбор плана до/после, объёма работы и цены индекса; отсутствие жёсткого порога миллисекунд. |
| `job-queue` | Два worker с SKIP LOCKED и сбой обработки | Показаны ownership и восстановление задания; отдельно разобрана возможность повторного внешнего эффекта. |
| `long-transaction` | Долгая транзакция со snapshot и очистка версий | Видно препятствие очистке и его устранение; VACUUM не трактуется как гарантия уменьшения файла. |
| `go-pool` | Занятый пул, отмена запроса, ошибка и завершение транзакции | Ожидание ограничено deadline, ресурсы освобождены; повтор выполняется только при известном допустимом исходе. |

Для SQL-задач условия содержат сценарий сессий и вопросы или фрагмент для
исправления. Для задач реализации Go предусмотрены собираемый starter, отдельное
solution и проверки бизнес-инвариантов. Незавершённый starter не ломает обычные
проверки: его проверки запускаются явно с тегом `exercise`.

Канонические README/SOLUTION живут внутри лаборатории, страницы сайта включают
их без копирования. Полные решения имеют `search: false`; подсказки исключаются
из поиска существующим механизмом. Условие не раскрывает эталонный ответ.

## Лаборатория и зависимости

`labs/postgres` — отдельный Go-модуль и Compose project с одной PostgreSQL.
Go-программы выполняются на хосте; psql доступен через контейнер.
Никакой зависимости от Kafka, Connect, работающей внешней БД или корневых Go-тестов.
Корневой go.mod и существующие лаборатории не меняются для запуска новой практики.

Базовая major-версия — PostgreSQL 17, согласованная с существующими примерами
репозитория. Перед реализацией в плане фиксируется проверенный точный patch-тег
официального образа; `latest` не используется. Версионные особенности новых
major-релизов не выдаются за свойства выбранной среды.
Для Go сохраняется toolchain репозитория; исходная версия pgx — `v5.11.0`, уже
закреплённая в Kafka-модуле. Совместимость подтверждается сборкой новой лаборатории.
Разрешённый прямой Go dependency — pgx; необходимые транзитивные зависимости
фиксируются в go.mod/go.sum. ORM, генератор SQL, сторонний test framework,
миграционный сервис и другие прямые зависимости в объём не входят.

Compose использует отдельные network/volume, loopback-порт с возможностью
переопределения и учебные credentials. README содержит точные команды запуска,
readiness, подготовки данных, сценариев, проверок, остановки и явного reset.
Reset действует только на ресурсы этой лаборатории; остановка сохраняет данные.
Команды изменения данных не выбирают произвольную пользовательскую БД по умолчанию.

Конкурентные сценарии используют барьеры и наблюдаемые состояния с ограниченным
ожиданием. Произвольный sleep не служит доказательством захвата блокировки.
При завершении и ошибке соединения/транзакции закрываются, ожидания ограничены.
Опасность выполнения DML через EXPLAIN ANALYZE объясняется до запуска примера.

## Интеграция сайта

Раздел `site/postgres/` получает индекс, восемь глав, страницу лаборатории и
маршруты практики/решений. `site/data/postgres.json` хранит стабильные ID,
порядок, заголовки, summary, PostgreSQL version, reviewedAt и sources.
По аналогии с Kafka реестр управляет sidebar и метаданными; content checker
проверяет полноту, уникальность, файлы и источники.

Добавляются пункт PostgreSQL в навигации, ссылки с главной и из каталога источников.
Roadmap обновляется по фактически завершённому объёму. README и авторская памятка
объясняют отдельные команды и реестры PostgreSQL, сохраняя маршруты Go/Kafka.
Новые SQL-задачи не подмешиваются в прежний реестр 20 Go-упражнений.

Обязательны компактные таблицы расписаний транзакций и диаграммы при объяснении
MVCC/блокировок. Новые интерактивные Vue-модели не входят в первую версию:
наблюдаемое поведение проверяется в реальной лаборатории.

## Критерии приёмки и верификация

1. Все восемь глав содержат механизм, рабочий пример, ограничения,
   Senior-вопросы, практику и проверенные первичные источники.
2. Все восемь практических единиц имеют отдельные условия и разборы;
   эталонные варианты проверены на реальной PostgreSQL выбранной версии.
3. Сценарии выполняются повторно после документированной подготовки данных,
   ограничивают ожидания и проверяют заявленные инварианты.
4. Проверки планов не требуют одинакового плана или времени на разных машинах;
   измерения и выводы сохраняются с версией, объёмом данных и условиями запуска.
5. `npm run test:site`, `npm run docs:check`, `npm run docs:build` проходят;
   новая навигация и исключение ответов из поиска проверены. Собранные страницы
   визуально проверены на читаемость таблиц и SQL/Go-примеров.
6. В `labs/postgres` выполняются `go test ./...`, `go test -race ./...`,
   `go build ./...` и явная интеграционная проверка всех сценариев с БД.
   Обычные тесты без БД не выдают пропущенные интеграционные сценарии за пройденные.
7. Корневые `go test ./...` и `go build ./...` проверяют отсутствие регрессий
   существующих материалов. Старые exercise failures фиксируются отдельно.
8. Проверены локальные Markdown-ссылки, `git diff --check`,
   `git diff --cached --check` и status. TOML не меняется; его парсинг не требуется.
9. Отчёт в `docs/reports/` перечисляет точные команды, исходы и ограничения.
   Недоступная Docker-среда означает непроверенную лабораторию, а не полную готовность.

## Границы и следующий этап

Полноценный курс SQL, отдельный сервис с HTTP API, ORM, production HA-кластер,
failover, стенд backup/PITR, sharding и глубокое администрирование не входят
в первую версию. WAL и репликация объясняются в объёме, нужном разработчику
для понимания подтверждения записи и чтения с реплик.

После review этой спецификации создаётся отдельный датированный план в
`docs/plans/`, связанный из индекса документации. План определяет точные файлы,
порядок реализации и команды проверки. Реализация начинается после review
плана и выбора способа выполнения согласно применимому workflow.
Без прямого запроса пользователя staging и commits не выполняются.
