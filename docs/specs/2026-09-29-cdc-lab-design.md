# Дизайн CDC-лаборатории Debezium

Дата: 2026-09-29. Статус дизайна: согласован. Статус реализации: **COMPLETE; принято Lead 2026-09-30**; см. [текущий план работ](../plans/2026-09-29-cdc-lab.md) и [отчёт верификации](../reports/cdc-verification.md).

## Цель и границы

Добавить отдельную CDC-лабораторию внутрь существующего модуля `labs/kafka`, используя тот же учебный сценарий заказов. Текущая лаборатория PostgreSQL + polling outbox остаётся рабочей и продолжает объяснять polling. Новая лаборатория показывает отдельный путь доставки через PostgreSQL logical decoding, Debezium и Kafka Connect; переключение существующей polling-лаборатории на CDC в объём не входит.

Использовать уже закреплённые в `labs/kafka` `franz-go` и `pgx`; новые Go-зависимости не добавлять. CDC-код, схемы, Compose-файлы, скрипты и тесты остаются внутри `labs/kafka`. Не добавлять Schema Registry, HA-топологию, стек мониторинга или миграцию работающей лаборатории.

## Матрица сред и образ Connect

Основная среда: broker Kafka `4.3.1` в KRaft, PostgreSQL `17.6`, один worker Kafka Connect и один Debezium connector. Использовать образ `quay.io/debezium/connect:3.6.3` с digest `sha256:5638e8e42c6681d1dfd753324040b7949e3cfe3f8f3aff1e39fc8c0b63c6ccec`, доступный для `linux/amd64` и `linux/arm64`; в конфигурации закрепить digest, а не только тег. Connect REST основной среды сообщает runtime Kafka Connect `4.3.0`, commit `a9ce3221537b8653`, и plugin `io.debezium.connector.postgresql.PostgresConnector` версии `3.6.3.Final`; это версия worker, а не broker. Для Connect задан heap `-Xms512m -Xmx1g`, чтобы JVM могла завершить сканирование bundled plugins. Совместимая учебная среда использует broker Kafka `3.9.2` в режиме ZooKeeper с тем же закреплённым образом; infra, consumer integration и E2E-проверки пройдены для обеих сред. В каждой среде — только один Connect worker/connector; HA не моделируется.

Исторически план ссылался на `3.7.0.Final`, но этот тег отсутствовал в реестре. Пользователь явно утвердил замену на `3.6.3` с указанным digest; это выбранная версия для реализации.

## Контракт события и записи заказа

CDC публикует JSON payload без Debezium envelope, с полями `event_id`, `order_id`, `type`, `version`, `order_version` и `amount_cents`. Kafka key — `order_id`. `version` равен `1` и обозначает версию формата события. Создание заказа выпускает `order_version=1`; успешное обновление выпускает следующую версию. `amount_cents` содержит абсолютную текущую сумму заказа, а не приращение.

Изменение заказа и вставка соответствующей записи outbox выполняются атомарно в одной транзакции PostgreSQL. Записи outbox только добавляются; прикладная роль имеет для outbox права `INSERT` и `SELECT`, без `UPDATE` и `DELETE`. Обновление заказа требует ожидаемую текущую версию. При конкурирующих обновлениях с одной ожидаемой версией ровно одно изменение побеждает, остальные получают конфликт версии.

`event_id` одновременно служит ключом идемпотентности команды. Повтор с тем же ID и теми же типизированными параметрами возвращает сохранённый исходный результат, даже если заказ уже обновляли позднее. Тот же ID с изменёнными параметрами даёт конфликт. Для сравнения параметров сохраняется hash канонических типизированных полей команды, а не исходного JSON-представления.

## CDC-публикация и обработка

PostgreSQL использует `pgoutput`, отдельные publication и replication slot для каждой изолированной среды и отдельную replication-роль. CDC connector читает только вставки outbox. Debezium Outbox Event Router публикует заданный JSON payload без envelope в один учебный topic с тремя partitions, ключом `order_id` и политикой удаления записей через семь дней.

Потребитель обрабатывает записи последовательно и вручную фиксирует Kafka offset. Для каждого события одна транзакция PostgreSQL выполняет проверку inbox/event ID и payload hash, проверку последовательности `order_version` и обновление projection. Offset фиксируется только после успешного commit этой транзакции. Повтор уже известного события с тем же payload пропускается как дубликат. Тот же ID с другим payload, неизвестная старая версия и пропуск версии — ошибка: обработчик останавливается на записи и не фиксирует offset за неё.

Replay использует отдельную projection, consumer group и inbox, поэтому не смешивает повторное построение с текущей проекцией. Topic хранит историю семь дней и использует delete retention: после истечения истории полный replay невозможен; snapshot состояния события не восстанавливает утраченную последовательность изменений.

Интерфейс чтения возвращает `State` JSON с полями `order_id`, `order_version` и `amount_cents`; и source order, и projection используют эту форму. Команды создания и обновления возвращают полное `Event`. Projection отделена от source outbox и не синтезирует `event_id` и не соединяется с таблицей outbox при чтении. Открытие модели заказа выполняет `cdcmodel.Open`.

## Изоляция и операции

Среды Kafka 4.3.1/KRaft и Kafka 3.9.2/ZooKeeper запускаются в отдельных Compose projects со своими named volumes, loopback-only ports, topics, PostgreSQL publication и replication slot. Они не используют проекты и volumes существующей Kafka/polling-лаборатории. Обычный `up` сохраняет состояние; несовместимая с сохранённым состоянием конфигурация должна завершаться явной ошибкой. `down` сохраняет volumes. Удаление состояния возможно только отдельной явно названной операцией reset. В каждой среде отдельно создаются `cdc.orders` и compact heartbeat topic `__debezium-heartbeat.cdc`; Connect использует config, offset и status topics с префиксами `cdc-kraft-connect-` и `cdc-zk-connect-`. `ready` ожидает `RUNNING` connector/tasks и сохранённый ненулевой source LSN после завершения snapshot; это readiness connector, не end-to-end проверка заказа.

Диагностика показывает состояние connector и task, consumer-group lag, состояние replication slot и удерживаемый WAL. PostgreSQL задаёт `max_slot_wal_keep_size=256MiB`, проверяемый на checkpoint; это не жёсткий потолок дискового WAL и не гарантия, что объём всегда останется ниже 256 MiB. При превышении порога требуемые slot-ом сегменты могут быть удалены, и продолжить чтение со старого LSN станет невозможно. Документация объясняет чистый начальный snapshot на пустом outbox: создать чистую среду явным `reset`, выполнить `up`, затем дождаться `ready` и выполнять end-to-end probe. Если начальный snapshot видит накопленные строки outbox, connector может отправить их как snapshot records, но порядок этих строк не гарантирует последовательность истории заказа и не заменяет replay. При недоступности broker consumer может завершиться с сетевой ошибкой; после восстановления Kafka проверяются status и slot, failed Connect tasks перезапускаются штатным REST endpoint, а consumer запускается заново с прежней projection/group. Бесконечные автоматические retry не обещаются; offsets, connector и slot не удаляются. Также разбираются накопленная история, порядок snapshot, ограничения replay при retention, восстановление после потери slot или connector offsets, очистка и отличие CDC от polling. Переключение polling на CDC описывается концептуально.

## Обязательные сценарии проверки

- Сумма заказа: создать `1000`, обновить до `1500`, затем до `1200`; projection содержит абсолютную сумму `1200` и версию заказа `3`.
- Откат атомарной записи заказа/outbox; конкурентные обновления с одной expected version; повтор команды с теми же параметрами и тем же event ID; конфликт при повторе того же ID с изменёнными параметрами.
- Отклонение malformed payload и несовпадения Kafka key с `order_id`; остановка на пропуске версии и неизвестном старом событии без commit offset.
- Детерминированный сбой после commit PostgreSQL, но до commit Kafka offset, затем повторная доставка без двойного эффекта.
- Перезапуск Connect, недоступность Kafka и восстановление доставки с ограниченным удержанием WAL.
- Детерминированные дубликаты и replay в независимые projection/group/inbox на обеих версиях Kafka.
